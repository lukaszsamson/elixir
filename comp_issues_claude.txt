23. defguard EXPANDS ONLY IN GUARD CONTEXT (kernel/utils.ex:331-334) - reported
--------------------------------------------------------------------
  env = :elixir_env.with_vars(%{env | context: :guard}, vars)
  {expr, _, _} = :elixir_expand.expand(expr, :elixir_env.env_to_ex(env), env)

The expanded AST is reused for both the guard branch AND the non-guard
branch. Context-dependent macros (e.g., Kernel.and → :erlang.andalso in
guards, case expression outside) get guard-specific expansions in both.


This looks like a real bug.
What I verified:
1. The implementation does exactly what the report says.
   - lib/elixir/lib/kernel/utils.ex:331-342
   - defguard/3 expands expr once with:
      env = :elixir_env.with_vars(%{env | context: :guard}, vars)
   {expr, _, _} = :elixir_expand.expand(expr, :elixir_env.env_to_ex(env), env)
      - then reuses that single expanded expr for:
     - the Macro.Env.in_guard?(__CALLER__) == true branch
     - the false branch too
2. The non-guard branch really gets guard-specific expansion.
   - Repro:
      Code.compile_string("""
   defmodule G do
     defguard g(x) when x and true
   end
   """, "g.ex")
   ast = quote(do: G.g(foo()))
   IO.puts(Macro.to_string(Macro.expand_once(ast, %{__ENV__ | requires: [G]})))
      - Output:
      {arg1} = {foo()}
   :erlang.andalso(arg1, true)
      - So the non-guard expansion is not arg1 and true; it is the guard form :erlang.andalso/2.
3. This changes observable runtime behavior today.
   - With:
      defmodule G do
     defguard g(x) when x and true
     def run(x), do: g(x)
   end
      - Current behavior:
      G.run(nil)
   # raises ArgumentError: argument error: nil
      - But ordinary Elixir non-guard and semantics are:
      nil and true
   # raises BadBooleanError
      - I confirmed the difference directly:
     - x and true raises BadBooleanError for non-booleans
     - :erlang.andalso(x, true) raises ArgumentError
Why this is a real bug:
- defguard is explicitly supposed to produce:
  - one form for guard contexts
  - another form for ordinary expression contexts
- The module docs in Kernel.Utils.defguard/3 even describe that split.
- Reusing the guard-expanded AST in both branches makes the non-guard branch semantically wrong for context-sensitive operators/macros.
Current triage:
- Real issue: yes
- Reachable: yes
- User-visible: yes
- Severity: correctness bug in defguard expansion
Strongest minimal repro:
defmodule G do
  defguard g(x) when x and true
  def run(x), do: g(x)
end
G.run(nil)
Observed:
- ArgumentError
Expected from non-guard semantics:
- BadBooleanError
So this is a confirmed, present-day bug.

29. DOC SAYS :sigstop BUT @vm_signals HAS :sigterm (system.ex:543-546 vs 138) - PR SUBMITTED
-----------------------------------------------------------------------------
  @doc says:
    By default, the Erlang VM register traps to the three signals:
      * `:sigstop` - gracefully shuts down the VM with `stop/0`
      * `:sigquit` - halts the VM via `halt/0`
      * `:sigusr1` - halts the VM via status code of 1

  Code:
    @vm_signals [:sigquit, :sigterm, :sigusr1]
    @os_signals [:sighup, :sigabrt, :sigalrm, :sigusr2, :sigchld, :sigstop, :sigtstp]

The doc lists :sigstop as a default VM trap, but the code has :sigterm in
@vm_signals and :sigstop in @os_signals. The `trapping?/1` function uses
@vm_signals to decide which signals stay trapped even after all user
handlers are removed. So :sigterm is always-trapped but :sigstop is not —
opposite of what the docs say. SIGSTOP is also untrappable on most Unix

37. expand_captures Arity=0 RELIES ON tl([0]) (elixir_erl_pass.erl:105-117) - not a bug

38. validate_opts SILENTLY SKIPS NON-TUPLE ELEMENTS (elixir_expand.erl:1007-1010) - low priority
--------------------------------------------------------------------------------
  validate_opts(Meta, Kind, Allowed, Opts, E) when is_list(Opts) ->
    [begin
      file_error(Meta, E, ?MODULE, {unsupported_option, Kind, Key})

I1. IO.getn/2 — @spec and clause ordering disagree about 2-arity "device" support
---------------------------------------------------------------------------------
io.ex:532-549

  @spec getn(
          device | chardata | String.Chars.t(),
          pos_integer | :eof | chardata | String.Chars.t()
        ) :: chardata | nodata
  def getn(prompt, count \\ 1)

  def getn(prompt, :eof),      do: getn(:stdio, prompt, :eof)
  def getn(prompt, count) when is_integer(count) and count > 0,
                                 do: getn(:stdio, prompt, count)
  def getn(device, prompt) when not is_integer(prompt),
                                 do: getn(device, prompt, 1)

The @spec advertises `(device, ...)` for the first arg in all second-arg
shapes (including `:eof` and positive integer). Clause 1 and clause 2
unconditionally consume those shapes and treat the first arg as a
*prompt*, never as a device. Consequences:

  * IO.getn(:stdio, :eof)
      => getn(:stdio, :stdio, :eof)
      => reads from :stdio but prints "stdio" as the prompt
  * IO.getn(some_pid, :eof)
      => getn(:stdio, some_pid, :eof)
      => crashes with Protocol.UndefinedError in
         to_chardata(pid) -> to_string(pid)
  * IO.getn(some_pid, 5)  — same story for integer count

Only `IO.getn(device, non_integer_prompt)` actually routes to the
device via clause 3. The @doc at io.ex:524 ("Gets a number of bytes
from IO device `:stdio`") further contradicts clause 3, which does
accept a custom device. So there are three documents that disagree:
the docstring says stdio-only, the @spec suggests any-device, and the
clauses only allow device when the second arg is a non-integer prompt.

Pick one story:
  a) Tighten the @spec to `chardata | String.Chars.t()` as first arg
     (matching the docstring) and drop clause 3, OR
  b) Keep clause 3 and add clauses that handle `(device, :eof)` and
     `(device, pos_integer)` shapes to match the @spec.

Either way the current state is a latent footgun: the @spec type-checks
usages the implementation doesn't actually support.

T3. String.count/2 also raises on `[""]` (list-with-empty-string) although so do split and replace — noting for consistency only - NOT A BUG

lib/elixir/lib/string.ex

The pattern value `[""]` (list containing an empty string) violates
`[nonempty_binary]` in `@type pattern`, so raising is technically
consistent with the type. However:

  * `String.contains?("abc", [""])` → `true`
  * `String.starts_with?("abc", [""])` → `true`

  * `String.replace("abc", [""], "X")` → raises ArgumentError
  * `String.count("abc", [""])` → raises ArgumentError

and then switch to `split`/`count` will be surprised.
