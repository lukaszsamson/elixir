A1. [LOW] `defimpl ... for: <Erlang module>` crashes the type checker
    of.ex:294 (clause 289-299); reached via types.ex:154 (default_domain/4);
    also reachable from the {:impl, for} hint in helpers.ex:116
--------------------------------------------------------------------------------
`Module.Types.Of.impl/2` does

without checking `function_exported?(struct, :__info__, 1)`. The parallel code
in `struct_info/5` (of.ex:505) has the guard; this clause does not. Any loaded
module that does not export __info__/1 (i.e. every Erlang module) crashes
compilation. The crash happens inside Module.Types.infer/7, OUTSIDE the
internal_error! try/rescue, so it aborts compilation with a raw exception.

        Module.Types.Of.impl/2 (of.ex:294)
        Module.Types.default_domain/4 (types.ex:154)

open_map(__struct__: atom([module])) (as `defimpl P3, for: Enum` does).

A3. [HIGH] difference/2 produces non-normalized empty dynamic `%{dynamic: %{}}`;
    later negation/difference from term() raises BadMapError
    descr.ex:504-514 (gradual difference branch, Map.put at :510);
    interacting clause difference_static at :517

right_static) can be %{} and is stored unconditionally, e.g.

Such descrs circulate in practice: fun_apply(dynamic(fun([integer()],
none())), [integer()]) returns {:ok, %{dynamic: %{}}}. Fuzzer hit this in

A4. [LOW] to_quoted_string crashes (or silently corrupts the printed type)
    on unions of static and dynamic fun types
    descr.ex:1945-1962 (fun_denormalize/3 first clause), consumer at :757-758
    https://github.com/elixir-lang/elixir/issues/15523
--------------------------------------------------------------------------------
fun_denormalize's reduce is seeded with the raw inner fun representations
{static_repr, dynamic_repr, []} (maps of arity => bdd) while the caller
(non_term_type_to_quoted, which computes difference(dynamic, static)) expects
full descrs. Two consequences:

(a) CRASH whenever any arity fails to denormalize — leftover integer keys
    reach difference/2 which iterates them as descr kind keys:
    to_quoted_string(difference(fun([term()], atom()),
                                fun([integer()], dynamic(atom()))))
    # ** (FunctionClauseError) no function clause matching in
    #    Module.Types.Descr.difference/3 (first arg = 1, an arity)
    This fires whenever the checker tries to *display* such a type in a
    warning — printing a valid type must never raise.

(b) SILENT TYPE CORRUPTION when denormalization succeeds — all non-fun
    components of both descrs are dropped from the printout:
    to_quoted_string(union(integer(),
        union(fun([integer()], atom()), dynamic(fun([integer()], atom())))))
    # observed: "(integer() -> atom())"
    # expected: "integer() or (integer() -> atom())"
    to_quoted_string renders every type warning, so affected warnings print
    a wrong type.

B1. [FIXED] Map difference: one-key "fast path" builds an unsound union leaf;
    subtype?/equal?/empty? wrong in BOTH directions on map types with negations
    descr.ex:3094-3116 (map_leaf_difference single-key open-negative clause)
    + 3134-3160 (map_leaf_one_key_difference :union arm at 3147-3148),
    consumed by bdd_difference at 6298-6320
    (found independently by 3 auditors + the fuzzer)
    https://github.com/elixir-lang/elixir/issues/15507
--------------------------------------------------------------------------------
bdd_difference computes node \ leaf using a {:one_key_difference, a_diff,
a_union} hint and relies on a_union being EXACTLY a1 ∪ a2 (the dual branch is
D1 \ a_union, valid because ¬a1 ∧ D1 ∧ ¬a2 = D1 \ (a1 ∪ a2)). The
map_difference_strategy path (4613+) only emits the hint when both literals
share tag and all other fields — correct. But the fast path at :3094 fires for
ANY positive literal vs an open single-key negative, including closed or
domain-tagged positives and open positives with extra fields. There
a_union ⊊ a1 ∪ a2, so the computed difference is TOO LARGE: it contains maps
belonging to the subtrahend, and dually subtype? returns false for true
relations.

Repros (all static types):
    a = open_map([a: atom([:x])]); b = closed_map([a: if_set(atom([:x]))])
    subtype?(difference(a, b), a)              # => false; must be true (a\b ⊆ a)

    a = open_map([c: integer()])
    b = negation(open_map([b: integer(), c: union(integer(), float())]))
    subtype?(intersection(a, b), a)            # => false; X ∧ Y ⊆ X universally

    a = closed_map(b: atom([:x, :y]), c: pid())
    b = closed_map(b: if_set(union(atom([:y]), float())),
                   c: union(pid(), union(binary(), integer())))
    c = open_map(c: if_set(union(pid(), binary())))
    subtype?(a, c)                             # => true
    empty?(difference(difference(a, b), c))    # => false; must be true (a ⊆ c)

Key-name dependent (BDD ordering): ~45% of random atom-key pairs fail.
Impact: subtype? wrongly false => spurious type errors downstream (map BDDs
with negations arise from clause/pattern subtraction); empty? wrongly false
for genuinely empty intersections; also misses warnings (the allowed
direction). Root cause verified experimentally: guarding the :union arm to
the exact-shape case (tag == :open and other fields equal) eliminates all
~30 distinct fuzzer violations (30k membership checks + 8k identity checks
go green) with the rest of the suite unaffected.

Current checkout note: the reduced repro now passes after the map-difference
refactors/fixes in the #15433 era:

    a = open_map([a: atom([:x])])
    b = closed_map([a: if_set(atom([:x]))])
    subtype?(opt_difference(a, b), a)          # => true

B2. [HIGH] map_put/map_update rewrite NEGATED BDD leaves, producing result
    types that exclude achievable runtime values
    descr.ex:4059-4099 (map_update_put_domains / map_update_put_domain),
    reached from map_put_static (:4172) and map_update_static (:3816)
    https://github.com/elixir-lang/elixir/issues/15509
--------------------------------------------------------------------------------
The domain-put transformation is applied via bdd_map, which rewrites EVERY
leaf label — including leaves in negated position. Rewriting ¬N into ¬put(N)
enlarges the negated set, so the result type wrongly excludes maps the
runtime operation can produce. The design comment at 4036-4058 ("a negation
will not remove any type from a domain unless it completely cancels out the
type") is disproven by:

(a) negated :closed leaf (4075-4081): ¬empty_map() becomes ¬%{atom() => :x}:
    d = difference(open_map(), empty_map())
    {:ok, res} = map_put(d, atom(), atom([:x]))   # Map.put(m, key::atom(), :x)
    to_quoted_string(res)   # "map() and not %{atom() => :x}"
    subtype?(closed_map(a: atom([:x])), res)      # => false; must be true:
    # Map.put(%{a: :anything}, :a, :x) == %{a: :x} and %{a: :anything} ∈ d

(b) domains-list negation (4085-4097):
    d = difference(open_map([{domain_key(:integer), atom()}]),
                   closed_map([{domain_key(:integer), atom([:y])}]))
    {:ok, res} = map_put(d, integer(), atom([:y]))
    x = difference(closed_map([{domain_key(:integer), atom([:y])}]), empty_map())
    empty?(intersection(x, res))   # => true; every achievable result
    # (e.g. Map.put(%{1 => :z}, 1, :y) == %{1 => :y}) is excluded
Same through map_update/5 and the dynamic paths. Result types narrower than
reality are the false-positive direction. Independent of B1 (persists with B1
patched out).

B3. [HIGH] tuple_fetch returns :badindex for always-valid accesses when the
    size lower bound is established by negations
    descr.ex: decision at 5538; root causes at 5599-5605
    (tuple_pair_projection_keeps_full_fst? shortcut), 5707
    (tuple_take_element -> term_or_optional() for short open positives),
    5717 (tuple_tag_to_type(:closed) -> none())
    https://github.com/elixir-lang/elixir/issues/15491
--------------------------------------------------------------------------------
For a DNF line whose positive is an open tuple shorter than the index, the
projected element carries the :optional marker (term_or_optional()).
Negations that remove exactly the small-arity tuples (where the index would
be absent) can never cancel the marker: closed negatives shorter than the
index project to none(), so they are treated as non-constraining. The
leftover :optional flag then trips `static_optional? or empty?(static_type)`
at :5538 => :badindex.

Repro:
    t = difference(open_tuple([]), tuple([]))   # all tuples of size >= 1
    equal?(t, open_tuple([term()]))             # => true
    tuple_fetch(t, 0)                           # => :badindex  (WRONG)
    tuple_fetch(open_tuple([term()]), 0)        # => {false, :term}
Equivalent minimal form via intersection (auto-shrunk by descr_model.exs,
2026-07-03; verified):
    t = opt_intersection(opt_negation(tuple([])), tuple())
    equal?(t, open_tuple([term()]))             # => true
    tuple_fetch(t, 0)                           # => :badindex  (WRONG)
tuple_fetch is not a congruence wrt equal?. Also fails for
difference(open_tuple([integer()]), tuple([integer()])) at index 1, etc.
Impact: elem/2 (and any tuple_fetch consumer) raises a spurious type error
on such static types; negated tuple types arise from clause subtraction.

B4. [MEDIUM] Redundant-clause false positive: bound variables inside binary
    patterns are treated as fresh
    pattern.ex:990-995 (of_precise_bitstring?), used at :791
    https://github.com/elixir-lang/elixir/issues/15455
--------------------------------------------------------------------------------
A clause is marked `precise?` (and its full type recorded for subsumption of
later clauses) only if its patterns are "precise". For a bare variable
pattern, precision correctly requires freshness (line 817 checks
`not is_map_key(context.vars, version)`), so `def f(x, x)` is imprecise. But
of_precise_bitstring?/1 returns true for `<<x::binary>>` based only on
is_var(expr), without consulting context.vars. When x is bound earlier in
the head, `<<x::binary>>` matches only binaries EQUAL to x, yet the clause is
recorded as covering `binary(), binary()`.

Repro:
    defmodule TRedundant do
      def f(x, <<x::binary>>), do: 1
      def f(a, b) when is_binary(a) and is_binary(b), do: 2
    end
Observed: warning "the following clause is redundant: def f(a, b) ...".
Runtime: TRedundant.f("a", "b") == 2 — the clause is reachable.
Control: `def f(x, x)` + same second clause compiles clean, confirming the
missing freshness check in the bitstring path is the cause.

B5. [MEDIUM] binary/bytes segments ignore the `unit` modifier: typed binary()
    and byte-aligned regardless of unit => multiple false-positive classes
    of.ex:663-664 (specifier_type returns {@binary, :aligned} for
    :binary/:bytes unconditionally); of.ex:619-621 (:aligned -> {0, context}
    skips size*unit alignment); reached from pattern.ex:788
    (found independently by 2 auditors)
    https://github.com/elixir-lang/elixir/issues/15465
--------------------------------------------------------------------------------
elixir_bitstring.erl permits unit 1..256 on binary/bytes segments (only
bitstring is pinned to unit 1). With size*unit not a multiple of 8 the
segment value is a sub-bitstring (NOT a binary) and the segment is not
byte-aligned. of.ex hardcodes value type binary() and alignment 0. Three
verified false-positive classes (all run correctly at runtime):

(1) match refinement / never-match:
    def h(<<n::4>> = b) do
      case b do
        <<x::binary-size(1)-unit(4)>> -> {n, x}
        _ -> :no
      end
    end
    # warning: "the following clause will never match ... which has type:
    #  bitstring() and not binary()"
    # runtime: h(<<5::4>>) == {5, <<5::size(4)>>}
(2) construction: x = <<7::3>>; <<x::binary-size(3)-unit(1)>>
    # warning: incompatible types in binary construction (got bitstring()
    #  and not binary() but expected binary()); runtime: <<7::size(3)>>
(3) inferred domain: def f(<<_x::binary-size(3)-unit(1)>>), do: :ok
    then f(<<7::3>>) warns "expected one of: binary()"; runtime: :ok
Expected: when size*unit is not a multiple of 8 the type should be
bitstring() with alignment size*unit (as already done for bits/bitstring
segments). (Note: the "unit comes before size" assumption in specifier_size
is safe — elixir_bitstring.erl normalizes the order before typing.)

B6. [BY DESIGN/WONT FIX] `for` comprehensions leak variable refinements from

D8. [LOW] compatible_intersection/2 accepts empty inputs that compatible?/2
    rejects
    descr.ex:928-972
    https://github.com/elixir-lang/elixir/issues/15511
--------------------------------------------------------------------------------
`compatible_intersection/2` documents that it returns the intersection "only if
they are compatible. Otherwise returns :error", and most clauses follow
`compatible?/2`'s restricted-consistent-subtyping rule. The special
`compatible_intersection(other, :term)` shortcut does not check compatibility:

    compatible_intersection(none(), term())   # => {:ok, none()}

user-facing false positive by itself. It is still an internal contract bug: the
refinement helper can report success for a pair that the predicate says is not
compatible, which makes compatibility-based laws and callers disagree.

NOTES — OBSERVED ODDITIES JUDGED INTENTIONAL (not counted as bugs)
================================================================================
Re-examined by two independent reviews plus direct empirical checks. Each
item below carries the reconciled verdict. NOTE: the confrontation upgraded
two of these from "intentional/benign" to genuine (low-severity) bugs — see
N4 (diagnostic false negative) and N5 (real precision bug). They are kept in
this section for provenance but are NOT actually "intentional".

N1. fun(1) vs fun([none()], term()) — DOC/PRINTER AMBIGUITY, not soundness.
    Verified: both print "(none() -> term())" but equal? is false; only
    fun([none()], term()) <: fun(1). fun(1) is the abstract arity-1 BDD top
    (descr.ex:174), a strictly larger lattice element than the maximal arrow.
    Both behave identically as tops for concrete arrows (supertype of any
    arrow; absorb arrows under union), so the lattice is internally
    consistent. The fun/1 docstring example `fun(1) #=> (none -> term)` is
    actively misleading (implies equality). Action: clarify the docstring
    and/or disambiguate the printer. Low priority.

N2. map_descr_pair static collapse (descr.ex:2839, trigger at :2846) —
    SOUND-BUT-IMPRECISE gradual-lower-bound precision bug; maintainer call.
    `static_empty? = static_value == @none` collapses the WHOLE map to purely
    dynamic. Correct for a required atom field (a none() required value really
    does empty the static map), but wrong for always-optional domain/optional
    values. Verified: closed_map([{[:integer], dynamic()}, {:b, integer()}])
    becomes %{dynamic: ...} with static lower bound none(), discarding the
    legitimate static part %{b: integer()} (the integer-domain key is
    optional, so the map can exist with only :b). Direction is toward-dynamic
    (more permissive) => safe (no false positives). Tightenable by gating
    static_empty? to required fields.

N3. %URI{} vs bare %{__struct__: URI} — DESIGN CHOICE (struct well-formedness).
    Verified match?(%URI{}, %{__struct__: URI}) == true at runtime, but the
    typer models %URI{} as the well-formed closed struct, so the intersection
    with a bare struct map is empty => "never match". This is the deliberate
    "__struct__ implies a well-formed struct" invariant; constructing bare/
    ill-formed structs is discouraged. Not a bug unless the invariant is
    reconsidered.

N4. :erlang.is_integer/3 signature (apply.ex:344; commit 127901b8f) —
    LOW-PRIORITY DIAGNOSTIC FALSE NEGATIVE on OTP without the BIF (upgraded
    from "benign"). Deliberate forward-compat for the upcoming range guard
    is_integer(Term, Min, Max). BUT the effect is not benign: in
    signature/6 (apply.ex:1516-1519) a non-:none static signature
    short-circuits and SKIPS export/6, the only path that emits the
    {:undefined, ...} warning (apply.ex:1563). Verified empirically:
    :erlang.is_integer(x, 1, 2) type-checks cleanly as boolean() with no
    diagnostic, while the equally-non-existent :erlang.totally_made_up_fun(x)
    warns {:badfunction, :erlang}. So on OTP where is_integer/3 is undef, a
    call to it is silently accepted instead of warned undefined — a real (if
    minor) false negative for as long as such OTP is supported.

N5. tuple_delete_at over-approximation (tuple_delete_static, descr.ex:5258) —
    REAL precision bug (over-approx = allowed direction), shares B3's root
    cause. Verified: tuple_delete_at(t2, 0) on size>=2 tuples (t2 built as
    open\{}\{term}) yields {...} admitting {}, while the equal? canonical
    open_tuple([term(),term()]) deletes to {term(), ...}; congruence is
    violated and layout is lost. Mechanism: tuple_delete_static uses the
    SHARED projection machinery (tuple_bdd_to_dnf_with_negations +
    tuple_take_element + tuple_split_negative +
    tuple_pair_projection_keeps_full_snd?), i.e. the same optional-marker path
    as tuple_fetch (B3) — NOT the bdd_map/:bdd_top path of tuple_insert.
    IMPORTANT: it is fixed by the B3 work ONLY if that fix touches the shared
    projection/optional-marker machinery; a local patch to tuple_fetch alone
    (e.g. a recompute inside tuple_bdd_fetch_static) does NOT fix it. There
    are three distinct sites: tuple_fetch + tuple_delete share the projection
    machinery; tuple_insert is a separate bdd_map/:bdd_top bug.
