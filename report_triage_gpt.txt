Most of the remaining report is over-claimed. The big pattern is: if the premise is “attacker can run macros, compiler tracers, on_load, on_definition, tamper ETS from same node, set compiler env vars, or inject BEAM/debug-info into the compiler,” that is generally not a new vuln in Elixir’s model. Compilation already executes trusted code.
Triage
Likely Not Security Issues
- 163 public elixir_modules ETS hijack
- 776 public per-module ETS callback/attribute tampering
- 1521 --remsh
- 1923 import/require hijack via AST metadata
- 2676 public elixir_config ETS / tracer injection
- 3210 return_compiler_module cast / arbitrary purge
- 3550, 586 __escape__/1 execution / AST injection
- 4108 predictable bootstrap cache keys
- 4452 ERL_COMPILER_OPTIONS
- 5093 on_definition callback injection
- 5290 struct expansion race for unintended module
- 5455 lexical tracker PID exposure
- 5576 process-dict BEAM injection
- 6427 module loading side effects in tainted expansion
- 6961 forgeable {if_undefined, apply} metadata
Reason: all of these assume capabilities Elixir already treats as trusted compile/build/node access. They may describe alternate paths to arbitrary code execution, but not new privilege boundaries.
Real But Not Security
- 4221 eval process-dictionary reentrancy
- 1, 2149, 4985 recursive macro expansion DoS claims
- 1154, 1676, 2352, 2581, 4574, 6701 atom exhaustion claims
Reason:
- 4221 is a real correctness/diagnostics bug, not a vuln.
- recursive macro expansion is mostly “trusted macros can already loop forever”; worth hardening maybe, but not high-severity security.
- atom creation items mostly describe APIs/compiler paths that intentionally intern atoms from trusted source; that is not a new security boundary.
Already Fixed / Already Labeled
- 350 fixed
- 469 fixed
- 1791 fixed
- 3080 fixed
- 5788 fixed
- plus 4221 already effectively triaged as “reported, only reentrancy is real”
Worth Keeping As Actual Bugs / Hardening
These are the ones that still look actionable on their own merits:
- 105 ANSI injection in unused-import warning
- 251 ANSI injection in parse errors
- 1089 path traversal in elixir_compiler:binary_to_path/2
- 4822 missing upper bound on capture position
- 6118 unbounded recursive parsing via string_tokens_parse
Why:
- 105: Function is formatted with ~ts unsanitized in elixir_lexical.erl; that can corrupt terminal/log output.
- 251: parse error formatting reconstructs user-controlled binary content and splices it into messages unsanitized.
- 1089: binary_to_path/2 does filename:join(CompilePath, atom_to_list(ModuleName) ++ ".beam") with no containment check. If weird module atoms with separators are accepted upstream, this can write outside the intended directory.
- 4822: elixir_fn:escape/3 accepts any positive integer &N, while only 1..255 is valid. That is a real correctness bug.
- 6118: nested interpolation reparses recursively without an explicit depth bound; that looks like a real crash/DoS bug.
Borderline / Needs Deeper Review
- 3832 debug_info(core_v1) compile options
- 6836 no_parens_remote/2
Notes:
- 6836 is not arbitrary invocation in the scary sense; the code explicitly does apply(Atom, Fun, []) for deprecated module.function syntax without parens in elixir_erl_pass.erl:757-769. That is surprising behavior, but it looks like intentional compatibility semantics, not a vuln.
- 3832 is the only “execution” claim I’d still want a closer look at, because BEAM debug-info processing may cross a different trust boundary than normal macro execution. Still, likely low priority unless there is a concrete untrusted-BEAM ingestion path.
Recommended shortlist
If you want a focused follow-up list, I’d keep only:
1. ANSI injection in warnings/errors (105, 251)
2. binary_to_path/2 containment/path traversal (1089)
3. capture upper-bound validation (4822)
4. recursive interpolation parsing depth (6118)
5. eval PD reentrancy as correctness (4221)
